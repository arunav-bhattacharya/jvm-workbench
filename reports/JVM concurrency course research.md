# Loom's Maturity Rewrites the JVM Concurrency Syllabus

As of October 2026 the core semantics of every topic in this course are stable — the Java Memory Model's happens-before rules, the `java.util.concurrent` contracts, the Reactive Streams protocol, kotlinx.coroutines' structured-concurrency rules and Kotlin's variance rules have not changed in substance — but the operational layer around that core has moved far enough that tutorials written in 2023 now teach more than twenty false or obsolete facts. The decisive shifts are that **JDK 24 stopped `synchronized` from pinning virtual threads and removed `-Djdk.tracePinnedThreads`**, **JDK 25 (the current LTS) made scoped values final** and sent all executor-less `CompletableFuture` async work to the common pool, **JDK 26 removed `Thread.stop`**, and **structured concurrency is still a preview API in JDK 27** (GA 15 September 2026) with a changed exception model, becoming final without changes in JDK 28 in March 2027; the library versions to pin are reactor-core 3.8.8, kotlinx.coroutines 1.11.0, Kotlin 2.4.21, Resilience4j 2.4.0 and Spring Framework 7. The misconceptions worth course time fall into a few families: visibility mistaken for atomicity, a thread-safe container mistaken for thread-safe code, assembly mistaken for execution in reactive pipelines, escape hatches that quietly leave structured concurrency (`launch(SupervisorJob())`, `runCatching` around suspending calls), "`out` means immutable", and "virtual threads are faster threads". On format, the learning-science evidence is as clear as the technical sources: only retrieval practice (g ≈ 0.5–0.7) and spacing (d ≈ 0.46) earn a high-utility rating, so each 35-minute session should open with about 10 minutes of auto-graded spaced review, ask for a prediction before teaching, fade worked examples quickly for a senior audience, mix easily confused constructs in practice, and close with a retrieval quiz feeding a scheduler limited to three to five new items a day. Two limits apply throughout: the JLS chapter 17 text and several JEP pages were checked only indirectly, and no study has tested a 35-minute session split on experienced professionals, so the session design below is a reasoned combination of supported findings rather than a tested protocol.

Two consequences follow for this course. First, it needs a declared baseline: **JDK 25 LTS** for virtual threads, scoped values and executors, and **JDK 27 with `--enable-preview`** for structured concurrency, because JDK 28 makes the JDK 27 API final without changes and later migration becomes "a build change, not a code change" ([InfoQ](https://www.infoq.com/news/2026/10/jep-543-jdk-28/)). The lab build does not yet match that baseline. `/home/user/jvm-workbench/labs/build.gradle.kts` pins Kotlin 2.4.21, kotlinx-coroutines 1.11.0 and reactor-core 3.8.8, all current, but compiles every track with `options.release.set(21)` and declares no toolchain. The final `ScopedValue` API and the JDK 27 `StructuredTaskScope` therefore cannot compile in the `vthreads` track, and whether a pinning demo shows JDK 21 or JDK 24+ behaviour depends on whichever JDK happens to run Gradle. A per-track release of 25 (or 27 plus `--enable-preview` for the structured-concurrency lessons) and an explicit runtime toolchain would fix both, and a deliberate side-by-side run of the same pinning demo on JDK 21 and JDK 25 is itself one of the most persuasive lessons available. Second, these facts have expiry dates. JDK ships every March and September, kotlinx.coroutines 1.12 is scheduled to turn the dispatcher-key deprecation into an error, reactor-core 3.9.0-RC1 shipped on 22 October 2026, and Resilience4j 3 (Java 21 baseline) is in development, so version-sensitive cards need a re-verification pass every release cycle.

## The memory model is unchanged since Java 5; the tooling around it is not

The contract engineers need is short. **"The results of a write by one thread are guaranteed to be visible to a read by another thread only if the write operation happens-before the read operation"**, and the JDK 25 `java.util.concurrent` package documentation restates the edges that matter in practice: program order within a thread, unlock→lock of the same monitor, volatile write→read of the same field, `Thread.start`, termination→`join`, transitivity, and the library's release→acquire extensions for concurrent collections, executor submission, `Future.get`, locks, semaphores, latches, barriers and `Exchanger` ([j.u.c package-info @ jdk-25-ga](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/package-info.java)). The JLS adds the interrupt edge and the data-race-free guarantee, under which correctly synchronized programs behave as if sequentially consistent. This research could not fetch the JLS SE 25 page, so lessons should quote the verified package Javadoc and check any JLS wording against the published spec before printing it. The "same monitor, same variable" qualifier is the idea learners trip over most: a volatile write to `a` followed by a volatile read of `b` creates no ordering at all. **Nothing about happens-before, `volatile`, `synchronized`, `ConcurrentHashMap`, atomics or synchronizers changed between JDK 21 and JDK 27**, so memory-model lessons written against JDK 25 stay valid.

For engineers who need to go below `volatile`, the VarHandle Javadoc gives a four-rung ladder: plain accesses are "bitwise atomic only for references and for primitive values of at most 32 bits" and promise no ordering across threads; opaque accesses are atomic and coherent per variable; acquire/release adds one-way message passing; and volatile adds a single total order, matching C/C++11 `memory_order_seq_cst` ([VarHandle.java @ jdk-25-ga](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/lang/invoke/VarHandle.java)). The jcstress sample suite turns that ladder into observable evidence. `BasicJMM_04_Progress` lists a plain spin loop that never sees the update as an acceptable outcome, records 100% termination for the volatile version, and forbids the stale outcome under opaque mode ([jcstress BasicJMM_04_Progress](https://github.com/openjdk/jcstress/blob/master/jcstress-samples/src/main/java/org/openjdk/jcstress/samples/jmm/basic/BasicJMM_04_Progress.java)). In `RaceCondition_01_RMW`, **two read-modify-write actors on a `volatile int` collided in roughly 11% of recorded samples**, and `BasicJMM_06_Causality` records a reader seeing `y` but not `x` in 0.09% of runs ([jcstress samples](https://github.com/openjdk/jcstress/tree/master/jcstress-samples)). The broken double-checked-locking sample states the problem in one line: omitting `volatile` "breaks safe publication guarantees, as the read of instance on fast path has no memory ordering at all" ([Singleton_07](https://github.com/openjdk/jcstress/blob/master/jcstress-samples/src/main/java/org/openjdk/jcstress/samples/primitives/singletons/Singleton_07_BrokenNonVolatileDCL.java)). Two cautions apply. The samples' own per-platform tables show that weak-memory outcomes depend on hardware (torn 64-bit writes appear on x86_32 but not on ARMv7 VMs that use wider instructions), so "interesting" outcomes should be taught as allowed rather than guaranteed to appear on an x86 laptop, while ARM machines such as Apple Silicon or Graviton show more of them. And jcstress has had **no tagged release since 0.16 (February 2023)**: master is at 0.17-SNAPSHOT, and only a Maven archetype setup is documented ([jcstress README](https://github.com/openjdk/jcstress)).

What did change between JDK 21 and 27 is the API surface and the observability tooling. `Thread.countStackFrames` went in JDK 22, `suspend`/`resume` and `ThreadGroup.stop` in JDK 23, and **`Thread.stop` in JDK 26**, after throwing `UnsupportedOperationException` since JDK 20; old binaries calling it now fail with `NoSuchMethodError` ([JDK-8368370](https://bugs.openjdk.org/browse/JDK-8368370); [OpenJDK history](https://github.com/openjdk/jdk)). The JDK 26 `Thread` Javadoc gained an interruption section telling callers to rethrow `InterruptedException` or restore the flag with `Thread.currentThread().interrupt()` ([Thread.java @ jdk-27-ga](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/Thread.java)), and JEP 500 makes changing a `final` field through deep reflection print a warning by default in JDK 26, ahead of a planned hard failure ([JEP 500](https://openjdk.org/jeps/500)). Diagnostics improved in every release. JDK 24 added the `jcmd Thread.vthread_scheduler` and `Thread.vthread_pollers` commands and put currently mounted virtual threads into `Thread.print` ([diagnosticCommand.hpp @ jdk-27-ga](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/hotspot/share/services/diagnosticCommand.hpp)). **JDK 25's JSON thread dump gives each thread `state`, `parkBlocker`, `blockedOn`, `waitingOn`, `monitorsOwned`, `owner`, `carrier` and `virtual` fields**, where the JDK 21 dumper wrote only `tid`, `name` and `stack` ([threadDump.schema.json @ jdk-25-ga](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/jdk.management/share/classes/com/sun/management/doc-files/threadDump.schema.json)). JDK 26 added the owners of `java.util.concurrent` locks to the dump and JDK 27 a `formatVersion` key ([OpenJDK history](https://github.com/openjdk/jdk)), and JDK 25 added the `JavaMonitorDeflate`, `JavaMonitorStatistics` and `JavaMonitorNotify` JFR events. No JFR event detects deadlock, so deadlock lessons still go through `jcmd Thread.print` or `ThreadMXBean` ([JFR metadata.xml @ jdk-27-ga](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/hotspot/share/jfr/metadata/metadata.xml)).

The misconceptions here are old but costly, and each has a runnable disproof. **`volatile` gives visibility and ordering, not an atomic read-modify-write**, as the jcstress collision rate shows and as the kotlinx.coroutines guide puts bluntly with "Volatiles are of no help" for counters ([shared-mutable-state guide](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/shared-mutable-state-and-concurrency.md)). **A concurrent collection makes single operations atomic, not sequences of them**: `containsKey` followed by `put` is a race, while `computeIfAbsent` runs "atomically", should be "short and simple", must not modify the map, and throws `IllegalStateException` when it detects a recursive update ([ConcurrentHashMap.java @ jdk-25-ga](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/ConcurrentHashMap.java)). **Catching `InterruptedException` and logging it does not handle it**, because methods that throw it clear the flag first, and the JDK's own commit log shows its engineers making this mistake in `sun.security.ssl`, `FileSystemPreferences` and `ImageIcon`, fixed as recently as JDK 23–24 ([OpenJDK history](https://github.com/openjdk/jdk)). **A thread stuck in `ReentrantLock.lock()` reports WAITING, not BLOCKED**, because BLOCKED applies only to monitors and `LockSupport.park` produces WAITING ([Thread.java @ jdk-27-ga](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/lang/Thread.java)). `StampedLock` is "not reentrant", and its optimistic reads give ordering guarantees only when `validate` succeeds ([StampedLock.java](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/locks/StampedLock.java)). Lock fairness "does not guarantee fairness of thread scheduling", and untimed `tryLock` jumps the queue ([ReentrantLock.java](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/locks/ReentrantLock.java)). `Object.wait` belongs inside a loop because spurious wakeups are permitted ([Object.java @ jdk-25-ga](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/lang/Object.java)). The JDK 25 fix for a deadlock risk in `java.util.logging.Handler`'s synchronized `publish()` makes the rule "never call outside code while holding a lock" concrete ([OpenJDK history](https://github.com/openjdk/jdk)).

## Virtual threads moved the bottleneck from threads to downstream resources

The executor framework has kept the shape it had in JDK 5, but its details shifted in ways that break copied examples. `ExecutorService` has been `AutoCloseable` since JDK 19, with a default `close()` that shuts the executor down and waits, and `Future` gained `state()`, `resultNow()` and `exceptionNow()` in the same release ([JDK-8285450](https://bugs.openjdk.org/browse/JDK-8285450); [ExecutorService.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/ExecutorService.java)). In JDK 25, `ForkJoinPool` began implementing `ScheduledExecutorService` and gained `submitWithTimeout` ([JDK-8362881](https://bugs.openjdk.org/browse/JDK-8362881)), and **`CompletableFuture` async methods without an explicit executor now always use the common pool**; before JDK 25 they fell back to a new thread per task whenever common-pool parallelism was below 2, which in practice meant one- and two-core containers ([net-dev, Oct 2025](https://mail.openjdk.org/pipermail/net-dev/2025-October/028226.html)). JDK 27 removed `ThreadPoolExecutor.finalize()` ([JDK 27 release notes](https://www.oracle.com/java/technologies/javase/27-relnote-issues.html)). The long-standing traps still deserve lessons. If any run of a periodic task throws, "subsequent executions are suppressed", with nothing logged ([ScheduledExecutorService Javadoc](https://www.iitk.ac.in/esc101/share/documentation/docs/api/java/util/concurrent/ScheduledExecutorService.html)). Pool sizing still starts from Goetz's `N = N_cpu × U_cpu × (1 + W/C)` (cores × target utilization × (1 + wait time ÷ compute time)) but should end with a load test ([Zalando Engineering](https://engineering.zalando.com/posts/2019/04/how-to-set-an-ideal-thread-pool-size.html)). The single best executor exercise has learners predict pool size, queue depth and rejections for a given `ThreadPoolExecutor` configuration, built on the rule that a pool grows past its core size only when its queue refuses a task. This research could not re-fetch the `ThreadPoolExecutor` Javadoc, so authors should re-check the queuing rules against the JDK 25 documentation before shipping that exercise.

Virtual threads have been final since JDK 21, but **JDK 25 is the first LTS in which they are production-safe by default**, because JEP 491 in JDK 24 lets a virtual thread "acquire, hold, and release monitors, independently of their carriers" ([JEP 491](https://openjdk.org/jeps/491)); Apple's ServiceTalk documentation names JDK 25 as the first release suitable for large-scale virtual-thread production ([ServiceTalk](https://apple.github.io/servicetalk/servicetalk/SNAPSHOT/virtual-threads.html)). Pinning has not disappeared. A virtual thread still pins its carrier when native code (JNI or an FFM downcall) calls back into Java that blocks, and when it blocks inside a class initializer, although JDK 26 lets threads that are merely *waiting* for another thread's class initializer unmount ([JEP 491](https://openjdk.org/jeps/491); [JDK 26 release notes](https://www.oracle.com/java/technologies/javase/26-relnote-issues.html)). Detection changed too: **`-Djdk.tracePinnedThreads` was dropped in JDK 24** ([serviceability-dev](https://mail.openjdk.org/pipermail/serviceability-dev/2025-May/064051.html)), leaving the JFR `jdk.VirtualThreadPinned` event, which has a 20 ms default threshold in JDK 25 and carries `blockingOperation`, `pinnedReason` and `carrierThread` fields ([InfoQ](https://www.infoq.com/articles/virtual-threads-after-jdk24/); [metadata.xml](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/hotspot/share/jfr/metadata/metadata.xml)). One practitioner test caught a native-call pin only after explicitly enabling the event at a 10 ms threshold ([devdojo](https://devdojo.academy/en/blog/virtual-thread-pinning-jdk-24-what-still-pins/)), a single data point but a good reason to lower thresholds in staging.

The best-known production failure explains why the course should teach resources rather than threads. Netflix enabled virtual threads on Java 21 with Spring Boot 3 and embedded Tomcat and saw services hang: virtual threads blocked inside `synchronized` pinned every carrier, so the virtual thread due to acquire the lock next could never get a carrier to run on ([InfoQ, Aug 2024](https://www.infoq.com/news/2024/08/netflix-performance-case-study)). JEP 491 removes that class of bug, but the lessons that survive JDK 25 are about what virtual threads expose. "Connection pools, rate limits, file descriptors, and downstream services become the real concurrency boundaries" ([InfoQ](https://www.infoq.com/articles/virtual-threads-after-jdk24/)). `ThreadLocal` caches stop caching because each task gets a fresh thread, and JEP 444 warns against using thread-locals to pool costly resources ([JEP 444](https://openjdk.org/jeps/444)). Pooling virtual threads remains wrong: a September 2026 Quarkus measurement found that pooling saved little allocation at a substantial memory cost ([Quarkus](https://quarkus.io/blog/to-cache-or-not-to-cache-virtual-threads/)). Little's law (requests in flight = arrival rate × latency) turns the point into arithmetic. An API serving 5,000 requests per second at 400 ms latency holds 2,000 requests in flight, so a 200-thread pool caps it at 500 requests per second, and once virtual threads remove that cap the database connection pool becomes the limit. The same reasoning disproves **"virtual threads are faster"**: they provide scale, not speed, and CPU-bound work gains nothing because a virtual thread computes only while mounted on one of a small set of carrier platform threads ([JEP 444](https://openjdk.org/jeps/444)). The right limiter is a `Semaphore` or bulkhead around the scarce resource, not a smaller pool.

Structured concurrency is where API churn bites hardest. JEP 505 in JDK 25 replaced the subclassing API (`ShutdownOnFailure`) with static `open()` factories and `Joiner`s ([InfoQ, JEP 505](https://www.infoq.com/news/2025/05/jep-505-concurrency-preview-5)). JEP 525 in JDK 26 made `allSuccessfulOrThrow()` return a `List` and renamed `anySuccessfulResultOrThrow()` to `anySuccessfulOrThrow()` ([JDK-8367858](https://bugs.openjdk.org/browse/JDK-8367858)). **JEP 533 in JDK 27 added a third type parameter so that the built-in joiners throw the standard `ExecutionException` instead of the preview-only `FailedException`** ([InfoQ, JEP 533](https://www.infoq.com/news/2026/05/jep-533-jdk-27/)), visible in the JDK 27 source as `sealed interface StructuredTaskScope<T, R, R_X extends Throwable>` ([StructuredTaskScope.java @ jdk-27-ga](https://github.com/openjdk/jdk/blob/jdk-27-ga/src/java.base/share/classes/java/util/concurrent/StructuredTaskScope.java)). JEP 543 makes that API final in JDK 28 without changes ([InfoQ, JEP 543](https://www.infoq.com/news/2026/10/jep-543-jdk-28/)), and OpenJDK master already marks the class `@since 28` with no preview annotation ([master source](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/StructuredTaskScope.java)). A course launching now should therefore teach the JDK 27 shape and warn JDK 25 LTS users that, on their JDK, `allSuccessfulOrThrow()` yields a stream of subtasks rather than a `List` and failures arrive as `FailedException` rather than `ExecutionException`. Scoped values need no such hedging: **JEP 506 made them final in JDK 25**, the one late change being that `orElse` no longer accepts `null` ([JEP 506](https://openjdk.org/jeps/506)), and child tasks forked in a scope inherit the parent's bindings ([inside.java](https://inside.java/2025/10/20/jdk-25-performance-improvements/)). The pairing makes a clean contrast lesson: a `ThreadLocal` value leaks from one pooled request into the next unless removed, while a scoped value is unbound the moment `run()` returns.

## Reactor earns its complexity on streams, not on request/response

The current stable line is **reactor-core 3.8.8 (22 October 2026) in release train 2025.0 (BOM 2025.0.8)**, and 3.9.0-RC1 with BOM 2026.0.0-RC1 shipped the same day ([Maven Central](https://repo1.maven.org/maven2/io/projectreactor/reactor-core/); [v3.9.0-RC1 notes](https://github.com/reactor/reactor-core/releases/tag/v3.9.0-RC1)). "Reactor 3 requires Java 8 or + to run" ([README 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/README.md)). The jar is multi-release, with Java 8, 11 and 21 variants, and since 3.6 the shared `boundedElastic()` scheduler runs "every submitted task" on a new virtual thread when `reactor.schedulers.defaultBoundedElasticOnVirtualThreads=true` is set on a Java 21+ runtime ([Schedulers.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/scheduler/Schedulers.java)). Reactor 3.8.0 adopted JSpecify nullness annotations, which its release notes warn can look like breaking changes to Kotlin callers; it also added `RepeatSpec` and made `Flux#map` reject a `null` mapper result ([v3.8.0 notes](https://github.com/reactor/reactor-core/releases/tag/v3.8.0)). Deprecated APIs linger — `Flux.first(...)` still carries a "to be removed in reactor 3.5" note in 3.8.x ([Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)) — and the reference guide still mentions `Schedulers.elastic()`, which no longer exists in the 3.8.x source ([Schedulers.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/scheduler/Schedulers.java)).

Underneath sits the Reactive Streams 1.0.4 protocol: four interfaces, seven one-way methods, the signal grammar `onSubscribe onNext* (onError | onComplete)?`, and numbered rules such as 1.3 (signals must not be concurrent), 1.9 (`onSubscribe` comes first), 2.13 (no nulls) and 3.9 (`request(n ≤ 0)` must produce `onError(IllegalArgumentException)`) ([Reactive Streams spec](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/README.md)). `java.util.concurrent.Flow` mirrors it one-for-one, with a default buffer of 256 ([Flow.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/Flow.java)), and Reactor builds a lazy "push-pull hybrid" on top, in which the subscriber pulls with `request(n)` and the publisher pushes items as they become ready ([reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)). The gap between spec and implementation makes a revealing lesson: Reactor's operators answer a bad `request(0)` by logging "Negative request" at DEBUG and emitting nothing ([Operators.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Operators.java)), so a hand-written subscriber with bad demand silently stalls instead of failing as rule 3.9 requires.

The semantics engineers get wrong are concentrated and testable. **Nothing happens until `subscribe()`**, yet **`Mono.just(callApi())` runs the call once, when the pipeline is assembled**, because the item "is captured at instantiation time"; `fromCallable` or `defer` makes the work happen per subscription ([Mono.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)). That matters doubly for retries, since `retry` "works by re-subscribing", and re-subscribing to an already-captured value never calls the service again ([error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)). **`flatMap` "does not necessarily preserve original ordering"** and by default subscribes to up to 256 inner publishers with a prefetch of 32, while `concatMap` preserves order with no prefetch and `flatMapSequential` subscribes eagerly but emits in source order ([Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)); nor is `flatMap` parallelism in itself, since any concurrency comes from the inners being asynchronous. **Only the `subscribeOn` closest to the source takes effect**, wherever it sits in the chain, while `publishOn` switches threads for the operators after it, and `block()` throws `IllegalStateException` on `parallel` and `single` threads ([schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)). **Errors are terminal**: an error operator replaces the upstream with a fallback sequence rather than resuming it, and `onErrorContinue` is officially "a specialist operator that can make the behaviour of your reactive chain unclear", best replaced by handling errors inside each `flatMap` inner ([error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc); [Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)). `Retry.backoff` defaults to a multiplier of 2 and a jitter of 0.5, so deterministic tests need `jitter(0)`, and exhaustion produces "Retries exhausted: N/N" ([Retry.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/retry/Retry.java)). `Mono.zip` with an empty source completes empty and cancels the others instead of erroring ([Mono.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)). The `onBackpressureBuffer`, `Drop`, `Latest` and `Error` operators all request an unbounded amount upstream and then choose what to do with the overflow, which is a loss policy rather than backpressure, and `groupBy` deadlocks unless downstream concurrency is at least the number of groups ([Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)). Testing has its own traps: `StepVerifier`'s `verify()` has no default timeout, and `withVirtualTime` works only if the `Flux` is created inside the supplier ([testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)).

On whether reactive is still worth it, the maintainers' position is that virtual threads and reactive complement each other. Mark Paluch wrote that "the reasons to use asynchronous programming models go away in many cases" on virtual threads, while ReactiveX-style APIs remain "the right approach for concurrent scenarios in which declarative concurrency (such as scatter-gather) matters" and for managing demand, backpressure and cancellation in pipelines ([Spring blog](https://spring.io/blog/2022/10/11/embracing-virtual-threads)). The current Spring Framework docs still say that an MVC application that works fine has "no need to change", that blocking persistence APIs make MVC "the best choice for common architectures", and that reactive "generally do[es] not make applications run faster", because the payoff is scaling on few threads and that requires real I/O latency ([WebFlux docs](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/web/webflux/new-framework.adoc)). This research found no 2025–2026 statement by a named Spring or Reactor maintainer updating that view. A defensible course position is therefore virtual threads plus plain imperative code for request/response over JDBC or JPA; Reactor for streaming, demand control, rate-limited fan-out, composable retries and timeouts, or stacks that are already reactive; and coroutines for Kotlin teams, with Spring mapping `Mono<T>` to a `suspend fun` and `Flux<T>` to `Flow<T>` ([Spring Kotlin coroutines docs](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/languages/kotlin/coroutines.adoc)). For lab readiness, BlockHound, `reactor-tools` and Micrometer context-propagation are not yet dependencies in `/home/user/jvm-workbench/labs/reactive/build.gradle.kts`, so lessons on blocking detection, the production debug agent and automatic `ThreadLocal` propagation need them added; `reactor-tools` 3.8.8 is aligned in BOM 2025.0.8 ([reactor-bom 2025.0.8](https://repo1.maven.org/maven2/io/projectreactor/reactor-bom/2025.0.8/reactor-bom-2025.0.8.pom)).

## Coroutine bugs cluster in the escape hatches from structured concurrency

**kotlinx.coroutines 1.11.0 is the latest release.** Maven Central's `latest` and `release` both point to it, with no 1.11.x patch or 1.12 pre-release as of late October 2026, and it is built against Kotlin 2.2.20 while the compiler itself is at **Kotlin 2.4.21 (8 October 2026)** ([Maven metadata](https://repo1.maven.org/maven2/org/jetbrains/kotlinx/kotlinx-coroutines-core/maven-metadata.xml); [Kotlin releases](https://kotlinlang.org/docs/releases.html)). The 1.9–1.11 changes worth teaching are a stable `limitedParallelism(n, name)`; the new `Flow.chunked` and `Flow.any/all/none` operators; a ground-up rewrite of the KDoc on structured concurrency and error handling; deprecation of `CoroutineDispatcher` as a context key ("WARNING since 1.11, ERROR since 1.12, remove in 1.13"); a lint check that flags passing a `Job` to coroutine builders; and ERROR-level deprecation of `runTest(dispatchTimeoutMs)` ([CHANGES.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/CHANGES.md); [CoroutineDispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)). On the language side, Kotlin 2.4.0 made explicit backing fields stable, which removes the `_state`/`state` property pair from the standard `StateFlow` pattern ([What's new 2.4](https://raw.githubusercontent.com/JetBrains/kotlin-web-site/master/docs/topics/whatsnew/whatsnew24.md)).

The mental model starts with the compiler: every suspend function takes a hidden `Continuation` parameter, returns either its result or the marker `COROUTINE_SUSPENDED`, and compiles to a state machine with one class per suspending lambda ([KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)). That alone refutes **"suspend means it runs on a background thread"**: the dispatcher decides the thread, and a suspend function that never suspends runs entirely on its caller's thread. The 1.11 KDoc states the structured-concurrency contract — a parent cannot complete before its children, cancellation flows down, a non-cancellation failure flows up through non-supervisor jobs, and a `CancellationException` does not notify the parent ([Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)) — and most production bugs are ways of stepping outside that contract without noticing. **A failed `async` cancels its parent whether or not anyone calls `await`**, unless the parent is a supervisor or there is no parent. **Passing `SupervisorJob()`, or any `Job`, to `launch` does the opposite of what people intend**: the passed job becomes the parent, so the scope stops waiting for and cancelling the coroutine, and its failure goes unhandled; the KDoc notes that this "does not throw an exception only for backward compatibility reasons" ([Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)). Supervisors belong in the scope constructor or in `supervisorScope {}` ([CoroutineScope.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineScope.kt)). A `CoroutineExceptionHandler` fires only for uncaught exceptions at the root or directly under a supervisor, and never for `async` ([exception-handling guide](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/exception-handling.md)). `runBlocking` inside a suspend function is "redundant and blocks the thread", and nested `runBlocking` calls share an event loop and can run each other's tasks ([Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)). `GlobalScope` is "an antipattern", and swapping it for `CoroutineScope().launch` "suffers from all the pitfalls" ([CoroutineScope.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineScope.kt)).

Cancellation is the second cluster. It is cooperative: a cancelled coroutine runs until its next suspension point, and blocking calls such as `Thread.sleep` or `BlockingQueue.take` are not interrupted unless wrapped in `runInterruptible` ([cancellation guide](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)). So **`withTimeout(1.seconds) { Thread.sleep(10_000) }` "will run to completion, taking 10 seconds"**, and because `TimeoutCancellationException` is a `CancellationException`, a timeout inside `launch` lets the parent "finish normally" instead of failing it ([Timeout.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Timeout.kt)). The guide warns that catching `CancellationException` "can break the cancellation propagation" ([cancellation guide](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)), and since the standard library's `runCatching` catches every `Throwable` ([runCatching](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/run-catching.html)), **`runCatching` around suspending calls swallows cancellation**. No official page calls it an anti-pattern, but the conclusion follows directly from those two sources. Dispatchers and shared state form the third cluster. `Dispatchers.Default` has one thread per core (at least two), while `Dispatchers.IO` defaults to 64 threads or the core count, shares threads with Default, and spawns elastic `limitedParallelism(n)` views whose limits add to that 64 rather than drawing from it; the KDoc's own example reaches 64 + 100 + 60 blocking tasks at once ([Dispatchers.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Dispatchers.kt)). **`limitedParallelism(1)` "is not a mutex"**: it runs the code between suspension points one coroutine at a time, but coroutines that suspend inside it interleave ([CoroutineDispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)). `Mutex` is non-reentrant, so a nested `withLock` on the same mutex suspends forever ([Mutex.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/sync/Mutex.kt)).

Flow is cold, sequential and runs in its collector's context: `flowOn` changes only the upstream context, and emitting from inside `withContext` throws `IllegalStateException` ([flow/Builders.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Builders.kt)), while `catch` sees only upstream exceptions ([Flow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Flow.kt)). A subtle trap survives into 1.11.0: `flow {}` checks for cancellation on every `emit`, but **flows built with `asFlow()` skip that check and are not cancellable** without `.cancellable()` ([Builders.kt @ 1.11.0](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.11.0/kotlinx-coroutines-core/common/src/flow/Builders.kt)). The rewritten Flow guide on master dropped the section that demonstrated this, so authors who read only the current kotlinlang page will miss it ([flow.md @ 1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)). `StateFlow` "never completes" and drops any new value that `equals` the current one, which makes it a state holder, not an event bus ([StateFlow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/StateFlow.kt)). In tests, `runTest` skips delays using virtual time but times out after 60 seconds of real time, does not virtualize `withContext(Dispatchers.Default/IO)` inside the code under test (so dispatchers must be injected), and needs `backgroundScope` for producers that never finish ([test README](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-test/README.md)); Turbine 1.2.1's three-second timeout is likewise real time ([Turbine](https://raw.githubusercontent.com/cashapp/turbine/trunk/README.md)). On virtual threads, JetBrains' own material still compares coroutines only with platform threads, and none of the 1.11 sources mention Loom ([coroutines-basics](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-basics.md)); the supported bridge is `Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()` ([Executors.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Executors.kt)). Interop with Reactor (`mono {}`, `flux {}`, `asFlux`, `awaitSingle`) and with `CompletableFuture` (`future {}`, and `await()`, which calls `cancel(false)` on the future when the awaiting coroutine is cancelled) is first-class ([reactor README](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/reactive/kotlinx-coroutines-reactor/README.md); [Future.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/future/Future.kt)). Roman Elizarov's structured-concurrency essays could not be fetched, so any quote from them needs checking before use.

## Declaration-site variance does Java's PECS bookkeeping once

Kotlin keeps the JVM's generics model — type arguments erased at runtime, types invariant by default — and adds declaration-site variance (`out`/`in` on the type parameter itself), use-site projections that play the role of Java wildcards, and reified type parameters on inline functions. It also makes nullability part of every type argument, with a default upper bound of `Any?` and `T & Any` as the definitely non-nullable form ([Kotlin generics](https://kotlinlang.org/docs/generics.html)). The docs' own mnemonic is "Consumer in, Producer out!", tied explicitly to PECS from *Effective Java* Item 31 (same source). The payoff for a Java engineer is concrete. Because Kotlin declares `Comparable` as `in T`, its `fun <T : Comparable<T>> maxOf(a: T, b: T)` compiles to Java's `<T extends Comparable<? super T>>`, and a Kotlin `fun <T : Comparable<T>> List<T>.biggest()` accepts a list of `Dog`, where `Dog` extends a `Comparable<Animal>`, with no wildcard at the call site ([kotlinc 2.4.21 probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)). The variance bookkeeping that Java makes every API author repeat is written once, on the declaration.

The position rules are where learners guess, and compiler probes with kotlinc 2.4.21 settle them ([kotlinc 2.4.21 probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)). Return types and `val` types are out-positions; parameter types and the bounds of a member function's own type parameters are in-positions; `var` types and type arguments of invariant generics are invariant; and each `in` layer flips the sign, so a callback parameter `(T) -> Unit` is legal in an `out` class while a return type of `(T) -> Unit` is not. **Only `private` members are exempt — `protected` and `internal` are checked — and private members become "private to this"**, so touching another instance's private `var t: T` fails with `cannot access 'var t: T': it is private/*private to this*/`. Inferred public return types count too, which makes them a frequent silent trap. The K2 error format is `type parameter 'T' is declared as 'out' but occurs in 'in' position in type '…'.`, with a lowercase first letter on the command line; older blog posts show K1 wording, and lessons should not mix the two. Star projections follow a per-parameter rule — for an invariant parameter, `Foo<*>` reads as `out TUpper` (its upper bound) and writes as `in Nothing` — and the docs call them "very much like Java's raw types, but safe" ([Kotlin generics](https://kotlinlang.org/docs/generics.html)). That safety is the lesson: `MutableList<*>` rejects even `add(null)` yet still permits `clear()` and `removeAt(0)`, while `MutableList<Any?>` refuses a `MutableList<String>` argument outright ([kotlinc probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)).

Java interop has asymmetries that surprise even experienced developers. The compiler generates wildcards for variant types **only in parameter positions — never in return types, and never for final type arguments** such as `String` ([Calling Kotlin from Java](https://kotlinlang.org/docs/java-to-kotlin-interop.html)), so a Kotlin library returning `List<Number>` hands Java callers an invariant list while Kotlin callers see a covariant one.

| Kotlin declaration | Java signature |
|---|---|
| parameter `l: List<Number>` | `List<? extends Number>` |
| return type `List<Number>` | `List<Number>` (no wildcard) |
| parameter `l: MutableList<Number>` | `List<Number>` (invariant) |
| parameter `l: MutableList<in Number>` | `List<? super Number>` |
| parameter `f: (Number) -> Base` | `Function1<? super Number, ? extends Base>` |
| parameter `a: Array<in Number>` | `Object[]` |
| return type `List<Nothing>` | raw `List` |
| `fun <T> dnn(x: T & Any): T & Any` | `<T> T dnn(T)` |
| `inline fun <reified T> f(x: Any)` | synthetic method, invisible to javac |

The Java column comes from `javap` on kotlinc 2.4.21 output ([kotlinc probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)), and `@JvmWildcard` and `@JvmSuppressWildcards` override the defaults ([Calling Kotlin from Java](https://kotlinlang.org/docs/java-to-kotlin-interop.html)).

Erasure and reification complete the picture. `is List<String>` is rejected and unchecked casts only warn, so a bad cast such as `listOf(1, 2) as Any as List<String>` succeeds and fails later, where an element is read, with a `ClassCastException` — heap pollution, the same failure mode as Java raw types ([kotlinc probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)). Reified type parameters exist only on inline functions, cannot be `Nothing`, and do not reify nested arguments: the docs' `asPairOf<String, List<String>>()` "Compiles but breaks type safety!" ([Kotlin generics](https://kotlinlang.org/docs/generics.html); [inline functions](https://kotlinlang.org/docs/inline-functions.html)). Kotlin 2.4.0 turned several former warnings into errors, including `::class` on a reified `T` with a nullable bound (KTLC-370), inconsistent type arguments in generic calls (KTLC-373), and nested-generic supertype mismatches that previously "later failed with a `ClassCastException`" (KTLC-372) ([2.4 compatibility guide](https://kotlinlang.org/docs/compatibility-guide-24.html)); `@BuilderInference` now draws a deprecation warning because builder inference is automatic ([kotlinc probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)). For runtime type information, a practical rule of thumb holds without `kotlin-reflect.jar`: class names, identity, `isInstance`/`cast`/`safeCast` and `typeOf<T>()` (with arguments, variance and nullability) all work, but anything that enumerates declarations — `objectInstance`, `sealedSubclasses`, `members`, `typeParameters` — throws `KotlinReflectionNotSupportedError`, and `toString()` output gains the suffix "(Kotlin reflection is not available)" (same probe). Because the `kotlinc` command line adds kotlin-reflect by default while Gradle builds do not, the same example can behave differently in the two setups ([Kotlin reflection](https://kotlinlang.org/docs/reflection.html)); the course's `generics` lab already handles this with a `-Preflect` switch that puts kotlin-reflect on the demo runtime classpath only on request. `typeOf<T>().javaType`, which in 2.4.21 still requires `@OptIn(ExperimentalStdlibApi::class)`, replaces Java's anonymous-subclass "super type token" trick.

The misconception to hit hardest is **"`out` means read-only or immutable"**. The docs reject it directly — "Immutability is a completely different story" ([Kotlin generics](https://kotlinlang.org/docs/generics.html)) — and calling `clear()` on a `MutableList<*>` makes the point in one line. Close behind come "`*` is the same as `Any?`", "reified gives full runtime generics", "`KClass` knows `List<String>`" (`List<String>::class` does not compile), and "Java sees Kotlin's variance everywhere". No empirical study of how people learn variance was found, so the teaching recommendation rests on reasoning: pair each slogan with a substitution test learners can run in their heads ("if I secretly hand you a `Box<Apple>` where you expected a `Box<Fruit>`, which call could go wrong?"), then introduce the position rules as the mechanical tool for nested cases.

## Sealed types and lambdas absorbed half the GoF catalog

The authoritative modern framing comes from Brian Goetz and Gavin Bierman. The claim that design patterns are workarounds for missing language features is "too facile" in general, they write, but "reasonably accurate in the case of Visitor — if your language has sufficiently powerful pattern matching, the Visitor pattern is almost completely unnecessary"; records and sealing together give Java algebraic data types; and pattern matching "doesn't mean that inheritance hierarchies and virtual methods are wrong" ([Pattern Matching for Java](https://raw.githubusercontent.com/openjdk/amber-docs/master/site/design-notes/patterns/pattern-matching-for-java.md)). Records, sealed interfaces, pattern-matching `switch` with guards and nested record patterns are all final in JDK 21, and Kotlin's `when` guards became stable in 2.2.0 ([What's new 2.2](https://kotlinlang.org/docs/whatsnew22.html)). The result sorts the catalog into three groups. Strategy, Command, Template Method, Visitor, State, Singleton, Prototype and, in Kotlin, Builder are **absorbed by language features**: function values, sealed types with exhaustive `switch`/`when`, `object` declarations, and `data class` with named and default arguments. Proxy, Decorator, Chain of Responsibility and Observer are **absorbed by frameworks and libraries**: Spring and Quarkus AOP, Resilience4j's stackable decorators, servlet filters and OkHttp interceptors, `Flow`, Reactor and `StateFlow`. Facade, Adapter, Bridge, Composite, Mediator and Flyweight **are still designed by hand**. The course stance that follows is "patterns are vocabulary": learn the intent so you recognize the language feature that replaced the pattern, and so you know when that feature is not enough — open hierarchies, cross-cutting concerns, distributed coordination.

The most valuable pattern lessons expose sharp edges the GoF book never mentioned, because they belong to the features that replaced the patterns. **A `default` branch on a sealed `switch` silently accepts new subtypes**, throwing away the compiler's list of unhandled cases that makes sealed State machines worth having, and even an exhaustive switch has a runtime "remainder" of `null` and separately compiled subtypes ([Exhaustiveness note](https://raw.githubusercontent.com/openjdk/amber-docs/master/site/design-notes/patterns/exhaustiveness.md)). **Kotlin's `by` delegation has no open recursion**: "members overridden in this way do not get called from the members of the delegate object", so a `CountingMap` that overrides only `put` misses every `putAll` ([Kotlin delegation](https://kotlinlang.org/docs/delegation.html)). **`copy()` on data classes is shallow** ([Kotlin data classes](https://kotlinlang.org/docs/data-classes.html)), Java records with mutable components share the trap, and in kotlinc 2.4.21 a `data class` with a private constructor still exposes a public `copy()` with only a warning unless annotated `@ConsistentCopyVisibility` ([kotlinc probe](https://github.com/JetBrains/kotlin/releases/download/v2.4.21/kotlin-compiler-2.4.21.zip)), so validation must live in `init`, not in a factory. `lazy(PUBLICATION)` can run its initializer several times ([LazyThreadSafetyMode](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/-lazy-thread-safety-mode/)); companion-object members are instance members, not statics, unless marked `@JvmStatic` ([object declarations](https://kotlinlang.org/docs/object-declarations.html)); `Collections.unmodifiableList` is a read-through view, not a copy ([Collections.java](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/util/Collections.java)); and the JDK's lazy-initialization holder is still moving, since JDK 25's `StableValue` became `LazyConstant` in JDK 26 and is still in third preview in JDK 27 ([PreviewFeature.java @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/java.base/share/classes/jdk/internal/javac/PreviewFeature.java)).

Proxy deserves the most time for backend engineers because its behaviour is observable and differs by framework. Spring AOP uses a JDK dynamic proxy when the target implements an interface and a CGLIB-generated subclass otherwise; `final` and `private` methods cannot be advised; and **a call a bean makes on itself through `this` bypasses the advice**, with refactoring the recommended fix and `AopContext.currentProxy()` "highly discouraged" ([Spring proxying docs](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/core/aop/proxying.adoc)). Quarkus ArC, by contrast, intercepts self-invocation as a non-standard feature and can transform `final` classes so they become proxyable ([Quarkus CDI reference](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/cdi-reference.adoc)), and Kotlin's final-by-default classes need the `kotlin-spring` all-open plugin before Spring can proxy them at all ([all-open plugin](https://kotlinlang.org/docs/all-open-plugin.html)). The same `@Transactional`-style annotation can therefore take effect in one framework and silently do nothing in another, which teaches more about Proxy than any UML diagram. Spring Framework 7 brought resilience into core as proxy-based annotations: `@Retryable` defaults to `maxRetries = 3` after the initial attempt with a one-second delay, and `@ConcurrencyLimit` caps how many calls can run a proxied method at once ([Spring resilience docs](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/core/resilience.adoc)).

The concurrency patterns change most with virtual threads. Thread-per-message is viable again, but only together with a concurrency limit, and with virtual threads a semaphore-based bulkhead becomes the natural limiter. Resilience4j 2.4.0 is the latest release, while the 3.x line on master "requires Java 21" and adds virtual-thread schedulers ([Maven metadata](https://repo1.maven.org/maven2/io/github/resilience4j/resilience4j-circuitbreaker/maven-metadata.xml); [Resilience4j README](https://raw.githubusercontent.com/resilience4j/resilience4j/master/README.adoc)). Its defaults hide a classic test trap: a circuit breaker needs **`minimumNumberOfCalls = 100`** before it evaluates its 50% failure threshold, so naive tests never see it open ([CircuitBreakerConfig.java](https://raw.githubusercontent.com/resilience4j/resilience4j/master/resilience4j-circuitbreaker/src/main/java/io/github/resilience4j/circuitbreaker/CircuitBreakerConfig.java)), while the semaphore bulkhead defaults to 25 concurrent calls with zero wait ([BulkheadConfig.java](https://raw.githubusercontent.com/resilience4j/resilience4j/master/resilience4j-bulkhead/src/main/java/io/github/resilience4j/bulkhead/BulkheadConfig.java)). A circuit breaker is itself a State machine wrapped in a Decorator, so teaching sealed-type State first lets the resilience lesson double as a capstone that reuses everything earlier in the course.

## Retrieval and spacing should set the shape of every 35-minute session

The evidence is lopsided in a way that simplifies design. Dunlosky and colleagues' 2013 review rated only two of ten techniques high-utility — **practice testing and distributed practice** — and rated rereading, highlighting and summarization low ([APS](https://www.psychologicalscience.org/news/releases/which-study-strategies-make-the-grade.html)). Meta-analyses put testing over restudy at **g ≈ 0.50** across 159 effect sizes, rising to **0.73 with feedback** (0.39 without) and to 0.69 when the final test comes a day or more later ([Rowland 2014, via Frontiers](https://www.frontiersin.org/articles/10.3389/fpsyg.2018.02412/pdf)), and at **g = 0.61–0.70** across 272 effect sizes, with classroom results (0.67) matching lab results ([Adesope et al. 2017](https://journals.sagepub.com/doi/10.3102/0034654316689306)). Distributed practice beats massed practice by **d = 0.46** ([Donovan & Radosevich, via awesome-fsrs](https://raw.githubusercontent.com/wiki/open-spaced-repetition/awesome-fsrs/Spaced-Repetition-Algorithm:-A-Three%E2%80%90Day-Journey-from-Novice-to-Expert.md)). The best gap between study sessions shrinks as a share of how long the material must be remembered — about 20–40% for a test a week away, 5–10% for one a year away ([Cepeda et al. 2008](https://www.evullab.org/pdf/CepedaVulRohrerWixtedPashler-PS-2008.pdf)) — and "a too-short interval is much more detrimental to retention than … too long" ([York University](https://www.yorku.ca/yfile/?p=9454)). The trap is that learners misjudge what works: rereading beat testing at five minutes but lost at two days and a week ([Roediger & Karpicke 2006](https://psychology.ecu.edu/wp-content/pv-uploads/sites/216/2019/03/Roediger-Karpicke-2006.pdf)), and learners rated practising one topic at a time as better even when mixed practice taught them more ([Kornell & Bjork, via Memory & Cognition](https://www.springermedizin.de/article/10.3758/s13421-012-0272-7)). Effective techniques must therefore be the course's defaults, not options. One caveat on provenance: several of these figures were confirmed from abstracts and secondary summaries rather than full texts, so quote them as rounded values.

Other techniques help under conditions that this audience and subject happen to meet. Interleaving — mixing practice on related topics instead of doing one at a time — has a moderate benefit overall that is largest when the categories are **similar and easily confused**, while for word lists blocked practice actually won (g = −0.39) ([Brunmair & Richter 2019](https://www.psychologie.uni-wuerzburg.de/fileadmin/06020400/2019/Brunmair_Richter_in_press__2019_META-ANALYSIS_OF_INTERLEAVED_LEARNING.pdf)). This course is full of exactly such clusters: `synchronized`, `volatile`, atomics, `LongAdder` and locks; `flatMap`, `concatMap`, `flatMapSequential` and `switchMap`; `launch`, `async`, `coroutineScope` and `supervisorScope`; `out`, `in` and `*`; Decorator versus Proxy and Strategy versus State. Prompting learners to explain in their own words beats handing them an explanation across 64 studies ([Bisra et al. 2018, via BPS](https://bps.org.uk/research-digest/self-explanation-powerful-learning-technique-according-meta-analysis-64-studies)); answering questions before reading improves learning even for questions answered wrongly ([Richland, Kornell & Kao 2009](https://learninglab.uchicago.edu/Pre-Testing_files/RichlandKornellKao.pdf)); and producing an answer beats reading it by about 0.40 ([Bertsch et al. 2007](https://mcdaniel97.github.io/Publications/Bertsch%20et%20al.%202007.pdf)). For a senior engineer the critical condition is the **expertise reversal effect**: worked examples help novices but lose their advantage or backfire as knowledge grows ([Heriot-Watt research portal](https://researchportal.hw.ac.uk/en/publications/the-expertise-reversal-effect-and-worked-examples-in-tutored-prob/); [worked-example effect](https://en.wikipedia.org/wiki/Worked-example_effect)), while removing steps from examples gradually beats an abrupt switch to problems, and fading that adapts to the learner's performance beats a fixed schedule ([MIT Open Learning](https://openlearning.mit.edu/mit-faculty/research-based-learning-findings/worked-and-faded-examples); [Salden et al. 2010](https://link.springer.com/doi/10.1007/s11251-009-9107-8)). Full worked examples belong only on genuinely new mental models — happens-before, structured cancellation, variance positions — and should fade within a lesson or two; Java and Kotlin syntax should never be walked through step by step. Short labels naming the purpose of each code chunk (subgoal labels) reduce cognitive load in programming, though a study at full-course scale found only a small effect on exam scores ([Raspberry Pi Foundation](https://www.raspberrypi.org/app/uploads/2020/07/Using-subgoal-labels-to-reduce-cognitive-load-in-introductory-programming.pdf)).

No study has tested a 35-minute split for adult professionals, so the template below orders the supported effects in a defensible sequence; it is a synthesis, not a tested protocol.

| Minutes | Block | What happens | Evidence |
|---|---|---|---|
| 0–10 | Due reviews | Auto-graded spaced-repetition queue mixing older topics, immediate explanatory feedback, hard cap with overflow rolling to tomorrow | Testing and spacing (high utility); feedback strengthens testing |
| 10–12 | Prediction | One to three questions before any explanation — "What can this print?", "Does this compile?", "Will this deadlock?" — with no penalty for wrong answers | Pretesting; generation effect |
| 12–22 | One new concept | Worked example with subgoal labels, inline prompts such as "why does this line need `volatile`?", and a contrast with the easily confused neighbouring construct | Worked examples; self-explanation |
| 22–32 | Practice | Fill a missing line, then write from a blank editor against tests, then one or two "pick the right tool" problems mixing today's construct with earlier ones | Fading; generation; interleaving |
| 32–35 | Exit quiz | Three to five retrieval questions; misses re-asked once, then every item added to the queue for tomorrow | Testing; spacing |

The choice of scheduler matters less than two properties: intervals grow, and a failed item drops back to a short interval. FSRS (the Free Spaced Repetition Scheduler) is the most accurate open option. On roughly 10,000 Anki users and 727 million reviews, even FSRS-7 with **default parameters and no per-user training** predicted recall better than a baseline that always predicts the user's average (log loss 0.3620 vs 0.3945, lower being better), and the FSRS-4.5 formulas are short enough to implement in about sixty lines of client-side JavaScript ([SRS benchmark](https://raw.githubusercontent.com/open-spaced-repetition/srs-benchmark/main/README.md); [FSRS algorithm](https://raw.githubusercontent.com/wiki/open-spaced-repetition/awesome-fsrs/The-Algorithm.md)). Anki's documentation sets the default desired retention at 90%, warns that workload climbs steeply above that, estimates about ten reviews per new card per day once a deck reaches steady state, and flags a card as a "leech" after eight failures ([Anki deck options](https://github.com/ankitects/anki-manual/blob/main/src/deck-options.md); [Anki leeches](https://raw.githubusercontent.com/ankitects/anki-manual/main/src/leeches.md)). With a ten-minute review budget and 20–40 seconds per code-reading item, that arithmetic supports only **three to five new review items per day**. The course should therefore cap daily intake, pause new lessons when a review backlog builds, schedule each item's first review for the next day, and grade from behaviour rather than self-rating (failed or gave up counts as Again, passed with a hint as Hard, a clean pass as Good). A leech usually signals a badly written card or a missing prerequisite, so it should go to a rewrite list rather than repeat forever.

This subject suits retrieval practice unusually well, because the JVM ecosystem ships its own answer keys. kotlinc's diagnostics grade "does this compile?" items exactly; jcstress `@Outcome` annotations label each possible result ACCEPTABLE, ACCEPTABLE_INTERESTING or FORBIDDEN and so grade "which outputs are allowed?" items ([jcstress samples](https://github.com/openjdk/jcstress/tree/master/jcstress-samples)); `StepVerifier.withVirtualTime` and `runTest`'s `currentTime` grade predictions about timing and ordering; and JFR recordings and JSON thread dumps grade diagnosis exercises. That lets every item follow the minimum information principle — one fact or decision per card, with a blank on a single token or line — and stay executable, which is how Execute Program builds every prompt ([SuperMemo 20 rules](https://www.supermemo.com/en/archives1990-2015/articles/20rules); [Execute Program](https://www.executeprogram.com/spaced-repetition)). Multiple-choice items should draw their wrong options from the real misconceptions documented above, because plausible, competitive wrong options improve later recall even of related material that was never tested ([Little & Bjork 2014](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2017/01/LittleBjorkMC2014.pdf)), and should avoid trick wording, which undermines the benefit ([Butler 2018, via WashU](https://source.washu.edu/2018/09/for-better-multiple-choice-tests-avoid-tricky-questions-study-finds/)). Hands-on "muscle memory" comes from the generation side of the template: the blank-editor practice block, plus repeated use of the real diagnostic commands (`jcmd Thread.print`, `Thread.dump_to_file -format=json`, `jfr print --events jdk.VirtualThreadPinned`) until they are reflexes rather than lookups.

At the course level, the habit research argues for forgiveness over streak pressure. In Lally and colleagues' study, the median time for a daily behaviour to become automatic was **66 days** (range 18–254), and **missing a single day had little effect** ([BPS Research Digest](https://bps.org.uk/research-digest/how-form-habit)). Streaks should count review days, include automatic grace days and show weekly consistency, while XP, badges and leaderboards have no learning evidence in the sources found and should never reward speed over correct recall. A "short day" mode that runs only the due reviews protects the spacing schedule when a learner has ten minutes. Concept-sized lessons match Exercism's concept exercises, scoped to five to ten minutes for an experienced developer ([Exercism](https://exercism.org/docs/building/product/concept-exercises)), and unlocking a lesson only after its prerequisites have been reviewed successfully mirrors Execute Program. A topic order that runs from the memory model and `java.util.concurrent`, through executors, virtual threads and structured concurrency, then Kotlin generics (ahead of the reactive and coroutine signatures that depend on variance), then Reactor and coroutines, and finally design patterns as an integrating capstone, comes to roughly 60–75 lessons — about 13 to 15 weeks at five sessions a week, which lands neatly on the habit-formation window. That arc is a judgement, not a tested finding. The evidence base has real gaps: almost all of it comes from students tested over days or weeks, direct evidence on professionals retaining technical skills over months is thin, and nothing was found on the order of blocks within a session, on one 35-minute block versus two shorter ones, on Parsons problems, or on executable versus text flashcards.

## Conclusion

The research shifts the course's centre of gravity. The durable content is small and old — happens-before, the Reactive Streams demand protocol, coroutine parent-child rules, variance positions — while most of what makes 2023-era material wrong is operational: which JDK pins, which flag still exists, which API shape compiles. That argues for two kinds of cards with different lifecycles: permanent concept cards whose intervals the scheduler can stretch to months, and version-stamped fact cards that carry a "valid since" field and are re-checked at every March and September JDK release. Because JDK 28 freezes the JDK 27 structured-concurrency API, and kotlinx.coroutines 1.12, Reactor 3.9 and Resilience4j 3 are already in view, the next two release cycles will mostly retire today's caveats rather than add new ones — and the lab build should move first, from a blanket `--release 21` to per-track JDK targets that match the lessons.

The second implication links the two halves of the question. The misconceptions catalogued here are more than content to correct; they are the best raw material for the course's practice items, because wrong options drawn from real errors are what make multiple-choice recall effective, and because the misconceptions come in exactly the clusters of easily confused constructs where interleaving pays off most. A course for senior engineers should therefore spend little of its 35 minutes explaining and most of it having learners predict, run and explain, with jcstress, kotlinc, StepVerifier, `runTest` and JFR delivering the verdict — and should hand the same tools to the spaced-review queue, so the reflexes last long after the lessons end.
