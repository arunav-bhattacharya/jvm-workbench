# New Defaults Rewrite the Advanced JVM Syllabus

As of November 2026, the mechanisms a senior backend engineer needs beyond concurrency have not changed: object headers and collectors, tiered compilation, class loaders and proxies, epoll-driven event loops, archived class metadata, Kotlin's compile-time lowering and Java's records and patterns. What has changed between JDK 21 and JDK 27 is the defaults and tool surfaces around them, enough that material from 2023 now teaches wrong numbers and dead flags. The largest shift is that **JDK 27 (GA 15 September 2026) selects G1 in every environment and turns compact object headers on by default**, so a one-CPU pod that silently ran Serial GC on JDK 21–26 now runs G1 with 8-byte headers. Project Leyden's AOT cache shipped across JDKs 24–26 and is a single property in Quarkus 3.40, but **releases before 25.0.4 and 26.0.2 could run stale class bytes from an old cache**, and AOT-compiled code (JEP 544) exists only in the unreleased JDK 28. The ClassFile API became final in JDK 24 and now generates the JDK's own proxies and lambdas. Netty 4.2 and Vert.x 5 changed their core APIs. Kotlin 2.4 made context parameters stable while contracts stay experimental. Java still has no withers and no final primitive patterns, and value objects exist only in the JDK 28 preview. The measurement toolbox barely moved: tiered-compilation thresholds are the same as in JDK 21, JMH 1.37 (August 2023) and JOL 0.17 (February 2023) are still the latest releases, and only JFR gained real features (CPU-time sampling, method timing, secret redaction). The misconceptions worth course time fall into a few families: treating the heap as the process, trusting wall-clock microbenchmarks, assuming a subclass proxy intercepts self-calls, equating non-blocking with faster or virtual threads with the end of event loops, equating Leyden with native image, and believing Kotlin's inline and value classes are free or Java's records deeply immutable. The exercises that teach these best grade what the JVM reports exactly — allocated bytes, field offsets, instance and class counts, parsed JFR events, call counters and compiler diagnostics — and never nanoseconds.

What did not change matters as much as the table. The C1 and C2 thresholds, the collector families, the JLS class-initialization rules, the `java.lang.ref` contracts and the JMH and JOL releases are all as they were in 2023, so a lesson written against JDK 21 keeps its conceptual core and loses only its numbers and flags. That argues for two habits. Every quantitative fact carries a version range ("tier-4 threshold 5,000, JDK 21–27"). And learners are trained to ask the running JVM rather than remember: `java -XX:+PrintFlagsFinal -version`, `-XshowSettings:system`, `-Xlog:aot`, `jcmd VM.native_memory` and `javap -v` answer most "what is the default?" questions on the learner's own machine. One limit applies to everything below. openjdk.org JEP pages could not be reached, so behaviour was checked against OpenJDK source at GA tags, project repositories and local runs (mostly on JDK 21). JEP benchmark figures come from search summaries, and several JDK 26 and 27 behaviours were read from source rather than run.

## The heap is the smallest surprise in JVM memory

On a default 64-bit HotSpot through JDK 26, every object starts with a 12-byte header. That is an 8-byte mark word, holding hash, GC age and lock bits, plus a 4-byte compressed class pointer. Every object is padded to 8 bytes, and references stay 4 bytes as long as the maximum heap fits the roughly 32 GB that compressed oops can address ([markWord.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/oops/markWord.hpp); [java.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/man/java.md)). JOL 0.17 makes the arithmetic concrete. An `Integer` takes 16 bytes, a `Long` 24, a three-character `String` 48 including its `byte[]`, and an `ArrayList<Integer>` of 1,000 values 20,976 bytes against 4,016 for an `int[1000]` ([jol-core 0.17](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jol/jol-core/0.17/jol-core-0.17.jar)). The 32 GB cliff is real: `-Xmx40g` switches compressed oops off and the same list grows to 25,920 bytes, so **a 40 GB heap can hold less data than a 31 GB one**. JOL is also a maintenance risk for course builders. Version 0.17, from February 2023, is still the latest release ([jol-cli metadata](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jol/jol-cli/maven-metadata.xml)). It needs `-Djol.magicFieldOffset=true` to lay out records on JDK 21, and it predates compact headers, which it can only simulate.

Compact headers fold a 22-bit class pointer into the mark word, shrinking the header to 8 bytes ([compressedKlass.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/oops/compressedKlass.hpp)). The JDK 25 man page promises a saving of "4 bytes per object (on average)", and alignment explains the averaging. In JOL's model a 40-byte payment DTO and a 32-byte `HashMap$Node` each lose 8 bytes while `Integer` and `String` lose nothing, and a heap dump dominated by large `byte[]` buffers shrank only 1.3%. The JEP 519 page reports 22% less heap and 8% less CPU on one SPECjbb2015 configuration, figures this research saw only in a search summary ([JEP 519](https://openjdk.org/jeps/519)). Because JDK 27 flips the default ([java.md @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/java.base/share/man/java.md)), anything that hard-codes 12-byte headers breaks on upgrade. That includes `Unsafe` offset arithmetic, old agents, and lab tests asserting absolute JOL offsets. The escape hatch is `-XX:-UseCompactObjectHeaders`, for which JDK 27 ships alternate CDS archives ([JDK 27 release notes](https://www.oracle.com/java/technologies/javase/27-relnote-issues.html)).

Allocation itself is a pointer bump inside a thread-local allocation buffer — `if (pointer_delta(end(), obj) >= size) { set_top(obj + size); return obj; }` in HotSpot's own code ([threadLocalAllocBuffer.inline.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/gc/shared/threadLocalAllocBuffer.inline.hpp)) — and G1 sends anything larger than half a region straight to humongous regions ([g1CollectedHeap.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/gc/g1/g1CollectedHeap.hpp)). C2's escape analysis then removes allocations that never leave a compiled method. In a local JDK 21 run, a loop creating a million two-`long` records allocated 8 MB in its first round and **zero bytes from the fifth round on**. With `-XX:-DoEscapeAnalysis` it allocated a steady 32 MB per round ([c2_globals.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/opto/c2_globals.hpp)). That timing dependence shapes grading. `com.sun.management.ThreadMXBean.getCurrentThreadAllocatedBytes()` is exact enough for assertions — `new byte[1 << 20]` measured 1,048,592 bytes, payload plus a 16-byte header, in 20 of 20 repetitions. But it returns −1 on a virtual thread ([ThreadMXBean.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/jdk.management/share/classes/com/sun/management/ThreadMXBean.java)), which matters for Quarkus `@RunOnVirtualThread` code.

**G1 sizing.** G1 sizes regions at max heap ÷ 2,048, clamped to 1–32 MB ([g1HeapRegionBounds.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/gc/g1/g1HeapRegionBounds.hpp)). It starts concurrent marking when old-generation occupancy crosses an adaptive threshold that begins at 45%. Its 200 ms pause goal is a target, not a bound ([g1_globals.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/gc/g1/g1_globals.hpp)).

**Reading GC logs.** This is the teachable skill. In `GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->1M(256M) 12.723ms` the duration is a stop-the-world pause. In a ZGC line such as `Minor Collection (Allocation Rate) 582M(57%)->226M(22%) 0.052s` the duration is the **concurrent cycle**. The real ZGC pauses are the `Pause Mark Start`, `Pause Mark End` and `Pause Relocate Start` phases, which measured about 0.02 ms each locally. HotSpot's cause strings, such as `G1 Humongous Allocation`, `Allocation Stall` and `Metadata GC Threshold`, live in one source file ([gcCause.cpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/gc/shared/gcCause.cpp)). Three signals are worth grepping for first: `Pause Full`; G1's `(Evacuation Failure)` or ZGC's `Allocation Stall`; and a rising floor under the "after" values of young pauses.

**Choosing a collector.** ZGC's man-page entry concedes the trade-off: "max pause times of a few milliseconds, at some throughput cost" for heaps from 8 MB to 16 TB ([java.md @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/java.base/share/man/java.md)). The defensible guidance follows from that: G1 for most services; ZGC when p99 latency matters and spare cores exist; Parallel for batch work; Serial for tiny single-CPU containers; and Epsilon, still experimental in 27, for allocation-budget tests ([gc_globals.hpp @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/hotspot/share/gc/shared/gc_globals.hpp)).

The heap is only part of the process. Container detection is on by default and caps the maximum heap at 25% of the container limit ([java.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/man/java.md)). Thread stacks, metaspace (unbounded by default), the code cache, GC structures, CDS mappings, direct buffers and FFM segments all sit on top ([globals.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/runtime/globals.hpp)). Two source facts surprise even experienced engineers. When `-XX:MaxDirectMemorySize` is unset, the direct-buffer limit equals `Runtime.maxMemory()`, so off-heap NIO buffers can grow to a second full heap ([VM.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/jdk/internal/misc/VM.java)). And FFM native segments reserve against that same limit ([SegmentFactories.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/jdk/internal/foreign/SegmentFactories.java)). A local `-Xmx256m` process with a 64 MB direct buffer, a 32 MB FFM segment and 50 parked threads committed 390 MB according to Native Memory Tracking ([jcmd.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/jdk.jcmd/share/man/jcmd.md)). The kernel, not the JVM, enforces the cgroup limit, so a process that exceeds it is killed with no `OutOfMemoryError` and no heap dump. The rule for a Quarkus pod running on Netty or Vert.x is therefore to set the heap with `-XX:MaxRAMPercentage` well below 100, cap direct memory explicitly, and verify with `jcmd <pid> VM.native_memory summary`. Older labs simulate a container with `-XX:MaxRAM`, which is deprecated in 26 and obsolete in 27, so JDK 27 labs need real `docker run --memory` limits.

The `java.lang.ref` ladder needs precise teaching because the common advice about it is wrong. Soft references are guaranteed to be cleared only before an `OutOfMemoryError`; otherwise their clearing schedule is unspecified ([SoftReference.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/ref/SoftReference.java)). A weakly reachable value vanishes at the next GC that processes references, which makes **weak references a poor cache**. `WeakHashMap` is weak on its keys, and it warns that values must not reference those keys ([WeakHashMap.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/util/WeakHashMap.java)).

`Cleaner` is the supported replacement for `finalize()` ([Cleaner.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/ref/Cleaner.java)). `finalize()` is deprecated for removal, and `--finalization=disabled` switches finalization off wholesale, which makes a cheap test for dependencies that still rely on it ([Object.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/Object.java)).

Leak hunting has two steps. `jcmd GC.class_histogram` shows *what* accumulates. A heap dump in Eclipse MAT then shows *who holds it*, through a dominator tree whose retained set is the "memory kept alive by X" ([MAT: shallow vs retained heap](https://raw.githubusercontent.com/eclipse-mat/mat/master/plugins/org.eclipse.mat.ui.help/concepts/shallowretainedheap.html)). Four service leaks are worth labs: unbounded idempotency caches; `ThreadLocal` values on pooled threads (a 1 MiB value stayed reachable after its task finished, until the same pooled thread called `remove()`); listeners that are never unregistered; and class-loader leaks in Quarkus dev mode.

The misconceptions in this track treat the heap as the process or the GC as a promise. "`System.gc()` frees memory now" is false: the Javadoc promises nothing ([Runtime.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/Runtime.java)), and `-XX:+DisableExplicitGC` silently turns the call into a no-op. Under that flag, 25 of 63 lab test executions that waited on a GC failed. The others to correct are: "a bigger heap is better"; "ZGC is always best"; "`-Xmx` caps the process"; "an `Integer` costs 4 bytes"; "every `new` hits the heap"; "compact headers save exactly 4 bytes"; "the JVM always picks G1" (true only from JDK 27); and "a heap dump explains an OOM-kill".

## Allocated bytes, not nanoseconds, are the trustworthy performance signal

HotSpot interprets first, compiles warm methods with C1 at tier 3 with full profiling, and recompiles hot ones with C2 at tier 4. The triggers are 200 invocations for tier 3 and 5,000 for tier 4, plus back-edge thresholds of 60,000 and 40,000 for on-stack replacement. They scale up automatically when compile queues are long, and **they have not changed between JDK 21 and JDK 27** ([compiler_globals.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/compiler/compiler_globals.hpp); [compilationPolicy.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/compiler/compilationPolicy.hpp)). The often-quoted 10,000-invocation `CompileThreshold` applies only with tiered compilation switched off. C2's inlining budget is measured in bytecode bytes, not source lines ([bytecodeInfo.cpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/opto/bytecodeInfo.cpp); [c2_globals_x86.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/cpu/x86/c2_globals_x86.hpp)): 35 bytes at a cold call site; 325 bytes at a hot one on x86; a 2,500-byte cap on callees that are already compiled; and a depth limit of 15.

Speculation is the core idea. With one receiver type in the profile, C2 inlines behind a class check. A third type makes the site megamorphic and turns it into a virtual call. A failed guard deoptimizes the method, which JDK 25 logs as `made not entrant: <reason>` where JDK 21 printed a bare `made not entrant` ([nmethod.cpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/code/nmethod.cpp)). Two beliefs fall to this evidence. `final` does not make methods faster, because devirtualization follows the receiver profile. And JIT output is not reproducible: three identical local runs first compiled the same loop at 40, 47 and 60 ms. Tutorials that show `made zombie` predate the current nmethod states, and JDK 27 adds only an experimental `HotCodeHeap` for hot C2 code ([c2_globals.hpp @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/hotspot/share/opto/c2_globals.hpp)).

JMH 1.37 from August 2023 is still the latest release ([jmh-core metadata](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jmh/jmh-core/maven-metadata.xml)), and its samples remain the curriculum. Sample 08 covers dead-code elimination, because "compilers are smart enough to deduce some computations are redundant and eliminate them completely" ([JMHSample_08](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_08_DeadCode.java)). Sample 10 covers constant folding through `final` fields: "IDEs will say 'Look, this field could be final'. Don't. Trust. Them." ([JMHSample_10](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_10_ConstantFold.java)). Sample 11 shows loops that make each addition appear to cost "1/20 ns" ([JMHSample_11](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_11_Loops.java)). The local reproduction added a twist worth teaching. On JDK 21 x86-64, a discarded `Math.sqrt` was eliminated like dead code, but a discarded `Math.log` was not: 10.1 ns against a 0.37 ns baseline ([jmh-core 1.37](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jmh/jmh-core/1.37/jmh-core-1.37.jar)). A wrong benchmark can therefore still print a plausible number, and dead-code demos should use pure arithmetic. The more important finding concerns noise. On a shared 4-vCPU VM, `-prof gc`'s normalized allocation rate held steady to ±0.002 B/op, while time scores carried ±100–250% error bars. Summing 100 card fees allocated 15,200 B/op with `BigDecimal` and effectively nothing with `long` cents. That makes **B/op the metric to gate in CI**, with time measured only on dedicated hardware with many forks. JMH 1.37 also triggers JDK 25's `sun.misc.Unsafe` warning, a harmless artifact that confuses learners.

The JDK's own answer to false sharing is `@jdk.internal.vm.annotation.Contended`, which pads by 128 bytes. It sits on `Striped64.Cell`, the cell behind `LongAdder`, whose source explains that without it, atomics in arrays "will most often share cache lines (with a huge negative performance impact)" ([Striped64.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/util/concurrent/atomic/Striped64.java)). User classes get the padding only with `-XX:-RestrictContended` and an export of the internal package ([globals.hpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/runtime/globals.hpp)). JOL shows the cost of each layout: unpadded, two `volatile long` fields sit 8 bytes apart in a 32-byte object; with manual padding, they sit 136 bytes apart in a 160-byte object; and with `@Contended`, they sit 136 bytes apart in a 288-byte object.

To be honest about the evidence: a local false-sharing benchmark showed no reliable speed-up on a shared VM, because two runs disagreed. JMH's sample 22 warns that manual padding is fragile anyway, since "JVMs can freely rearrange the field order" ([JMHSample_22](https://raw.githubusercontent.com/openjdk/jmh/master/jmh-samples/src/main/java/org/openjdk/jmh/samples/JMHSample_22_FalseSharing.java)). Teach the mechanism with layout evidence, recommend `LongAdder` for application counters, and keep timing demos for bare-metal multicore machines.

JFR changed more than any other tool in this track. `jfr view` and its built-in query views arrived in JDK 21 with 74 views, which grew to 84 by JDK 27 ([view.ini @ jdk-21-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-21-ga/src/jdk.jfr/share/classes/jdk/jfr/internal/query/view.ini); [view.ini @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/jdk.jfr/share/classes/jdk/jfr/internal/query/view.ini)). Commands such as `jfr view allocation-by-site rec.jfr` and `jfr view gc-pauses rec.jfr` now replace most JMC clicking for a first diagnosis. JDK 25 added three profiling JEPs: **CPU-time sampling on Linux (JEP 509)** uses per-thread POSIX CPU timers. Its `jdk.CPUTimeSample` event is marked experimental and disabled in both shipped settings files ([metadata.xml @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/jfr/metadata/metadata.xml)). **Cooperative sampling (JEP 518)** has the target thread finish its own stack walk at its next safepoint poll ([jfrSampleRequest.cpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/jfr/periodic/sampling/jfrSampleRequest.cpp)). **Method timing and tracing (JEP 520)** accepts filters naming a class, a method reference, a class initializer or an annotation such as `@jakarta.ws.rs.GET`, which suits Quarkus endpoints ([default.jfc @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/jdk.jfr/share/conf/jfr/default.jfc)).

JEP 518 changes one teaching point. JFR now uses safepoints by design, yet it records the PC captured at the sampling instant and flags the samples that really are biased, so "uses safepoints" no longer means "safepoint-biased". JDK 27's JEP 536 adds in-process redaction of command-line arguments, system properties and environment variables that match patterns such as `*secret*`. Child-process events are excepted ([java.md @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/java.base/share/man/java.md)). Redaction matters for PCI-scoped payment services that ship recordings to vendors.

async-profiler 4.6 samples asynchronously through perf_events or through timers and signals. It sees native, kernel, GC and JIT frames. Since 4.2 it has walked Java stacks with its own HotSpot VM-structs walker by default, because `AsyncGetCallTrace` "was broken several times even in minor JDK updates" ([StackWalkingModes.md](https://raw.githubusercontent.com/async-profiler/async-profiler/master/docs/StackWalkingModes.md)). Its allocation mode samples TLAB refills without disturbing escape analysis, so scalar-replaced objects never appear ([ProfilingModes.md](https://raw.githubusercontent.com/async-profiler/async-profiler/master/docs/ProfilingModes.md)). The misconception to kill is that a flame graph's x-axis is time. Frames are sorted alphabetically and merged, so the graph shows "how often", never "when", and wide tops mark self time ([FlamegraphInterpretation.md](https://raw.githubusercontent.com/async-profiler/async-profiler/master/docs/FlamegraphInterpretation.md); [flamegraph.pl](https://raw.githubusercontent.com/brendangregg/FlameGraph/master/flamegraph.pl)).

The capstone that ties the track together is a reproducible fee-calculator investigation. The method under test had three costs: it compiled a regex on every request; it formatted a DEBUG line with `String.format` and then discarded it; and it rebuilt constant `BigDecimal`s on every call.

Its p99.99 latency was 13.6 ms, with 129 GC pauses in 15 seconds. `jfr view allocation-by-site` and a `RecordingFile` parser pointed at the exact source lines, and async-profiler showed who called them ([RecordingFile.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/jdk.jfr/share/classes/jdk/jfr/consumer/RecordingFile.java); [async-profiler 4.6](https://github.com/async-profiler/async-profiler/releases/download/v4.6/async-profiler-4.6-linux-x64.tar.gz)). Precompiling the pattern, guarding the log call and hoisting the constants cut JMH allocation from 2,032 to 200 B/op. Re-profiling then exposed a `Matcher` allocation that had been invisible before. Replacing the regex brought allocation to 72 B/op, p99.99 to 28.4 µs and GC pauses to 36 ([jmh-core 1.37](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jmh/jmh-core/1.37/jmh-core-1.37.jar)). The lessons are "fix one thing, then re-profile", "symptoms live in the tail, not the mean", and "the JMH B/op number is the regression test". Maximum latency stayed at 0.4–0.5 s throughout. That was an artifact of the shared machine and must not be credited to the fix.

## Self-invocation depends on where the proxy keeps the target

A class's identity is the pair of its binary name and its defining loader. The bootstrap loader appears as `null`, and the app loader delegates parent-first to the platform loader ([ClassLoader.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/ClassLoader.java)). Two child-first loaders that define `demo.plugin.Counter` from identical bytes produce two classes with separate statics. Casting between them throws a `ClassCastException` that names the same class twice with different loaders. That message is the signature of isolation bugs in Quarkus dev and test mode, whose runtime class loader "is always isolated" and is recreated on every restart ([Quarkus class-loading reference](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/class-loading-reference.adoc)). Initialization is lazy and narrower than learners expect ([instanceKlass.cpp @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/oops/instanceKlass.cpp)). Reading a `static final int` constant initializes nothing, and neither do `X.class`, array creation or `Class.forName(name, false, loader)`. A static field read through a subclass initializes only the declaring class. Implementing an interface initializes that interface only if it declares a default method.

Two diagnostics deserve slides. **`NoClassDefFoundError` usually does not mean a missing jar.** After a static initializer throws, every later use fails with `Could not initialize class …`, and on JDK 21+ its cause carries the original exception. And a class-initialization deadlock shows both threads as RUNNABLE and "waiting on the Class initialization monitor"; `jstack`'s deadlock detector flagged it on neither JDK 21 nor JDK 25. Class-loader leaks follow one pattern: a long-lived loader's static registry references an object from a short-lived loader. A `URLClassLoader` whose plugin had been registered in a parent-loaded list stayed reachable after `close()` and ten GCs.

`javap -c -p` shows the JVM's shape of a class, not Kotlin's source structure ([kotlinc 2.4.21 run](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-compiler/2.4.21/)): a data class becomes getters, `componentN()`, `copy`, and a static `copy$default` driven by a bitmask; a companion becomes a nested `$Companion` class plus a static field; `lateinit` becomes a public field; and every public non-null parameter gets an `Intrinsics.checkNotNullParameter` call.

Kotlin's own view survives only in the protobuf-encoded `@kotlin.Metadata` annotation. The 2.4.21 `kotlinc` command line still defaults to class-file version 52 (Java 8), where string templates fall back to `StringBuilder`. With `-jvm-target 21` they compile to `invokedynamic makeConcatWithConstants` ([What's new in Kotlin 1.5.20](https://kotlinlang.org/docs/whatsnew1520.html)), so demos must pass the target explicitly. One javac 21 source file is enough to show every bootstrap the compiler uses ([InnerClassLambdaMetafactory.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/invoke/InnerClassLambdaMetafactory.java); [ObjectMethods.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/runtime/ObjectMethods.java)): `LambdaMetafactory` for lambdas, whose classes are hidden nestmates that `Class.forName` cannot find; `StringConcatFactory` for string concatenation; `ObjectMethods` for a record's `equals`, `hashCode` and `toString`, built over direct field getters; `SwitchBootstraps.typeSwitch` for pattern switches; and **condy** (`ConstantBootstraps.invoke`) for enum-constant labels inside a pattern switch.

`Proxy.newProxyInstance` generates a `public final` class named like `jdk.proxy1.$Proxy0`, or reuses one from a per-loader cache keyed by the *ordered* interface list. The class extends `java.lang.reflect.Proxy`, lives in one dynamic module per class loader, and holds each `Method` in a static field ([Proxy.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/reflect/Proxy.java); [ProxyGenerator.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/reflect/ProxyGenerator.java)). The Javadoc fixes the edge cases that labs should test: `hashCode`, `equals` and `toString` go to the handler, but `getClass` does not; a checked exception that the interface method does not declare surfaces as `UndeclaredThrowableException`; and only non-hidden, non-sealed interfaces qualify.

Almost every first handler forwards with `m.invoke(target, args)` and never unwraps `InvocationTargetException`. A target's `IOException` then arrives as `UndeclaredThrowableException → InvocationTargetException → IOException`. `InvocationHandler.invokeDefault` (JDK 16) runs a default method whose `this` *is* the proxy, so its inner calls re-enter the handler; a handler wrapping a default `greetTwice` ran three times. A target's own `this.greet()` calls, by contrast, bypass the proxy entirely ([InvocationHandler.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/reflect/InvocationHandler.java)). Per-call cost is small. In a local JMH 1.37 run on JDK 25 ([jmh-core 1.37](https://maven-central.storage-download.googleapis.com/maven2/org/openjdk/jmh/jmh-core/1.37/jmh-core-1.37.jar)): a direct call took 0.8 ns; a Byte Buddy `@SuperCall` subclass took 0.9 ns; a JDK proxy took 4.3 ns; and `Method.invoke` with boxing took 11.8 ns.

That cost is irrelevant beside a database call but relevant in a tight loop.

Whether a self-call is intercepted depends on where the intercepted state lives, not on whether the proxy is a subclass. **Spring AOP.** The CGLIB proxy is a runtime subclass, but it forwards to a separate target bean, so "self invocation via an explicit or implicit this reference will bypass the advice" ([Spring proxying.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/core/aop/proxying.adoc)). A self-invoked `@Transactional` method "does not lead to an actual transaction" in the default proxy mode ([Spring transaction annotations.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/data-access/transaction/declarative/annotations.adoc)). Spring Boot defaults to class-based proxies, with `spring.aop.proxy-target-class` true unless set ([AopAutoConfiguration](https://raw.githubusercontent.com/spring-projects/spring-boot/main/core/spring-boot-autoconfigure/src/main/java/org/springframework/boot/autoconfigure/aop/AopAutoConfiguration.java)). Spring 7 adds `@Proxyable` to force a proxy type per bean ([Proxyable.java](https://raw.githubusercontent.com/spring-projects/spring-framework/main/spring-context/src/main/java/org/springframework/context/annotation/Proxyable.java)). "The constructor is called twice" is a Spring 3.2-era fact that Objenesis retired. **Quarkus ArC.** ArC generates `Foo_Subclass extends Foo` at build time and documents self-interception as a supported non-standard feature. With `quarkus.arc.transform-unproxyable-classes` true by default, it can even proxy final Kotlin classes ([Quarkus cdi-reference.adoc](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/cdi-reference.adoc); [SubclassGenerator.java](https://raw.githubusercontent.com/quarkusio/quarkus/main/independent-projects/arc/processor/src/main/java/io/quarkus/arc/processor/SubclassGenerator.java)). A Spring-to-Quarkus migrant can therefore be surprised in either direction. **Hibernate.** Hibernate builds lazy proxies with Byte Buddy. That is why entities must be non-final with a non-private no-arg constructor, and why `equals` must tolerate a proxy argument ([Hibernate Entities.adoc](https://raw.githubusercontent.com/hibernate/hibernate-orm/main/documentation/src/main/asciidoc/introduction/Entities.adoc)). **cglib.** Its own README calls it unmaintained and unreliable "particularly JDK17+", and Spring ships a patched internal copy ([cglib README](https://raw.githubusercontent.com/cglib/cglib/master/README.md)). **Byte Buddy.** Version 1.18.17 (1 November 2026) supports new Java versions through its ClassFile API bridge, and it stopped using `Unsafe` by default from Java 26 ([Byte Buddy release notes](https://raw.githubusercontent.com/raphw/byte-buddy/master/release-notes.md)).

A side-by-side Byte Buddy pair explains Spring, ArC and the "it's a subclass" fallacy in one demo. In one, the proxy instance is the subclass, and its self-call is intercepted. In the other, the proxy forwards to a separate target, and its self-call is not.

The `java.lang.classfile` API was a preview in JDKs 22 and 23 and became final in JDK 24. `ClassFile.of()` offers four operations ([ClassFile.java @ jdk-24-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-24-ga/src/java.base/share/classes/java/lang/classfile/ClassFile.java); [classfile package-info](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/classfile/package-info.java)): `parse` into a lazily inflated, immutable model; `build` through builder lambdas; `transformClass` as a "flatMap" over elements; and `verify`.

The JDK now uses the API itself. `ProxyGenerator` dropped the internal ASM copy in JDK 23 and the lambda spinner followed in JDK 24, and the ASM copy is gone from the JDK 25 tree ([ProxyGenerator.java @ jdk-23-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-23-ga/src/java.base/share/classes/java/lang/reflect/ProxyGenerator.java); [Opcodes.java @ jdk-24-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-24-ga/src/java.base/share/classes/jdk/internal/org/objectweb/asm/Opcodes.java)). Because the API exists only on JDK 24+, a ClassFile lab cannot compile in a `--release 21` build.

"Agents need a restart" is false. `retransformClasses` swapped a method body on an already-instantiated object in a live JVM. It cannot add or remove members or change signatures, and frames that are already running keep the old code ([Instrumentation.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.instrument/share/classes/java/lang/instrument/Instrumentation.java); [jvmti.xml @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/hotspot/share/prims/jvmti.xml)). Since JEP 451 in JDK 21, a dynamically loaded agent still works but prints a four-line warning ending "Dynamic loading of agents will be disallowed by default in a future release", unless `-XX:+EnableDynamicAgentLoading` is set. JDK 27.0.1 still allows it ([instrument package-info @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.instrument/share/classes/java/lang/instrument/package-info.java)). That warning belongs to a family ([java.md @ jdk-24-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-24-ga/src/java.base/share/man/java.md); [java.md @ jdk-26-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-26-ga/src/java.base/share/man/java.md); [Unsafe.java @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/jdk.unsupported/share/classes/sun/misc/Unsafe.java)): `sun.misc.Unsafe` memory-access methods have warned by default since JDK 24 (JEP 498), and throw `UnsupportedOperationException` under `--sun-misc-unsafe-memory-access=deny`. Reflective mutation of a `final` field has warned since JDK 26 (JEP 500), and throws `IllegalAccessException` under `--illegal-final-field-mutation=deny`.

**None of these defaults had become a hard failure by JDK 27.** A cheap future-proofing CI job runs the test suite with both deny flags and without `EnableDynamicAgentLoading`. It surfaces the mocking, serialization and DI libraries that will break when the defaults change.

## Every JVM server is an event loop; the difference is who runs blocking code

Non-blocking I/O exists because a blocked thread "can't do anything else", and Vert.x's own docs frame the problem as scalability: "a blocking approach just doesn't scale" ([Vert.x 5.2.3 core docs](https://raw.githubusercontent.com/eclipse-vertx/vert.x/5.2.3/vertx-core/src/main/asciidoc/index.adoc)). The java.nio fundamentals reduce to a short list of traps: **Partial reads and writes are normal.** A non-blocking `read` or `write` moves only what the kernel buffer allows ([WritableByteChannel.java](https://raw.githubusercontent.com/openjdk/jdk25u/master/src/java.base/share/classes/java/nio/channels/WritableByteChannel.java)). **Handled keys must be removed from `selectedKeys()` by hand**, and that set is not thread-safe ([Selector.java](https://raw.githubusercontent.com/openjdk/jdk25u/master/src/java.base/share/classes/java/nio/channels/Selector.java)). **Leaving `OP_WRITE` armed makes the loop spin.** Linux's `EPollSelectorImpl` registers file descriptors level-triggered (there is no `EPOLLET` in the source), so `OP_WRITE` on a writable socket makes `select()` return continuously ([EPollSelectorImpl.java @ jdk25u](https://raw.githubusercontent.com/openjdk/jdk25u/master/src/java.base/linux/classes/sun/nio/ch/EPollSelectorImpl.java)). A local echo server took tens of thousands of wakeups in 300 idle milliseconds, against none when `OP_WRITE` was armed only while bytes were pending.

Heap buffers passed to channels are copied through a temporary direct buffer, which is why direct buffers help native I/O. But the Javadoc warns they cost more to allocate and recommends them "primarily for large, long-lived buffers", so the real answer is pooling ([X-Buffer.java.template](https://raw.githubusercontent.com/openjdk/jdk25u/master/src/java.base/share/classes/java/nio/X-Buffer.java.template); [IOUtil.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/sun/nio/ch/IOUtil.java)).

Virtual threads did not abolish the event loop; they hid it. A virtual thread that blocks in `Socket.read()` has put the file descriptor in non-blocking mode, registered it one-shot with the JDK's internal `sun.nio.ch.Poller`, and parked. The poller, itself sitting in `EPoll.wait`, unparks the thread when the descriptor is ready ([Poller.java @ jdk21u](https://raw.githubusercontent.com/openjdk/jdk21u/master/src/java.base/share/classes/sun/nio/ch/Poller.java)). In a local JDK 21 run, 2,000 virtual threads blocked on sockets used 15 platform threads in total. The machinery changed during the LTS line. On JDK 21 the pollers are dedicated platform threads (`Read-Poller`, `Write-Poller`). From JDK 22, Linux defaults to `VTHREAD_POLLERS`: one platform master poller plus virtual sub-pollers scheduled like any other virtual thread ([Poller.java @ jdk25u](https://raw.githubusercontent.com/openjdk/jdk25u/master/src/java.base/share/classes/sun/nio/ch/Poller.java); [commit c099cf53](https://github.com/openjdk/jdk/commit/c099cf53)). JDK 24 added `jcmd Thread.vthread_pollers` to inspect them ([commit 5c8cb2ed](https://github.com/openjdk/jdk/commit/5c8cb2ed)). JDK 27 adds an optional per-carrier mode without changing the default ([Poller.java @ jdk27u](https://raw.githubusercontent.com/openjdk/jdk27u/master/src/java.base/share/classes/sun/nio/ch/Poller.java)).

The JDK 25 thread names come from source, not a run.

Netty 4.2, whose 4.2.0.Final release came in April 2025, changed four defaults and APIs ([Netty 4.2 migration guide](https://raw.githubusercontent.com/wiki/netty/netty/Netty-4.2-Migration-Guide.md)): every transport-specific event-loop group is deprecated in favour of `new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory())` and its epoll, kqueue, io_uring and local siblings; the adaptive allocator is the default, "designed from the start to work well with virtual threads"; TLS clients verify hostnames by default; and io_uring has graduated from the incubator to a first-class transport.

It also deprecated the per-handler `ChannelPipeline.addLast(EventExecutorGroup, …)` overloads that 4.1-era material recommended for slow handlers, because "it became clear that this introduce more problems then it solves" ([commit d64340b](https://github.com/netty/netty/commit/d64340b)). The pattern now is to hand blocking work to an application executor and call `ctx.writeAndFlush` from there. The core rules are unchanged ([ResourceLeakDetector.java @ 4.2](https://raw.githubusercontent.com/netty/netty/4.2/common/src/main/java/io/netty/util/ResourceLeakDetector.java); [Reference counted objects](https://raw.githubusercontent.com/wiki/netty/netty/Reference-counted-objects.md)): an `EventLoop` is one thread, and there are `2 × CPUs` loops by default; a channel stays on one loop for life; the last party to touch a reference-counted `ByteBuf` releases it; and leak detection samples about 1 in 128 buffers at `SIMPLE`, while `PARANOID` tracks every buffer for tests.

Local runs against 4.2.20 made three traps concrete ([netty-transport 4.2.20](https://repo.maven.apache.org/maven2/io/netty/netty-transport/4.2.20.Final/)): a handler sleeping one second on a shared loop delayed an unrelated client's reply by 1,060 ms. Dispatched off the loop, the same reply took 4 ms. Calling `close()` right after the last `flush()` dropped about 57 KB still in the outbound buffer. Closing from the last write's future fixes it. Ignoring writability let up to 16 MB pile up in the outbound buffer. Toggling `autoRead` on the 32 KiB and 64 KiB water marks capped it near 129 KB.

io_uring was slower than epoll in a single bulk FileRegion send, and the 4.2 line was still landing io_uring fixes in October and November 2026, so "io_uring is faster" is not a claim to teach.

Vert.x 5.2.3 runs on Netty 4.2.20 and keeps its golden rule. A handler "will never be executed concurrently" and runs on "the exact same event loop", so blocking one loop stalls everything pinned to it ([Vert.x 5.2.3 core docs](https://raw.githubusercontent.com/eclipse-vertx/vert.x/5.2.3/vertx-core/src/main/asciidoc/index.adoc)). The blocked-thread checker runs every second and warns `Thread vert.x-eventloop-thread-0 has been blocked for 2703 ms, time limit is 2000 ms`, adding a stack trace after 5 s. Its JUL category is still `io.vertx.core.impl.BlockedThreadChecker`, even though the class moved ([vertx-core 5.2.3](https://repo.maven.apache.org/maven2/io/vertx/vertx-core/5.2.3/)). Vert.x 5 kept only the future model, so `server.listen(8080, ar -> …)` no longer compiles. It also removed `setWorker` in favour of `ThreadingModel.WORKER` or `VIRTUAL_THREAD` ([Vert.x 5 migration guide](https://github.com/vert-x3/vertx-5-migration-guide/blob/main/asciidoc/modules/vertx_core.adoc)). The non-obvious trap for experienced engineers is that **`executeBlocking` is ordered per context by default** ([Vert.x 5.2.3 core docs](https://raw.githubusercontent.com/eclipse-vertx/vert.x/5.2.3/vertx-core/src/main/asciidoc/index.adoc)). Four 500 ms stand-in JDBC calls took: 2.8 s on the event loop; still 2.0 s through the default `executeBlocking`; and 0.58 s only with `executeBlocking(callable, false)`.

The event bus is in-memory and best-effort, with a 30-second reply timeout; it is not a broker. And a vertx-junit5 assertion outside `verify(...)` surfaces as a timeout rather than a failure.

Quarkus REST picks the thread from the method signature. Endpoints returning `Uni`, `Multi`, `CompletionStage` or `Publisher`, and Kotlin `suspend` functions, run on the IO thread; everything else runs on a worker; and `@Blocking` and `@NonBlocking` override the choice ([rest.adoc @ 3.40.1](https://raw.githubusercontent.com/quarkusio/quarkus/3.40.1/docs/src/main/asciidoc/rest.adoc)). **A `Uni` return type is a promise not to block.** Quarkus configures one event loop per CPU (minimum two, capped by memory) instead of Vert.x's two. Its source comment says 1:1 "seems … a more reasonable default. It also saves memory". It also sets the warning-exception time to 2 s, so a blocked IO thread logs a stack trace with its first warning ([VertxCoreRecorder.java @ 3.40.1](https://github.com/quarkusio/quarkus/blob/3.40.1/extensions/vertx/runtime/src/main/java/io/quarkus/vertx/core/runtime/VertxCoreRecorder.java)). Some APIs fail fast instead: a blocking body read on the IO thread, or a JTA `@Transactional` inside a reactive pipeline, throws `BlockingOperationNotAllowedException` ([TransactionalInterceptorBase.java @ 3.40.1](https://github.com/quarkusio/quarkus/blob/3.40.1/extensions/narayana-jta/runtime/src/main/java/io/quarkus/narayana/jta/runtime/interceptor/TransactionalInterceptorBase.java)). Quarkus's docs contradict each other on one rule that matters. The guide tagged 3.40.1 says `@Transactional` makes a method blocking, while the main-branch guide says that stopped "since Quarkus 3.35" ([rest.adoc main](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/rest.adoc)). Until the docs agree, put an explicit `@Blocking` on any JTA endpoint that returns `Uni`. `@RunOnVirtualThread` runs the method on a new virtual thread. The Quarkus guide lists its costs honestly: pinning by native code, monopolization by CPU-bound work, and libraries such as Jackson and Netty that "assume that the application uses a limited number of threads" ([Quarkus virtual-threads.adoc](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/virtual-threads.adoc)).

Jetty 12 shows that the choice between an event loop and a thread pool can be made per task. Its `AdaptiveExecutionStrategy`, formerly "Eat What You Kill", runs each task in one of three modes ([arch/threads.adoc](https://github.com/jetty/jetty.project/blob/jetty-12.1.14/documentation/jetty/modules/programming-guide/pages/arch/threads.adoc)): **Produce-Consume.** A task the handler declares `NON_BLOCKING` runs directly on the selector thread, as in an event loop. **Execute-Produce-Consume.** A blocking task runs on the selector thread while a reserved thread takes over selecting, which keeps CPU caches warm. **Produce-Execute-Consume.** The task is dispatched to the pool, which happens only when no reserved thread is free.

Extending `Handler.Abstract.NonBlocking` is therefore a promise, not a transformation; break it and "you risk a server lock-up" ([server/http.adoc](https://github.com/jetty/jetty.project/blob/jetty-12.1.14/documentation/jetty/modules/programming-guide/pages/server/http.adoc)). The core handler API became fully asynchronous. `boolean handle(Request, Response, Callback)` can return before the response is written, and every `Content.Chunk` read must be released ([11→12 migration](https://github.com/jetty/jetty.project/blob/jetty-12.1.14/documentation/jetty/modules/programming-guide/pages/migration/11-to-12.adoc); [arch/io.adoc](https://github.com/jetty/jetty.project/blob/jetty-12.1.14/documentation/jetty/modules/programming-guide/pages/arch/io.adoc)). The default `QueuedThreadPool` runs 8–200 threads, and its queue "must be unbounded" because HTTP/2 must write in order to make progress on reads; load limiting belongs in a QoS handler. Virtual threads come two ways ([arch/threads.adoc](https://github.com/jetty/jetty.project/blob/jetty-12.1.14/documentation/jetty/modules/programming-guide/pages/arch/threads.adoc)): `setVirtualThreadsExecutor` sends only blocking tasks to virtual threads. Locally, 40 concurrent 500 ms requests on a 12-thread pool fell from about 2.7 s to 0.55 s. `VirtualThreadPool` is a semaphore over unpooled virtual threads, and the acceptor and selectors also consume its permits.

Selectors pin carriers on JDK 19–23 either way. Tomcat 11's NIO connector, by comparison, hands requests to an executor of 200 threads by default and makes virtual threads opt-in through `useVirtualThreads` ([Tomcat 11 http.xml](https://raw.githubusercontent.com/apache/tomcat/11.0.x/webapps/docs/config/http.xml)).

The decision rule that falls out is short. Use an event loop with reactive clients when the whole stack is asynchronous and memory per connection matters. Use virtual threads when the code is naturally blocking and I/O-bound. Use a bounded worker pool, or a semaphore around the scarce resource, when concurrency itself must be capped, because virtual threads do not bound anything.

In every model, never block a Netty or Vert.x event-loop thread. The misconceptions to dismantle are: "non-blocking is faster" (it improves concurrency per thread, not per-request latency); "an event loop is a thread pool"; "virtual threads make event loops obsolete"; "direct buffers are always better"; "a bounded Jetty queue protects me"; and "Netty buffers writes for me".

## Leyden starts the JVM faster without leaving the JVM

Startup is mostly work repeated on every launch: reading, parsing and verifying classes; running static initializers; spinning lambdas; interpreting until profiles exist; and, in frameworks, scanning and reflection. A local Hello-world with one lambda loaded 560 classes on JDK 21, 549 of them from the default CDS archive. `-Xlog:class+load` labels every class with its `source:`, which turns "startup is class loading" into a visible histogram ([java.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/man/java.md)). Footprint needs the same honesty. Quarkus warns "**DO NOT use docker stat**", which "only measures a subset of the in-use resident pages", and measures RSS with `ps` because containers are killed on full RSS ([Quarkus performance-measure.adoc](https://github.com/quarkusio/quarkus/blob/main/docs/src/main/asciidoc/performance-measure.adoc)). NMT's committed figure does not measure residency either. One local run committed 288 MiB against a maximum RSS of about 50 MiB, because untouched heap pages are never resident. Three clocks also differ. `-Xlog:startuptime` covers JVM creation only, the framework's "started in" line covers its own init, and only external time-to-first-request measures what a load balancer sees.

Every JDK since 12 ships a default CDS archive of about 1,300 core classes. AppCDS adds application classes through a static dump or a dynamic `-XX:ArchiveClassesAtExit` archive, and `-XX:+AutoCreateSharedArchive` (JDK 19) maintains one automatically ([java.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/man/java.md)). The man page now points elsewhere: the dynamic archive "supports fewer optimizations… consider using the AOT cache". One old selling point has also faded. Archive mappings are relocated to randomized addresses by default (`ArchiveRelocationMode=1`) ([cds_globals.hpp @ jdk-21-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-21-ga/src/hotspot/share/cds/cds_globals.hpp); [commit 437342b](https://github.com/openjdk/jdk/commit/437342b93e9e66340ac57bd1c6fdc948b3302db0)). In one JDK 25 process, about 11.5 MB of the 14.4 MB mapped from an AOT cache were private dirty pages. CDS should therefore be sold for startup, not for RAM shared across containers.

Project Leyden shipped in pieces: JEP 483 (JDK 24) introduced the AOT cache, with ahead-of-time class loading and linking ([commit 41a2d49](https://github.com/openjdk/jdk/commit/41a2d49f0a1ed298b8ab023ce634335464454fe7)). JEPs 514 and 515 (JDK 25) added the one-step `-XX:AOTCacheOutput` workflow and method profiles ([commit dede353](https://github.com/openjdk/jdk/commit/dede3532f7238d527fb89be41f1b8050bde02ee3); [commit e3f85c9](https://github.com/openjdk/jdk/commit/e3f85c961b4c1e5e01aedf3a0f4e1b0e6ff457fd)). JEP 516 (JDK 26) stored heap objects in a GC-agnostic streamable form, so the full cache works with ZGC ([commit c865644](https://github.com/openjdk/jdk/commit/c8656449c28581ae9c3d815105e338e42253bb43)). JDK 27 shipped no Leyden JEP, only `-XX:AOTMode=required` as the preferred spelling of `on` ([commit 42d6307](https://github.com/openjdk/jdk/commit/42d6307030543948317d767d6085840f1b0a2ea8)). **AOT code compilation (JEP 544) and faster ZGC startup (JEP 545) are integrated only in the JDK 28 mainline** ([commit f6fa653](https://github.com/openjdk/jdk/commit/f6fa65381d0c32e22120159415f8c472e990cdc7); [commit d544fca](https://github.com/openjdk/jdk/commit/d544fca92aab371187df86fbbf3b473abdab25b2)).

On JDK 25, training and assembly are one command, `java -XX:AOTCacheOutput=app.aot -cp app.jar Main`, implemented by forking a second JVM configured through `JAVA_TOOL_OPTIONS`. Production then runs `java -XX:AOTCache=app.aot -cp app.jar Main` ([java.md @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/man/java.md)). The JEP 483 work measured Spring PetClinic, which loads about 21,000 classes at startup. The draft reported it starting 42% faster, and InfoQ reported the shipped feature as up to 40% faster ([JEP 483](https://openjdk.org/jeps/483); [InfoQ, March 2025](https://www.infoq.com/news/2025/03/java-24-leyden-ships)). A cache is specific to the application classpath, the JDK release, the OS and CPU, and the JVM options. In the default `auto` mode, which the man page recommends for production, an unusable cache is silently skipped. `required` exits instead, and the JDK 27 man page warns that a cloud provider's JVMTI class-file hook can then stop the application from launching ([java.md @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/java.base/share/man/java.md)).

The pitfalls are the lesson. **On JDK 25.0.0–25.0.3 and 26.0.0–26.0.1, the AOT cache was not rejected when the application JAR changed.** A pipeline that rebuilt the JAR but reused an old cache therefore ran stale class bytes. This was reproduced locally on Temurin 25+36: a rebuilt JAR printing "version TWO" ran as "version ONE", while the older CDS archive formats correctly refused the changed JAR. The fix, JDK-8377932, landed in JDK 27 and was backported to 25.0.4 and 26.0.2 ([commit b41ba3a](https://github.com/openjdk/jdk/commit/b41ba3a496b59c8058067a49617f798606f0a51c); [jdk25u](https://github.com/openjdk/jdk25u)). Generate the cache in the same build step as the JAR, and require 25.0.4 or later. Four other traps follow the same theme of an invisible mismatch. A mistyped `-XX:AOTCache` path also disables the default CDS archive, making startup worse than passing no flag. On JDK 25, a G1-built cache is unusable under ZGC, and a ZGC-built one helps only partly. `-XX:StartFlightRecording` adds `jdk.jfr` to the module graph, so a mismatched `--add-modules` rejects the cache ([Quarkus aot.adoc main](https://github.com/quarkusio/quarkus/blob/main/docs/src/main/asciidoc/aot.adoc)). Because the cache records `UseCompactObjectHeaders`, a cache built under JDK 27 defaults will likely not load in a process that turns compact headers off. This is an inference from the log, untested.

CDS and AOT do not change initialization order: archived classes are loaded and linked, not initialized early. A local holder-idiom test confirmed this under both an AppCDS archive and an AOT cache.

Quarkus 3.40 reduces all of this to one property ([Quarkus aot.adoc @ 3.40.1.1](https://raw.githubusercontent.com/quarkusio/quarkus/3.40.1.1/docs/src/main/asciidoc/aot.adoc)). `quarkus.package.jar.aot.enabled=true` builds an `aot-jar` package that hands class loading to the JDK's own loaders, because Leyden does not support custom loaders. The build trains the cache during `@QuarkusIntegrationTest`, and the application runs with `java -XX:AOTCache=app.aot -jar quarkus-run.jar`. On JDKs before 24 it falls back to AppCDS. Quarkus's own perf-lab table, measured with Quarkus 3.34.3 on JDK 25.0.2, quantifies the trade-off ([building-native-image.adoc](https://github.com/quarkusio/quarkus/blob/main/docs/src/main/asciidoc/building-native-image.adoc)):

| Mode | Time to first request | Peak throughput | RSS | Build cost |
|---|---|---|---|---|
| JVM fast-jar | 4,417 ms | 13,265 tps | 304 MiB | about 30 s |
| JVM with Leyden AOT cache | 1,859 ms | 12,389 tps (about 7% lower) | 240 MiB | build plus training run; image about 198 MB larger |
| Native (Mandrel) | 581 ms | 5,411 tps (about 59% lower) | 95 MiB | 3–10 min and 4–8 GB of build-host RAM |

GraalVM Native Image compiles the reachable application and JDK under a closed-world assumption. Reflection, resources, proxies, serialization and JNI therefore need reachability metadata in `META-INF/native-image/<groupId>/<artifactId>/reachability-metadata.json` ([ReachabilityMetadata.md](https://github.com/oracle/graal/blob/master/docs/reference-manual/native-image/ReachabilityMetadata.md)). The current schema, v1.2.0, allows only `reflection`, `resources`, `foreign` and `comment` at the top level. A proxy is a reflection entry whose `type` is `{"proxy": [ordered interfaces]}`, and serialization and JNI are flags on reflection entries ([schema v1.2.0](https://github.com/oracle/graal/blob/master/docs/reference-manual/native-image/assets/reachability-metadata-schema-v1.2.0.json)). Two sets of docs contradict that schema. GraalVM's prose still describes a top-level `jni` section, and Quarkus main's docs speak of a "`proxy` section". Quarkus 4.0 also drops the legacy `reflect-config.json` and `proxy-config.json` files that the 3.x docs still show ([Quarkus native tips @ 3.40.1.1](https://raw.githubusercontent.com/quarkusio/quarkus/3.40.1.1/docs/src/main/asciidoc/writing-native-applications-tips.adoc)). The mental model is "the build is the program's first run". Quarkus initializes all classes at build time by default, so a static `Random` or `NativePRNG` captured in the image heap fails the build and needs `--initialize-at-run-time` ([ClassInitialization.md](https://github.com/oracle/graal/blob/master/docs/reference-manual/native-image/ClassInitialization.md)). The default native GC is Serial, with a maximum heap of 80% of physical memory, while G1 and profile-guided optimization exist only in Oracle GraalVM ([MemoryManagement.md](https://github.com/oracle/graal/blob/master/docs/reference-manual/native-image/MemoryManagement.md); [PGO.md](https://github.com/oracle/graal/blob/master/docs/reference-manual/native-image/PGO.md)).

CRaC snapshots a warmed process through CRIU and restores it with its JIT code intact. The project's published 2020 measurements cut time-to-first-operation from 980 ms to 33 ms for Quarkus and from 3,898 ms to 38 ms for Spring Boot ([CRaC startup.data](https://github.com/CRaC/docs/blob/master/startup.data)). It is **not in mainline OpenJDK**: the openjdk/jdk history has no CRaC commits. It ships in Azul Zulu 17, 21 and 25 Linux builds marked "-crac-" and in BellSoft Liberica CRaC builds ([CRaC docs](https://github.com/CRaC/docs/blob/master/README.md); [Azul: running CRaC](https://docs.azul.com/crac/usage/running-crac)). Its default file-descriptor policy is `error`, so an open socket fails the checkpoint, and the socket `reopen` action is documented as not implemented ([fd-policies.md](https://github.com/CRaC/docs/blob/master/fd-policies.md)). AWS Lambda SnapStart uses the same `org.crac` hooks. It calls `beforeCheckpoint` in reverse registration order and `afterRestore` in registration order, and allows 10 seconds for the restore ([AWS SnapStart runtime hooks](https://docs.aws.amazon.com/lambda/latest/dg/snapstart-runtime-hooks-java.html)). A restore also clones any entropy captured before the snapshot: seeds, UUID generators, tokens and connection pools.

The decision follows from this evidence. Default to the JVM. On JDK 25.0.4+, add a Leyden cache trained by integration tests, which needs no code changes. On JDK 21, use AppCDS. Choose native image when millisecond cold starts or RSS density is the binding constraint, and the team accepts slower builds, metadata upkeep and lower peak throughput. Choose CRaC or SnapStart when instant warmed performance matters and the runtime and its resources can be made checkpoint-safe. Choose nothing for long-running services nobody waits on.

Startup matters well beyond serverless: scale-out under load, rolling deploys, readiness probes and every `@QuarkusIntegrationTest` JVM. The misconceptions to correct are: "native is always faster"; "CDS/AOT changes what my code does"; "Leyden is native image"; "`required` is the safer production mode"; "CRaC can snapshot anything"; "docker stats shows my memory"; and "CDS saves RAM across containers".

## Kotlin 2.4 and Java 27 ship stable features with documented sharp edges

### Kotlin's conveniences compile to costs that Java can see

Kotlin 2.4.0 (14 July 2026) made three features stable: context parameters (except explicit context arguments and callable references), explicit backing fields, and the new annotation use-site rules. It also removed the K1 compiler (`-language-version 1.9`) and can emit Java 26 bytecode ([What's new in 2.4.0](https://kotlinlang.org/docs/whatsnew24.html)). Context receivers, the earlier prototype, lost support in 2.3.20, and 2.4.21 rejects both the old `context(Logger)` syntax and the `-Xcontext-receivers` flag with errors that point to the migration ([What's new in 2.3.20](https://kotlinlang.org/docs/whatsnew2320.html)). Several features remain experimental ([features and proposals](https://kotlinlang.org/docs/kotlin-language-features-and-proposals.html); [kotlinc 2.4.21 run](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-compiler/2.4.21/)): contracts still need `@OptIn(ExperimentalContracts::class)`; `@JvmExposeBoxed` needs `@OptIn(ExperimentalStdlibApi::class)`; and name-based destructuring needs language-version 2.5 semantics.

Multi-field value classes do not exist, even behind an internal flag. Because context parameters are newly stable, much published material still passes `-Xcontext-parameters`, which 2.4.21 reports as "redundant".

**Inlining copies code, and the copy is part of the ABI.** The bytecode shows the difference ([kotlinc 2.4.21 run](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-compiler/2.4.21/)): a non-inline higher-order call allocates a `Function0` through `invokedynamic` and unboxes a generic result. The inline version puts `x * 2` straight into the caller, but it also duplicates the function's `try/finally` printing code for both the normal and the exceptional path.

When a library changed both an `inline fun greeting()` and a plain function from "v1" to "v2", an old client binary printed `inline=v1 plain=v2`. That is the docs' "risks of binary incompatibility" made visible ([Inline functions](https://kotlinlang.org/docs/inline-functions.html)). Java sees an inline function as an ordinary static method with no inlining, and a reified one as a synthetic method it cannot call. Value classes are "boxed whenever they are used as another type": in generics, nullables, interfaces, collections and `println`. Functions that take them are name-mangled, so `charge(amount: Money)` becomes `charge-DfepdXk(long)` unless `@JvmName` or the experimental `@JvmExposeBoxed` provides a Java-callable form ([Inline value classes](https://kotlinlang.org/docs/inline-classes.html); [Calling Kotlin from Java](https://kotlinlang.org/docs/java-to-kotlin-interop.html)). A Money lab should keep `override fun toString(): String` explicit. Both 2.4.21 and 2.3.21 crash with a backend IR error on a value class whose `toString` infers a Java platform type and is then used in a string template ([kotlinc 2.4.21 run](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-compiler/2.4.21/)).

Class delegation forwards everything that is not overridden, including bulk methods. An `AuditedMap … by inner` that overrode only `put` logged one entry after `putAll` had added two more. The delegate is also captured once into a hidden `$$delegate_0` field, so reassigning the constructor property changes nothing ([Delegation](https://kotlinlang.org/docs/delegation.html)). `by lazy` is synchronized by default. Each instance pays for a `SynchronizedLazyImpl` with a lock and a volatile field plus an initializer lambda, and every read goes through `Lazy.getValue()` ([Delegated properties](https://kotlinlang.org/docs/delegated-properties.html)). DSLs need no library: function literals with receivers plus a `@DslMarker` annotation are enough. The marker turns a misplaced `payee { }` from a silently built second party into a compile error ([Type-safe builders](https://kotlinlang.org/docs/type-safe-builders.html)). One docs-versus-compiler conflict surfaced. The builders page calls a receiver shadowed by a context parameter "a warning", but 2.4.21 reports the KEEP's own example as an error, so trust the compiler ([KEEP-0367](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0367-context-parameters.md)). **Contracts are trusted, not verified.** KEEP-139 says the compiler "trusts contracts unconditionally". A lying `returns(true) implies (this is Captured)` compiled cleanly and threw `ClassCastException` at run time; K2 only warns on some `callsInPlace` misuse ([KEEP-0139](https://github.com/Kotlin/KEEP/blob/main/proposals/KEEP-0139-kotlin-contracts.md)).

Compiler plugins are where Kotlin meets JVM proxies. All-open opens only classes that carry a configured annotation or meta-annotation, and it leaves private members private and backing fields final. The kotlin-spring preset covers `@Component`, `@Transactional`, `@Async`, `@Cacheable` and `@SpringBootTest`, and in the 2.4.21 jar also `@Validated` ([All-open plugin](https://kotlinlang.org/docs/all-open-plugin.html); [allopen 2.4.21](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-allopen-compiler-plugin/2.4.21/)). **The built-in `quarkus` preset in 2.4.21 matches only `javax.enterprise.context.ApplicationScoped` and `RequestScoped`.** A Quarkus 3 bean annotated with `jakarta.enterprise.context.ApplicationScoped` therefore stayed `final` until the jakarta annotation was configured explicitly. ArC can transform unproxyable classes by default, yet the Quarkus Kotlin guide still recommends all-open for JAX-RS resources, `@ApplicationScoped` beans and JPA entities ([Quarkus kotlin.adoc](https://raw.githubusercontent.com/quarkusio/quarkus/main/docs/src/main/asciidoc/kotlin.adoc)). Teach both mechanisms and configure jakarta annotations explicitly. From 2.3.20 the kotlin-jpa plugin also applies all-open with the JPA preset, so "lazy associations work as expected instead of causing eager loading" ([What's new in 2.3.20](https://kotlinlang.org/docs/whatsnew2320.html)). The no-arg plugin generates a constructor that is hidden from Kotlin and skips property initializers unless `invokeInitializers=true` is set. A non-null `var note: String = "default-note"` was `null` when Java reflection built the object ([No-arg plugin](https://kotlinlang.org/docs/no-arg-plugin.html); [noarg 2.4.21](https://maven-central.storage-download.googleapis.com/maven2/org/jetbrains/kotlin/kotlin-noarg-compiler-plugin/2.4.21/)). kotlinx.serialization is static by default and needs a sealed base for closed polymorphism. Its default type discriminator is the fully qualified class name, which `@SerialName` should pin ([Serialize polymorphic classes](https://kotlinlang.org/docs/serialization-polymorphism.html)). KSP 2.3 deprecated KSP1 and decoupled its version from the compiler's ([KSP 2.3.0 release](https://github.com/google/ksp/releases/tag/2.3.0)). It claims up to 2× faster processing than kapt ([KSP README](https://github.com/google/ksp)), whose stubs "significantly" increase build time ([Migrate from kapt](https://kotlinlang.org/docs/ksp-kapt-migration.html)).

### Java's data model is final in 21, and its next arc is still a design note

Records, sealed types, pattern `switch` with guards and `case null`, and record patterns have all been final since JDK 21, so a `--release 21` course can teach the whole core ([Source.java @ master](https://raw.githubusercontent.com/openjdk/jdk/master/src/jdk.compiler/share/classes/com/sun/tools/javac/code/Source.java)). Two adjacent features are missing there. Unnamed variables (`_`) need `--enable-preview` on 21 and became final in 22. Flexible constructor bodies, which allow statements before `this(...)`, became final in 25 ([Preview.java @ jdk-22-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-22-ga/src/jdk.compiler/share/classes/com/sun/tools/javac/code/Preview.java); [Source.java @ master](https://raw.githubusercontent.com/openjdk/jdk/master/src/jdk.compiler/share/classes/com/sun/tools/javac/code/Source.java)). Three common claims are false: **Primitive patterns are not final.** Primitive types in patterns have been a preview in every release from 23 through 27, and remain one on master ([Preview.java @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/jdk.compiler/share/classes/com/sun/tools/javac/code/Preview.java)). **Withers never shipped.** Derived record creation (JEP 468) has no implementing commit, and Brian Goetz wrote in January 2026 that it "has been 'on hold' for a while" ([beyond-records.md](https://github.com/openjdk/amber-docs/blob/master/site/design-notes/beyond-records.md)). **Valhalla's value objects are not in JDK 25, 26 or 27.** JEP 401 was integrated on 31 July 2026, eight weeks after the JDK 28 fork, as a JDK 28 preview ([commit cc278db](https://github.com/openjdk/jdk/commit/cc278dbb8a1ca0754d5842708b9029441055d361); [Valhalla project page](https://github.com/openjdk/valhalla-docs/blob/main/site/_index.md)).

The pattern-matching change that does matter in JDK 27 is diagnostic: javac now lists the missing patterns in a non-exhaustive-switch error ([compiler.properties @ jdk-27-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-27-ga/src/jdk.compiler/share/classes/com/sun/tools/javac/resources/compiler.properties)).

A record is a "shallowly immutable, transparent carrier" ([Record.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/Record.java)). Its equality uses `Objects.equals` for references and the wrapper's `compare` for primitives. That makes `NaN` equal to itself and `0.0` unequal to `-0.0`, while array components compare by reference. Shallow immutability is the production hazard. A record that holds a caller's `ArrayList` changes its `hashCode` when the list changes, so it can be lost as a `HashSet` key. `List.copyOf` in the compact constructor fixes that, at the price of rejecting null elements. The canonical constructor is the only door. Every factory, every non-canonical constructor and even deserialization go through it, so swapping two ints in a serialized `Range` stream failed with `InvalidObjectException: lo > hi`. Records cannot hide data either: overriding an accessor leaves the generated `toString` printing the raw field.

A pattern `switch` is not sugar for an `instanceof` chain: an `instanceof` chain that forgets a subtype compiles silently, while the switch fails with "does not cover all possible input values"; javac rejects dominated labels; and the bytecode is an `invokedynamic` to `SwitchBootstraps.typeSwitch` plus a synthetic `MatchException` arm for the remainder: nested `null`s and subtypes added under separate compilation ([MatchException.java @ jdk-25-ga](https://raw.githubusercontent.com/openjdk/jdk/jdk-25-ga/src/java.base/share/classes/java/lang/MatchException.java)).

The Amber exhaustiveness guide is blunt about the most common mistake: "A `default` label is almost never the right answer… it sweeps errors, both present and future, under the rug… it does not handle a `null` selector" ([exhaustiveness-guide.md](https://github.com/openjdk/amber-docs/blob/master/site/guides/exhaustiveness-guide.md)).

Data-oriented programming ties the track together. Model data as records and sealed sums, make illegal states unrepresentable through types and constructor validation, and write operations as functions that switch over the data. That trades easy new types for easy new operations, and the compiler names every site a new type breaks. Goetz calls records, sealed classes and record patterns "the first feature arc" and has announced carrier classes as the next one, still a design note ([beyond-records.md](https://github.com/openjdk/amber-docs/blob/master/site/design-notes/beyond-records.md)).

Under the JDK 28 preview, value objects give up identity in exchange for flattening and scalarization. `value record` is legal, and 28 JDK classes become value classes, including `Integer`, `Optional` and `LocalDate`; synchronizing on one throws `IdentityException` ([value-objects.md](https://github.com/openjdk/valhalla-docs/blob/main/site/value-objects.md); [Integer.java @ master](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/lang/Integer.java)). The limits are part of the lesson: heap-flattened encodings are atomic and must encode null, so "value objects with 64 bits or more of field data cannot normally be flattened"; scalarization waits for C2; and generic code is not flattened.

A `record Money(long minor, String currency)` therefore gains little from `value`. Kotlin's `@JvmInline value class` remains a single-field, compile-time erasure designed to leave room for a Valhalla-backed form, but no Kotlin compilation mode for JEP 401 exists ([KEEP notes: value classes](https://github.com/Kotlin/KEEP/blob/master/notes/value-classes.md)). Compared honestly ([Kotlin data classes](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/data-classes.md); [JVM records in Kotlin](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/jvm/jvm-records.md)): **Kotlin wins** on `copy`, `data object`, smart casts and long-standing exhaustiveness errors that name the missing branch. **Java wins** on nested deconstruction with guards over components, transparent serialization and reflection, a defined run-time story for separate compilation, and the path to `value record`.

Kotlin destructuring is still positional `componentN()`. `val (amount2, id2) = p` silently swapped two fields without a warning in 2.4.21, and name-based destructuring stays experimental ([Destructuring declarations](https://github.com/JetBrains/kotlin-web-site/blob/master/docs/topics/destructuring-declarations.md)).

## Grade bytes, counts and compiler verdicts, not nanoseconds

Across all seven tracks, one rule separates labs that grade reliably from labs that flake. Assert what the JVM reports exactly: allocated bytes, field offsets, instance and class counts, parsed log or JFR records, call counters and compiler diagnostics. Use time only as a coarse relation with a wide margin, such as "the second client's reply arrives in under 200 ms" against an observed 1,060 ms failure. The memory, class-loading, proxy, I/O, Kotlin and Java labs below ran as JUnit suites on the course's pinned stack: JDK 21 unless noted, JUnit 6.1.3 ([console launcher](https://maven-central.storage-download.googleapis.com/maven2/org/junit/platform/junit-platform-console-standalone/6.1.3/junit-platform-console-standalone-6.1.3.jar)), Kotlin 2.4.21, Byte Buddy 1.18.17, Netty 4.2.20, Vert.x 5.2.3 and Jetty 12.1.14. Several harness rules were learned by breaking them. Never put `-XX:+DisableExplicitGC` on the test JVM. Bound every GC wait loop (for example, 50 × `System.gc()` with a short `ReferenceQueue.remove`), so a misbehaving test fails within the 20 s default timeout instead of hanging. Measure allocation on platform threads. Keep scalar-replacement "zero bytes" as a demo, not a CI assertion. Assert relative JOL offsets, because compact headers move every absolute offset on JDK 27. Run JOL on records with `-Djol.magicFieldOffset=true` on JDK 21. Compile Kotlin tests with `-jvm-target 21`. JUnit's inline `assertThrows` is built for 17 and will not inline into 1.8 bytecode. Add `-XX:+EnableDynamicAgentLoading` wherever Byte Buddy or Mockito self-attaches. Bind servers to `127.0.0.1:0`. Use `java.net.http.HttpClient` with `NO_PROXY` in proxied CI. Put vertx-junit5 assertions inside `verify`. Run each class-initialization test in a fresh class loader.

The labs project itself constrains three tracks. `labs/build.gradle.kts` compiles everything at `--release 21` and passes `-Xshare:off` to test JVMs. The ClassFile API lab, `_` patterns and flexible constructor bodies therefore need a per-module JDK 25 target, and every CDS or Leyden assertion must run in a forked JVM.

The misconceptions catalogued above double as practice material. Practice testing and distributed practice are the two techniques Dunlosky's review rated high-utility ([APS](https://www.psychologicalscience.org/news/releases/which-study-strategies-make-the-grade.html)). And multiple-choice questions with plausible wrong options improve later recall even of related material that was never tested ([Little & Bjork 2014](https://bjorklab.psych.ucla.edu/wp-content/uploads/sites/13/2017/01/LittleBjorkMC2014.pdf)). This track's distractors write themselves: `CompileThreshold` 10,000 versus a tier-4 threshold of 5,000; "G1 everywhere" versus "G1 everywhere from 27"; `AOTMode=on` versus `auto`; and Spring versus ArC self-invocation.

The JVM ships its own answer keys. javac and kotlinc grade "does this compile?" items. `PrintFlagsFinal` grades "what is the default on JDK N?" items. `jfr view`, NMT and `-Xlog:class+load` grade diagnosis items. Version-stamped fact cards need a "valid since" field and a re-check at each March and September release. Mechanism cards, which cover headers, tiers, delegation, event loops and the closed world, can be scheduled for months.

## Conclusion

The understanding that changed is that "advanced JVM" now means reading the runtime's effective configuration rather than memorizing it. JDK 27's two default flips alone change GC choice, object size, CDS archive selection, JOL offsets and AOT cache compatibility at once. Fact-checking also found real defects at the seams between versions. One was a stale-cache bug in shipped LTS updates. Others were a Kotlin compiler crash, a Kotlin all-open preset still matching `javax.*`, and Quarkus and GraalVM docs that contradict their own code or schema. A course that trains learners to ask the JVM (`PrintFlagsFinal`, `-XshowSettings:system`, `-Xlog:aot`, NMT, `javap`) builds a skill that survives the next release. A course that teaches the numbers builds flashcards that expire every six months.

The second takeaway is structural: a handful of mechanisms recur across all seven topics, so a course can teach each once and map the frameworks onto it. Subclass-versus-forwarding proxies explain Spring, ArC, Hibernate, Byte Buddy and Kotlin's all-open plugin. The single-threaded event loop explains NIO, Netty, Vert.x, Quarkus, Jetty's Produce-Consume mode and even the JDK's virtual-thread poller. "Work moved from run time to build time" explains class initialization, CDS, Leyden, native image, CRaC and Quarkus itself. JDK 28 in March 2027 will extend that last arc with AOT-compiled code and open the Valhalla arc with value objects. The next refresh should therefore add material rather than rewrite it, provided the lab build first moves from a blanket `--release 21` to per-track JDK targets.
