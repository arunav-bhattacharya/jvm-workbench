## Key Question 1: What changed in kotlinx.coroutines 1.9, 1.10 and 1.11, and what changed in Kotlin 2.x that affects coroutines?

### Takeaway
1.9 (built with Kotlin 2.0) made `limitedParallelism` stable and added a `name` parameter. It also added `Flow.chunked`, made closeable dispatchers `AutoCloseable`, and pushed the old test API and the `BroadcastChannel` API further into deprecation. 1.10 (Kotlin 2.1.0) added `Flow.any/all/none` and reorganized the debug artifact. 1.11 (Kotlin 2.2.20) rewrote the structured-concurrency and error-handling KDoc and deprecated `CoroutineDispatcher` as a context key. It also added lint against passing a `Job` to builders, raised the old `runTest(dispatchTimeoutMs)` overloads to ERROR, and added small APIs such as `SharedFlow.asFlow` and `CompletableDeferred.asDeferred`. On the Kotlin side, the things that matter for coroutine code are: explicit backing fields (experimental in 2.3.0, **stable in 2.4.0**), which simplify exposing `MutableStateFlow` as `StateFlow`; common atomics in the stdlib (2.1.20, experimental); suspend-lambda overload resolution (2.2.20); and the new stdlib `StackTraceRecoverable` interface (2.4.20, experimental).

### Inferences
- The labs pair Kotlin 2.4.21 with kotlinx.coroutines 1.11.0, a library compiled against Kotlin 2.2.20. That is the normal pairing: a newer compiler consuming an older library. I found no source saying they are incompatible, but I also did not find an explicit compatibility statement.
- 1.11.0's changelog says nothing about `StackTraceRecoverable`, and 1.11.0 is compiled against Kotlin 2.2.20, which predates the 2.4.20 interface. So the labs probably will **not** see 1.11.0 use `StackTraceRecoverable`. Lessons should present it as "new stdlib hook, library support may need a later kotlinx.coroutines" unless a lab checks it.
- Because of the 1.11 `callsInPlace(EXACTLY_ONCE)` contract on `runBlocking`, the compiler should accept `val x: Int; runBlocking { x = compute() }`, that is, definite assignment of a `val` inside the block. This follows from contract semantics and was not tested.
- Code that reads `coroutineContext[CoroutineDispatcher]` warns on 1.11 and is scheduled to break on 1.12. Teach `coroutineContext[ContinuationInterceptor] as? CoroutineDispatcher`.

## Key Question 2: What are the precise rules people get wrong? (exceptions in async without await, SupervisorJob placement, runBlocking inside coroutines, catching CancellationException / runCatching, Dispatchers.IO vs Default, blocking calls)

### Takeaway
Five rules cover most mistakes. (1) A failed `async` child in a regular scope cancels its parent whether or not anyone calls `await`. (2) Passing any `Job`, including `SupervisorJob()`, to `launch`/`async`/`withContext` replaces the parent and breaks structured concurrency. The scope stops waiting for that coroutine, its failures bypass the scope, and 1.11 adds lint against it. (3) Calling `runBlocking` inside a suspend function blocks the thread and is always wrong. Nested `runBlocking` calls share one event loop. (4) Cancellation is an exception. Catching it, which includes `runCatching`, breaks cancellation unless you rethrow, and a `CancellationException` escaping a child is treated as "cancelled", not "failed". (5) Cancellation is cooperative. Blocking calls (`Thread.sleep`, blocking IO) ignore `withTimeout` unless wrapped in `runInterruptible`. Use `Dispatchers.IO` for blocking IO (64 threads by default, elastic views) and `Dispatchers.Default` for CPU work (one thread per core, at least 2).

### Cited Findings

**Suspension and the compiler (mechanics that underpin every rule)**
- Suspend functions use continuation-passing style. "Every suspending function and suspending lambda has an additional `Continuation` parameter". `suspend fun <T> CompletableFuture<T>.await(): T` is compiled to `fun <T> CompletableFuture<T>.await(continuation: Continuation<T>): Any?`, and the `Any?` result is in effect a union of `COROUTINE_SUSPENDED` and `T`. — [KEEP coroutines.md](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- A suspend function that suspends returns the `COROUTINE_SUSPENDED` marker. If it does not suspend, "it returns its result or throws an exception directly". — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- State machines: "a suspending function is compiled to a state machine, where states correspond to suspension points". The compiler creates "only one class per suspending lambda that may have an arbitrary number of suspension points". The generated class has a `label` field for the current state and fields for locals that live across states. — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- A suspend function that calls other suspend functions only in tail position is compiled like a regular function and simply passes its continuation along. A state machine is created only when a suspending call is in non-tail position. That state-machine instance is created when the function is invoked and is reused across its suspending calls. — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- `interface Continuation<in T> { val context: CoroutineContext; fun resumeWith(result: Result<T>) }`, plus the `resume`/`resumeWithException` extensions. — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- The implementation must not invoke the continuation in its own stack frame, because that risks stack overflow. `suspendCoroutine` hides this from the developer. — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- The KEEP lists its authors as Andrey Breslav and Roman Elizarov, with status "Stable since Kotlin 1.3 (Revision 3.3), experimental in Kotlin 1.1-1.2". — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)
- `suspendCancellableCoroutine` is the canonical way to wrap callbacks; the example is `CompletableFuture.await` with `c.invokeOnCancellation { future.cancel(true) }`.
  - `CancellableContinuation` is thread-safe. When `cancel` and `resume` race, only one succeeds, and concurrent `resume` calls throw `IllegalStateException`.
  - It gives a **prompt cancellation guarantee**: if the job was cancelled while suspended, the coroutine "will not resume successfully, even if `resume` was already invoked but not yet executed".
  — [CancellableContinuation.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CancellableContinuation.kt)
- **[1.9]** `resume(value) { cause, value, context -> ... }` is the stable overload for closing a resource that never got delivered. The old single-argument `onCancellation` overload is deprecated in its favor. — [CancellableContinuation.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CancellableContinuation.kt); [CHANGES.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/CHANGES.md)
- "You can only call a suspending function from another suspending function"; `suspend fun main()` is allowed. — [coroutines-basics.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-basics.md)
- `async`/`await` are not keywords in Kotlin and are not part of its standard library; they live in kotlinx.coroutines. — [coroutines-guide.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-guide.md)

**Builders, Job/Deferred, structured concurrency (rewritten 1.11 KDoc)**
- `launch` creates a *child coroutine* of the receiver scope. The scope's `Job` becomes the parent, and the coroutine "is considered active until the block and all the child coroutines created in it finish". — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- How the lifecycles interact:
  - The parent scope cannot end until the child and all its children complete.
  - If the parent is cancelled, the child is cancelled.
  - If the child fails with a non-`CancellationException` and the parent has a non-supervisor `Job`, "the parent `Job` is cancelled with this exception".
  - If the block throws `CancellationException`, the coroutine counts as cancelled, cancels its own children, and "the parent does not get notified".
  — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- **`async` without `await`**: the same rules apply. If an `async` child fails with a non-`CancellationException` and the parent has a non-supervisor `Job`, the parent is cancelled. Only when the parent has a supervisor job or no job (`GlobalScope`) is "the exception ... only available through the returned `Deferred`". — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- `launch` vs `async`: "The only difference is the handling of failures that cannot be propagated to the parent". For `async`, a `CoroutineExceptionHandler` is not invoked; the user must call `await`. — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- `Job.join` succeeds even when the coroutine was cancelled or failed. `cancelAndJoin` combines both. `CoroutineStart.LAZY` starts on `start()`, `join()` or `await()`. — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- `async(start = CoroutineStart.LAZY)` is presented as a replacement for stdlib `lazy` when the computation involves suspend functions. — [composing-suspending-functions.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/composing-suspending-functions.md)
- "Async-style functions" (`fun somethingAsync() = GlobalScope.async {...}`) are "**strongly discouraged**". If the caller aborts, the async work "still running in the background". — [composing-suspending-functions.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/composing-suspending-functions.md)

**SupervisorJob placement (the "passing a Job to launch" trap)**
- "It is incorrect to pass a [Job] element there, as this breaks structured concurrency." "Passing a Job in the context argument ... is not a supported pattern. It does not throw an exception only for backward compatibility reasons". — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- What happens if you do it anyway: the passed `Job` becomes the parent.
  - "If the CoroutineScope is cancelled, the new coroutine will not be affected."
  - Failures go to the passed job. "If that Job is a SupervisorJob, the exception will be unhandled" and goes to `CoroutineExceptionHandler` / last-resort handling.
  - "The CoroutineScope may complete without waiting for the new coroutine to finish". In particular, `coroutineScope`/`withContext` "will not wait for the new coroutine".
  — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- `withContext`: passing a `Job` is incorrect "unless it is `NonCancellable`". — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- The correct places for a supervisor are the scope constructor, as in `CoroutineScope(SupervisorJob() + Dispatchers.Main + CoroutineExceptionHandler {...})` (`MainScope()` is `ContextScope(SupervisorJob() + Dispatchers.Main)`), or `supervisorScope {}`. — [CoroutineScope.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineScope.kt)
- `SupervisorJob`: "Children of a supervisor job can fail independently". A `launch` child's failure is handled through `CoroutineExceptionHandler`, and an `async` child's failure through `await`. If a parent job is given, the supervisor is cancelled when that parent fails or is cancelled. — [Supervisor.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Supervisor.kt)
- `supervisorScope`: if the *block itself* throws, it cancels the scope and all its children. It "does not install a CoroutineExceptionHandler in the new scope", so a failing `launch` child is unhandled unless a handler is somewhere in the context. — [Supervisor.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Supervisor.kt)
- `runBlocking(CoroutineExceptionHandler {...}) { supervisorScope { ... } }`: the KDoc comment says a handler is "necessary when using `supervisorScope`". — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)

**CoroutineExceptionHandler rules**
- `CoroutineExceptionHandler` is "invoked only on **uncaught** exceptions". Children delegate to their parent "until the root, so the CoroutineExceptionHandler installed in their context is never used". "async builder always catches all exceptions ... so its CoroutineExceptionHandler has no effect either." — [exception-handling.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/exception-handling.md)
- Coroutines launched directly inside `supervisorScope` "do use the CoroutineExceptionHandler that is installed in their scope in the same way as root coroutines do". — [exception-handling.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/exception-handling.md)
- Root `GlobalScope.launch` prints the exception through `Thread.defaultUncaughtExceptionHandler`. Root `GlobalScope.async` prints nothing and relies on `await`. — [exception-handling.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/exception-handling.md)
- Aggregation: the first exception wins and "All additional exceptions ... are attached to the first exception as suppressed ones". `CancellationException`s are "ignored by all handlers". — [exception-handling.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/exception-handling.md)
- JVM last-resort handling for an exception with no propagation path: every `CoroutineExceptionHandler` found through `ServiceLoader` and the current thread's `Thread.uncaughtExceptionHandler` are invoked. A common pitfall is trying to use a CEH to prevent the expected failure of a child; "A CoroutineExceptionHandler has no effect in the scenario above." — [CoroutineExceptionHandler.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineExceptionHandler.kt)

**CancellationException and runCatching**
- "Catching `CancellationException` can break the cancellation propagation. If you must catch it, rethrow it". — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)
- `runCatching` "catch[es] any Throwable exception that was thrown from the block". The stdlib page says nothing about coroutines or `CancellationException`. — [runCatching API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/run-catching.html)
- Pitfall "CancellationException silently stopping computations": if a coroutine awaits a `Deferred` that was cancelled, the `CancellationException` that results is treated as cancellation of the awaiting coroutine, not as a failure, so the parent stays active. "This is a legacy behavior that cannot be changed in a backward-compatible way." The fix is to check `isActive`/`ensureActive()` in the `catch` to tell "I was cancelled" apart from "the thing I awaited was cancelled". — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)

**Cancellation is cooperative**
- A cancelled coroutine "continues running until it reaches ... a suspension point". "A call to a suspend function is a suspension point, but it doesn't always suspend", for example `await` on a completed `Deferred`. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)
- There are three ways to cooperate: `yield()` (suspends, lets other coroutines run, and throws if cancelled), `isActive` (returns a Boolean), and `ensureActive()` (throws `CancellationException`). The guide recommends `yield()` unless monopolizing the thread is intended. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)
- `yield()` checks for cancellation and gives a prompt cancellation guarantee. With a single coroutine on the dispatcher it may not actually suspend, though "the check for cancellation still happens". With no dispatcher in the context it does not suspend. The KDoc also has a pitfall section warning against using `yield` "to wait for something to happen". — [Yield.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Yield.kt)
- On the JVM, blocking functions like `Thread.sleep()` or `BlockingQueue.take()` are not interrupted by cancellation. Wrap them in `runInterruptible()`, for example `runInterruptible(Dispatchers.IO) { queue.take() }`. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md); [Interruptible.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Interruptible.kt)
- Prompt cancellation: a cancelled suspended coroutine "resumes with a CancellationException instead of returning any values, even if those values are already available". `withContext()` checks for cancellation before entering the block and after it returns. The risk is losing a returned resource such as an `AutoCloseable`, so keep cleanup in code that is guaranteed to run. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)
- `NonCancellable`: use it only as `withContext(NonCancellable) { ... }`, typically in `finally` for a suspending `close()`. "Avoid using NonCancellable with other coroutine builders like .launch() or .async()", because that breaks the parent-child relationship. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)

**withTimeout vs withTimeoutOrNull**
- `withTimeout` cancels its block with `TimeoutCancellationException`, which is a subclass of `CancellationException`. A non-positive timeout fires immediately and the block does not run. Cancellation on timeout "may happen at any time, even after the block finishes executing but before the caller gets resumed". `withTimeout` is lexically scoped like `coroutineScope`. — [Timeout.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Timeout.kt)
- Pitfall "Cancellation is cooperative": `withTimeout(1.seconds) { Thread.sleep(10_000) }` "will run to completion, taking 10 seconds"; use `runInterruptible`. — [Timeout.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Timeout.kt)
- Pitfall "TimeoutCancellationException is not considered an error": `coroutineScope { launch { withTimeout(10.ms) { awaitCancellation() } } }` "will finish normally". The fixes are `withTimeoutOrNull(...) ?: error("Timed out!")`, catching `TimeoutCancellationException` and rethrowing a real error, or `select` with `onTimeout`. — [Timeout.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Timeout.kt)
- `withTimeoutOrNull` returns `null` on timeout. — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)

**runBlocking**
- `runBlocking` is meant for `main` functions, tests, and non-suspend callbacks. On the JVM, interrupting the blocked thread cancels the job and makes `runBlocking` throw `InterruptedException`. — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)
- Pitfall "Calling from a suspend function": "redundant and blocks the thread, avoid this!" It can lead to thread starvation, and the caller's `currentCoroutineContext()` is ignored. — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)
- Pitfall "Sharing tasks between runBlocking calls": nested `runBlocking` calls share a thread-local event loop. An inner `runBlocking` can run the outer one's tasks, so the output is "Entered the inner runBlocking / Hello from the outer child coroutine / Leaving the inner runBlocking". 1000 nested launches that each call `runBlocking` can overflow the stack. "The specific behavior of work stealing may change in the future, but is unlikely to be fully fixed". — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)
- `runBlocking` is lexically scoped. Even when a `Job` is passed in, a failure is rethrown to the caller rather than cancelling that job, but cancelling the passed job does cancel `runBlocking`. — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)

**GlobalScope**
- `GlobalScope` is `@DelicateCoroutinesApi` and needs `@OptIn(DelicateCoroutinesApi::class)`. Using it is "an antipattern and should be avoided". Do not replace `GlobalScope.launch` with `CoroutineScope().launch`, which "suffers from all the pitfalls". A legitimate use is a top-level background process that lives as long as the app, such as a stats logger with a CEH. The recommended alternatives are plain sequential suspend calls, `coroutineScope {}`, and `withContext(Dispatchers.Default)` inside `suspend fun main()`. — [CoroutineScope.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineScope.kt)

**Dispatchers**
- `Dispatchers.Default`: the number of threads "is equal to the number of CPU cores, but is at least two". — [Dispatchers.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Dispatchers.common.kt)
- When the context contains no dispatcher, builders use `Dispatchers.Default`. Values written before a suspension are visible after resumption even when the coroutine resumes on another thread. — [coroutines-basics.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-basics.md)
- `Dispatchers.IO` is limited by the `kotlinx.coroutines.io.parallelism` property, which "defaults to the limit of 64 threads or the number of cores (whichever is larger)". It "shares threads with the Default dispatcher", so `withContext(Dispatchers.IO)` from Default "typically does not lead to an actual switching to another thread". The limit is on parallel blocking tasks, not strictly on threads. — [Dispatchers.kt (JVM)](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Dispatchers.kt)
- **IO elasticity**: views from `Dispatchers.IO.limitedParallelism(n)` "are not restricted by the Dispatchers.IO parallelism". With views of 100 (MySQL) and 60 (MongoDB), "the system may have up to 64 + 100 + 60 threads running blocking tasks in parallel during peak loads". Internally, `DefaultIoScheduler` is `UnlimitedIoScheduler.limitedParallelism(64 or cores)`, and IO's `limitedParallelism` delegates to the unlimited scheduler. — [Dispatchers.kt (JVM)](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Dispatchers.kt); [scheduling/Dispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/scheduling/Dispatcher.kt)
- **limitedParallelism semantics** **[stable since 1.9]**:
  - It creates a *view* that allows "no more than parallelism coroutines are executed at the same time". There is no limit on the number of views or on the sum of their limits, but the effective parallelism cannot exceed that of the original dispatcher.
  - It does not pin to particular threads, and a view "does not constitute a resource" that needs closing.
  - On a fixed 4-thread pool, views of 2, 3 and 1 still give at most 4 parallel tasks.
  - Implementations may return `this`; for example, `Dispatchers.Main.limitedParallelism(1)` returns `Dispatchers.Main`.
  - It throws `IllegalArgumentException` for non-positive values and `UnsupportedOperationException` for unsupported direct dispatchers.
  — [CoroutineDispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)
- **`limitedParallelism(1)` "is not a mutex!"** It guarantees sequential execution of code between suspensions, with happens-before, so `++counter` is race-free. But three coroutines that `delay` inside it interleave: "entering 0, 1, 2 … leaving 0, 1, 2". Use `Mutex`/`Semaphore` to limit concurrency. — [CoroutineDispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)
- `Dispatchers.IO.limitedParallelism(n)` can safely replace `newFixedThreadPoolContext(n)` "w.r.t. available number of threads". — [CoroutineDispatcher.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/CoroutineDispatcher.kt)
- `Dispatchers.Unconfined` "should not be used in general code". Nested unconfined coroutines form an event loop to avoid stack overflow. — [coroutine-context-and-dispatchers.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutine-context-and-dispatchers.md); [Dispatchers.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Dispatchers.common.kt)
- `Dispatchers.Main` on the JVM is the Android main thread, JavaFX, or the Swing EDT, and needs `kotlinx-coroutines-android`, `-javafx` or `-swing` respectively. — [Dispatchers.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Dispatchers.common.kt)
- `newSingleThreadContext`/`newFixedThreadPoolContext` dispatchers must be `close`d when no longer needed. — [coroutine-context-and-dispatchers.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutine-context-and-dispatchers.md)
- `Executor.asCoroutineDispatcher()` and `ExecutorService.asCoroutineDispatcher()` turn any executor into a dispatcher. If it is a `ScheduledExecutorService`, `delay`/`withTimeout` are scheduled on it; otherwise a separate internal thread tracks delays. `CoroutineDispatcher.asExecutor()` goes the other way. — [Executors.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Executors.kt)
- `Dispatchers.shutdown()` is `@DelicateCoroutinesApi` and irreversible. It is intended for containers such as OSGi, Gradle plugins and IDEA plugins. — [Dispatchers.kt (JVM)](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Dispatchers.kt)

**CoroutineContext elements**
- Context elements: the `Job`, the dispatcher (keyed by `ContinuationInterceptor` **[1.11]**), `CoroutineName` (shows in thread names in debug mode), and `CoroutineExceptionHandler`. A builder's context argument is combined with the scope's context, and its elements "simply override" the scope's. — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt); [coroutine-context-and-dispatchers.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutine-context-and-dispatchers.md)

**Shared mutable state**
- "Volatiles are of no help": `@Volatile` gives atomic reads and writes but not atomic increments. `AtomicInteger.incrementAndGet` works for simple counters. Fine-grained thread confinement, which switches context for every increment, is very slow; coarse-grained confinement is the practical choice. — [shared-mutable-state-and-concurrency.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/shared-mutable-state-and-concurrency.md)
- `Mutex.lock()` suspends and does not block. `withLock` wraps the lock/try/finally/unlock pattern. — [shared-mutable-state-and-concurrency.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/shared-mutable-state-and-concurrency.md)
- `Mutex` is **non-reentrant**: locking again from the same coroutine "still suspends the invoker". It is fair, granting the lock first come, first served. Its memory semantics are like a `synchronized` block on the JVM. — [Mutex.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/sync/Mutex.kt)

### Inferences
- `runCatching { suspendingCall() }` inside a coroutine catches `CancellationException`, because it catches every `Throwable`. That breaks the guide's "always rethrow" rule. A loop such as `while (true) { runCatching { delay(100) } }` keeps spinning after cancellation, since each `delay` throws immediately and the exception is swallowed. Teach `runCatching {...}.onFailure { if (it is CancellationException) throw it }` or `currentCoroutineContext().ensureActive()`. This combines the two sources above; the docs do not state it explicitly.
- "IO for blocking, Default for CPU" comes from the dispatchers' design: IO's 64-thread ceiling and elasticity versus Default's one thread per core. Because they share threads, switching from Default to IO is cheap. Running blocking calls on Default starves CPU work, since it has only one thread per core.
- `Dispatchers.Default.limitedParallelism(n)` with `n` at or above the core count has a special-case branch in `DefaultScheduler`. It very likely returns the dispatcher itself, under a name, but I did not read that exact line.

### Gaps
- I found no official kotlinx.coroutines doc page that names `runCatching` as an anti-pattern. The inference above is built from the stdlib page plus the cancellation guide. kotlinx.coroutines GitHub issues could not be searched (API blocked).
- I did not read the exact RejectedExecutionException handling in `asCoroutineDispatcher`; the KDoc mentions it but the text was cut off in my extract.

## Key Question 3: How do coroutines compare with Java virtual threads and Reactor today, and what do JetBrains and Roman Elizarov's writings say about structured concurrency and the design?

### Takeaway
The official JetBrains material frames coroutines against **platform threads**: threads take a few MB and number in the thousands, while you can run millions of suspended coroutines. kotlinx.coroutines 1.11.0 has **no built-in virtual-thread dispatcher**; the supported route is `Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()`. Community material says JetBrains does not plan to rebuild dispatchers on Loom, but I could not verify that from an official source. Flow was inspired by Reactive Streams but deliberately kept simpler, suspension-friendly and structured. Interop is first-class through `kotlinx-coroutines-reactive`/`-reactor` (`mono{}`, `flux{}`, `awaitSingle`, `asFlow`, `asFlux`) and through the core `future{}`/`await()` for `CompletableFuture`. Structured concurrency is now the documented core contract: every coroutine is a child of a scope, the scope waits for its children, failures propagate up, and cancellation propagates down. `GlobalScope` is explicitly an antipattern.

### Cited Findings

**Coroutines vs threads (official)**
- "A thread is managed by the operating system... Each thread usually needs a few megabytes of memory, and typically the JVM can only handle a few thousand threads at once." A coroutine "isn't bound to a specific thread. It can suspend on one thread and resume on another... allows running millions of them". The demo launches 50,000 coroutines that each `delay(5.seconds)`, then the same with 50,000 `thread {}`. — [coroutines-basics.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-basics.md)
- None of the fetched kotlinx.coroutines 1.11/master sources or guide pages mention "virtual" or "Loom". I grepped Dispatchers, Executors, CoroutineDispatcher, Builders, the test sources and all guide topics. — [Dispatchers.kt (JVM)](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Dispatchers.kt); [Executors.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Executors.kt)
- `ExecutorService.asCoroutineDispatcher()` returns an `ExecutorCoroutineDispatcher`, which is closeable and `AutoCloseable` since **[1.9]**. — [Executors.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/Executors.kt); [CHANGES.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/CHANGES.md)

**Reactor / Reactive Streams interop**
- `kotlinx-coroutines-reactor`:
  - `mono {}` is "a cold Mono that starts the coroutine on subscription", and `flux {}` is the cold `Flux` equivalent.
  - `Flow.asFlux` gives a TCK-compliant Flux.
  - It integrates Reactor `Context` with the coroutine `ReactorContext`.
  - `Job.asMono` and `Deferred.asMono` give hot Monos.
  - `Scheduler.asCoroutineDispatcher` converts a Reactor scheduler.
  — [reactor README](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/reactive/kotlinx-coroutines-reactor/README.md)
- `mono(context)` requires `context[Job] === null` ("Mono context cannot contain job in it."). A `null` result completes the Mono empty. `Mono.awaitSingle()` is `awaitSingleOrNull() ?: throw NoSuchElementException()`. — [Mono.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/reactive/kotlinx-coroutines-reactor/src/Mono.kt)
- **[1.7.0]** `Mono.awaitSingleOrNull` waits for the `onComplete` signal. — [CHANGES.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/CHANGES.md)

- "Flow is Reactive Streams compliant". The `Flow` interface is "not stable for inheritance" by third-party libraries; implement flows with `flow {}` or `AbstractFlow`. — [Flow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Flow.kt)
- Flow's design "was inspired by Reactive Streams and its various implementations. But Flow main goal is to have as simple design as possible, be Kotlin and suspension friendly and respect structured concurrency." The guide links Elizarov's "Reactive Streams and Kotlin Flows" article (not fetched). — [flow.md @1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)

**CompletableFuture interop (core, JVM)**
- `CoroutineScope.future {}`: "The running coroutine is cancelled when the resulting future is cancelled or otherwise completed". — [future/Future.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/future/Future.kt)
- `CompletionStage<T>.await()` has a fast path when the future is already done, and it unwraps `ExecutionException` to the original cause. Cancelling the awaiting coroutine calls `future.cancel(false)`. "If cancelling the given stage is undesired, `stage.asDeferred().await()` should be used instead." — [future/Future.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/jvm/src/future/Future.kt)
- **[1.7.0]** The `kotlinx-coroutines-jdk8` artifact was merged into `kotlinx-coroutines-core`, so no extra dependency is needed for `future`/`await`. **[1.7.0]** Also, the global CEH is no longer invoked for an unprocessed `future` failure. — [CHANGES.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/CHANGES.md)

**Structured concurrency in JetBrains' own words (current KDoc and guide)**
- "Structured concurrency ensures that canceling a coroutine also cancels all of its children." — [coroutines-cancellation.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-cancellation.md)
- The 1.11 KDoc lists the rules: the parent cannot end before its children; cancellation goes down; non-cancellation failure goes up through non-supervisor jobs; a `CancellationException` does not notify the parent. — [Builders.common.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/Builders.common.kt)
- `runBlocking`: "The lifecycle of the new coroutine's Job begins with starting the block and completes when both the block and all the coroutines created in the scope complete." — [Builders.concurrent.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/concurrent/src/Builders.concurrent.kt)
- The KEEP design doc, co-authored by Roman Elizarov, explains that the compiler-side design (CPS plus state machines, one class per suspending lambda) exists to "create as few classes and objects as possible", in contrast to callback styles that allocate a fresh closure per step. — [KEEP](https://raw.githubusercontent.com/Kotlin/KEEP/master/proposals/coroutines.md)

### Inferences
- For lessons: virtual threads make *blocking* code cheap, while coroutines make *suspension* explicit and add structured cancellation and Flow. On a JVM 21+ lab you can show both by running blocking JDBC-style calls inside `withContext(vtDispatcher)`, where `vtDispatcher = Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher()`. Cancellation still needs `runInterruptible` to interrupt the blocked virtual thread. This combines the asCoroutineDispatcher and runInterruptible docs and was not tested.
- Because `Dispatchers.IO.limitedParallelism(n)` is elastic, the classic argument for virtual threads ("IO is capped at 64") is weaker than many blog posts suggest. You can create larger IO views without new pools.

## Topic reference: Flow, StateFlow/SharedFlow, channels, testing, debugging (source-of-truth facts)

### Takeaway
Flows are cold and sequential. They preserve their context: change the upstream context with `flowOn`, never with `withContext` around `emit`. They are exception-transparent: `catch` sees only upstream errors. `flow {}` checks cancellation on every `emit`, but `asFlow()` and other builders do **not**, so use `.cancellable()`. Hot flows never complete. `StateFlow` = replay 1, `DROP_OLDEST`, equality-based conflation. Channel capacities are RENDEZVOUS/BUFFERED(64)/CONFLATED/UNLIMITED. `actor` is obsolete, `select` and `produce` are experimental. `runTest` skips delays on virtual time, times out after 60 s of wall-clock time, and needs `backgroundScope` for never-ending work. Turbine times out after 3 s of wall-clock time. Debug mode is enabled with `-Dkotlinx.coroutines.debug` (or `-ea`), and `kotlinx-coroutines-debug` provides `DebugProbes`.

### Cited Findings

**Flow basics and operators**
- Cold flows are lazy, "like a recipe". "Each call to `collect()` runs the entire cold flow from the beginning". Intermediate operators are cold even when the upstream is hot. — [coroutines-flow.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-flow.md)
- "By default, flows are sequential and all flow operations are executed sequentially in the same coroutine", except for operators designed to add concurrency, such as `buffer` and `flatMapMerge`. Builders are `flowOf`, `asFlow`, `flow {}`, `channelFlow {}` and `MutableStateFlow`/`MutableSharedFlow`. — [Flow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Flow.kt)
- Context preservation: a cold flow runs in the collector's context. `flowOn` "changes only the coroutine context of the upstream flow while keeping the downstream flow in the caller's context". — [coroutines-flow.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-flow.md)
- "emit should happen strictly in the dispatchers of the block in order to preserve the flow context". Emitting from another context, for example inside `withContext`, results in `IllegalStateException`; use `channelFlow` for concurrent emission. — [flow/Builders.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Builders.kt)
- Exception transparency: when `emit` throws, the flow must stop emitting and complete with that exception. `catch` "only catches upstream exceptions, but passes all downstream exceptions". `onCompletion` is "a declarative replacement for the finally block". The runtime throws `IllegalStateException` if code emits after a previous emit has thrown. — [Flow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Flow.kt)
- `onCompletion { cause -> ... }` receives a nullable cause, which is non-null when the flow aborted, including because of a downstream exception. — [flow.md @1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)
- `retry(retries, predicate)` is shorthand for `retryWhen { cause, attempt -> attempt < retries && predicate(cause) }`. — [flow/operators/Errors.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/operators/Errors.kt)
- **Flow cancellation checks**: emissions from `flow {}` "are cancellable by default — each call to emit also calls ensureActive". — [flow/Builders.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Builders.kt)
- **But `asFlow()` is not cancellable.** `flow/Builders.kt` imports `kotlinx.coroutines.flow.internal.unsafeFlow as flow`, so `IntRange.asFlow()` and the other `asFlow` builders in that file run on `unsafeFlow`, which has no `ensureActive` per emit. This holds identically at the 1.10.2 and 1.11.0 tags. The 1.10.2 guide demonstrates it: `(1..5).asFlow().collect { if (it == 3) cancel(); println(it) }` prints 1 to 5 and only throws `JobCancellationException` at the end of `runBlocking`, while `.cancellable()` stops after 3. — [flow/Builders.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Builders.kt); [Builders.kt @1.11.0](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.11.0/kotlinx-coroutines-core/common/src/flow/Builders.kt); [flow.md @1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)
- `cancellable()` is "a shortcut for `.onEach { currentCoroutineContext().ensureActive() }`". "`flow` builder and all implementations of `SharedFlow` are cancellable by default". — [flow/operators/Context.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/operators/Context.kt)
- `buffer(capacity = BUFFERED, onBufferOverflow = BufferOverflow.SUSPEND)`. `conflate()` is `buffer(CONFLATED)`, "a shortcut for `buffer(capacity = 0, onBufferOverflow = BufferOverflow.DROP_OLDEST)`". — [flow/operators/Context.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/operators/Context.kt)
- Backpressure numbers from the guide, with an emitter that waits 100 ms per item, a collector that takes 300 ms, and 3 items:
  - no buffer: "Collected in 1220 ms";
  - `.buffer()`: "1071 ms";
  - `.conflate()`: prints `1, 3`, "758 ms";
  - `.collectLatest {}`: "Collecting 1 / Collecting 2 / Collecting 3 / Done 3", "741 ms".
  — [flow.md @1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)
- `collectLatest` inserts `buffer(0)` internally so that `flowOf(1,2,3).collectLatest { delay(1); println(it) }` prints only 3. — [flow/terminal/Collect.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/terminal/Collect.kt)
- `onEach {...}.launchIn(scope)` works "like the addEventListener", and cancelling the scope plays the role of `removeEventListener`. — [flow.md @1.10.2](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.10.2/docs/topics/flow.md)
- `channelFlow {}` is cold and backed by a channel. Its default buffer holds 64 values; `.buffer(n)` and `.buffer(0)` change it. — [coroutines-flow.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-flow.md)
- `callbackFlow {}`: `awaitClose { unregister }` is "mandatory in order to prevent memory leaks". If the block returns while the channel is still open, it throws `IllegalStateException`. Register and unregister "must be thread-safe". For single-shot callbacks use `suspendCancellableCoroutine`. — [flow/Builders.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/Builders.kt)

**StateFlow / SharedFlow**
- "State flow never completes" and "Shared flow never completes". `collect` on them never returns normally. — [StateFlow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/StateFlow.kt); [SharedFlow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/SharedFlow.kt)
- StateFlow updates "are always conflated", and the conflation is equality-based through `Any.equals`, like `distinctUntilChanged`. `_counter.update { it + 1 }` is "atomic, safe for concurrent use". A `MutableStateFlow(initial)` behaves like `MutableSharedFlow(replay = 1, onBufferOverflow = BufferOverflow.DROP_OLDEST)` plus `tryEmit(initial)` plus `distinctUntilChanged()`. — [StateFlow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/StateFlow.kt)
- `MutableSharedFlow(replay, extraBufferCapacity, onBufferOverflow)`. `extraBufferCapacity` is "the number of values buffered in addition to replay". Values of `onBufferOverflow` other than `SUSPEND` "are supported only when replay > 0 or extraBufferCapacity > 0". `tryEmit` never suspends. `subscriptionCount` is a `StateFlow<Int>` that is deliberately *not* conflated. — [SharedFlow.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/SharedFlow.kt)
- `SharingStarted.Eagerly` and `SharingStarted.Lazily`, and `SharingStarted.WhileSubscribed(stopTimeoutMillis = 0, replayExpirationMillis = Long.MAX_VALUE)`. The latter throws `IllegalArgumentException` for negative values. — [SharingStarted.kt](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/kotlinx-coroutines-core/common/src/flow/SharingStarted.kt)
- `shareIn(scope, started, replay)` and `stateIn` convert cold flows to hot ones. `Eagerly` starts upstream collection immediately, before any subscriber. — [coroutines-flow.md](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/docs/topics/coroutines-flow.md)

## Teaching notes

### Misconceptions to address head-on (each backed by a citation above)
1. **"suspend means it runs on a background thread."** No. `suspend` only lets a function pause without blocking; the thread is chosen by the dispatcher, and builders default to `Dispatchers.Default` when the context has none. A suspend function that never suspends runs entirely on the caller's thread. (KEEP CPS; basics guide)
2. **"async errors only show up when I call await."** That is only true in a supervisor scope or with no parent. In a normal `coroutineScope`, a failing `async` cancels the parent and its siblings immediately. (Builders KDoc)
3. **"`launch(SupervisorJob()) { }` makes this child independent but still supervised by my scope."** It does the opposite. It detaches the child from the scope: the scope will not wait, will not cancel it, and its failure goes to the CEH or uncaught handler. 1.11 adds lint against it. Put `SupervisorJob()` in the `CoroutineScope(...)` constructor or use `supervisorScope {}`.
4. **"A CoroutineExceptionHandler on a child catches its exceptions."** CEH works only on root coroutines and on direct children of `supervisorScope`/`SupervisorJob`. It never works on `async`.
5. **"`withTimeout` stops my code after N ms."** Only at suspension points. `Thread.sleep` or blocking IO runs to completion unless wrapped in `runInterruptible`.
6. **"A timeout inside `launch` fails the parent."** It does not. `TimeoutCancellationException` is a `CancellationException`, so the parent completes normally. Use `withTimeoutOrNull ?: error(...)`.
7. **"`runCatching` is a safe way to handle errors in coroutines."** It also catches `CancellationException`. Rethrow it, or call `ensureActive()`.
8. **"`limitedParallelism(1)` is a lock."** It serializes the code between suspensions but not whole coroutines. Use `Mutex` for critical sections that span a suspension.
9. **"Mutex is like ReentrantLock."** `Mutex` is non-reentrant, so a nested `withLock` on the same mutex suspends forever.
10. **"`Dispatchers.IO` caps blocking work at 64 threads total."** IO itself does, but `IO.limitedParallelism(n)` views are elastic and add to that budget (64 + 100 + 60 example). IO and Default share threads.
11. **"Every flow is cancellable."** `flow {}` and SharedFlow are, but `asFlow()` builders are not; use `.cancellable()`. A busy collector that never suspends is not cancellable either.
12. **"`catch` catches everything in the chain."** It catches upstream errors only. Exceptions thrown in `collect {}` pass through.
13. **"StateFlow emits every value I set."** It conflates by equality. Setting an equal value emits nothing, and slow collectors skip intermediate values.
14. **"`runBlocking` is fine inside suspend code if it is short."** It blocks the thread, ignores the caller's context, and can steal tasks from other `runBlocking` calls.
15. **"`runTest` timeout uses virtual time" / "Turbine timeout uses virtual time."** Both are wall clock: 60 s by default for `runTest` and 3 s for Turbine. Delays inside `Dispatchers.Default/IO` are not skipped.

### Analogies
- **Continuation = bookmark plus callback.** The compiler turns a suspend function into a numbered-step recipe (`label`). It keeps a bookmark of which step you are on and which local variables you have, so a thread can put the book down at a suspension point and anyone can pick it up later. This is grounded in the KEEP state-machine description.
- **Structured concurrency = a family tree with a parent who will not leave the party until every child is home.** If one child gets hurt (an exception), the parent calls everyone home (cancellation). A child who just decides to leave (a `CancellationException`) does not alarm the parent. `SupervisorJob` is a parent who lets each child deal with its own problems.
- **`flowOn` = changing the kitchen, not the dining room.** The upstream (cooking) moves to another dispatcher, and the collector (eating) stays where it was.
- **`conflate` vs `collectLatest`.** `conflate` is a news ticker that shows only the latest headline when you look up. `collectLatest` is an editor who throws away a half-written article whenever a newer story arrives.
- **Hot vs cold flow.** A cold flow is a recipe that each diner cooks again. `SharedFlow` is a radio broadcast, where `replay` is "the last N songs for people tuning in late". `StateFlow` is a thermometer: one current value, no history, and no update when the value has not changed.

### Demo ideas (with expected outcomes from the cited docs)
1. **Structured-concurrency tree.** `coroutineScope { launch { delay(100); throw IOException() }; launch { try { delay(10_000) } finally { println("B cleanup") } } }`, run under the debug option so thread names show `@coroutine#N`. *Expected:* "B cleanup" prints at about 100 ms, then `coroutineScope` rethrows `IOException`. Next, swap `coroutineScope` for `supervisorScope`. *Expected:* B keeps running for its full 10 s, and the IOException goes to the uncaught handler (or a CEH, if one is installed in `runBlocking`).
2. **SupervisorJob placement trap.** Inside `coroutineScope`, run `launch(SupervisorJob()) { delay(500); throw IllegalStateException() }`, followed by `println("scope done")`. *Expected:* "scope done" prints immediately, because the scope does not wait. The exception later reaches the uncaught or CEH handler, and the scope is never cancelled. Point out the 1.11 lint warning.
3. **Cancelling a slow "API call".** Run `withTimeout(1.seconds) { Thread.sleep(5_000) }`. *Expected:* it takes about 5 s, then throws `TimeoutCancellationException`. Change it to `withTimeout(1.seconds) { runInterruptible(Dispatchers.IO) { Thread.sleep(5_000) } }`. *Expected:* it fails at about 1 s. Then wrap a real `CompletableFuture` with `.await()` and show that cancelling the coroutine cancels the future (`future.cancel(false)`), and that `asDeferred().await()` does not.
4. **Timeout does not fail the parent.** Run `coroutineScope { launch { withTimeout(10.milliseconds) { awaitCancellation() } } }; println("ok")`. *Expected:* prints "ok". With `withTimeoutOrNull(...) ?: error("Timed out!")` the scope fails with `IllegalStateException`.
5. **runCatching swallow.** In `val j = launch { while (true) { runCatching { delay(100) } } }; delay(300); j.cancelAndJoin()`. *Expected (inferred):* `cancelAndJoin` never returns, because the loop spins. Fix it with `ensureActive()`, or by rethrowing `CancellationException` in `onFailure`. Run this with a short `withTimeout` guard or under `runTest` timeout so the lab does not hang.
6. **Flow backpressure lab.** The emitter waits 100 ms per item and the collector takes 300 ms, for 3 items. Measure with `measureTimeMillis`. *Expected:* about 1200 ms with no buffer; about 1000 ms with `buffer()`; `1, 3` printed in about 750 ms with `conflate()`; "Collecting 1/2/3, Done 3" in about 750 ms with `collectLatest`.

8. **flowOn vs withContext in a flow.** Calling `withContext(Dispatchers.IO) { emit(x) }` inside `flow {}` gives `IllegalStateException` (flow invariant violated). `flow {...}.flowOn(Dispatchers.IO)` works, with emission on an IO thread and collection on the caller's thread; print thread names to show it.

12. **Virtual-time testing.** Use the README example with a `launch` doing delays 1000/200/2000 and an `async` doing 3000/500. *Expected:* prints at 1000, 1200, 3000, 3200, 3500. Then `runCurrent` / `advanceTimeBy(2.seconds)` / `advanceUntilIdle` with `assertEquals(6500, currentTime)`. Show that `withContext(Dispatchers.Default) { delay(1000) }` inside the code under test takes about 1 real second and does not advance virtual time, then fix it by injecting the dispatcher.
13. **StateFlow conflation.** Set `MutableStateFlow(0)`, then values 1, 2, 3 quickly with a collector that `delay(100)`s, then set 3 again. *Expected:* the collector sees 0 and then 3 (intermediate values skipped), and setting 3 again emits nothing. Test it with Turbine `test { awaitItem() ... expectMostRecentItem() }`.

### Exercise ideas (with expected outcomes)
- **E1: Model the state machine.** Hand-translate `suspend fun f() { val a = g(); val b = h(a); println(b) }` into a `when(label)` state machine with a `Continuation` parameter that returns `Any?` or `COROUTINE_SUSPENDED`. *Expected:* three states, `a` stored as a field, and the function returns `COROUTINE_SUSPENDED` when `g` or `h` suspends. - **E2: Wrap a callback API.** Turn a `fetch(callback)` API into `suspend fun fetch()` with `suspendCancellableCoroutine` and `invokeOnCancellation { call.cancel() }`. *Expected:* cancelling the caller invokes `call.cancel()`, and a late callback after cancellation does not resume the caller (prompt cancellation guarantee).

- **E6: Resource safety.** Close a resource in `finally` with a suspending `close()`. *Expected:* without `withContext(NonCancellable)`, the suspending close throws `CancellationException` and does not complete. With it, close completes.
- **E7: Flow pipeline with backpressure.** A sensor flow emits every 10 ms into a slow 50 ms processor. Choose `buffer(capacity, DROP_OLDEST)` vs `conflate()` vs `collectLatest` and justify the choice. Test each with `runTest` and Turbine. *Expected:* show how each drops or keeps items and assert the counts deterministically under virtual time. Remember that Turbine's timeout is wall clock.
- **E8: Hot sharing.** Convert a cold "ticker" repository flow to `stateIn(scope, SharingStarted.WhileSubscribed(5_000), initial)`. Test in `runTest` with `backgroundScope` that the upstream stops 5 s of virtual time after the last subscriber leaves. *Expected:* the upstream's `onCompletion` fires after `advanceTimeBy(5.seconds)` and not before.
- **E9: Channel fan-out / fan-in.** A producer sends 100 jobs into a `Channel(BUFFERED)` and 4 workers consume them with `for (x in ch)`. Fan the results into one channel. *Expected:* all 100 are processed exactly once, and the work spreads roughly evenly (channels are fair). Closing the producer ends the workers' loops.
- **E10: Shared counter.** Increment a counter 100,000 times from 100 coroutines on `Dispatchers.Default`, using plain `var`, `@Volatile`, `AtomicInteger` (or Kotlin `AtomicInt` with opt-in), `Mutex`, and `limitedParallelism(1)`. *Expected:* `var` and `@Volatile` come out below 100,000. The others reach exactly 100,000. Fine-grained confinement and `Mutex` are slowest.
- **E11: Reactor bridge.** Expose `suspend fun user(id)` as `mono { user(id) }` and consume a `Flux` as `flux.asFlow()`. *Expected:* `mono {}` does nothing until subscribed (it is cold). `awaitSingle()` on an empty Mono throws `NoSuchElementException`. Passing a `Job` into `mono(context)` fails with "Mono context cannot contain job in it."
- **E12: Virtual-thread dispatcher (JDK 21+).** `Executors.newVirtualThreadPerTaskExecutor().asCoroutineDispatcher().use { vt -> ... }` runs 10,000 blocking `Thread.sleep(1000)` calls via `withContext(vt)`. Compare with `Dispatchers.IO` and with `Dispatchers.IO.limitedParallelism(10_000)`. *Expected (inferred):* the VT dispatcher and the large IO view both finish in roughly 1 s or a little more, while plain IO takes about ⌈10,000/64⌉ s ≈ 157 s. Cut it short and measure throughput instead. Cancellation of blocked VTs needs `runInterruptible`.
