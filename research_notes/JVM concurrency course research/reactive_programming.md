## Key Question 0: Core reference (source-of-truth facts for every topic in the course)

### Takeaway
Reactive Streams is a small interoperability protocol (4 interfaces, 7 methods, numbered rules) for asynchronous streams with mandatory non-blocking backpressure. `java.util.concurrent.Flow` (Java 9+) mirrors it one-for-one. Reactor's `Flux` (0..N items) and `Mono` (0..1 item) build a lazy, push-pull hybrid operator library on top of it. Nothing runs until `subscribe()`, errors are terminal, and threading is explicit through `Scheduler`s.

### Cited Findings

**Why reactive: push vs pull, backpressure, non-blocking IO**
- Reactive Streams' main goal is "to govern the exchange of stream data across an asynchronous boundary ... while ensuring that the receiving side is not forced to buffer arbitrary amounts of data". It covers libraries that process a potentially unbounded number of elements, in sequence, asynchronously passing elements between components, "with mandatory non-blocking backpressure". — [RS spec README](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/README.md)
- The spec does not cover stream manipulations (transform, split, merge). It only mediates data between API components. It has two parts: the API and a TCK. — [RS spec README](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/README.md)
- Reactor's doc lists three properties of reactive libraries: "Nothing happens until you *subscribe*", "*Backpressure* or the ability for the consumer to signal the producer that the rate of emission is too high", and a "*High level* but *high value* abstraction that is _concurrency-agnostic_". — [Reactor ref: reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)
- A subscriber can work in unbounded mode or use `request(n)`. Operators can change the request in transit, and prefetching avoids `request(1)` round-trips. "This transforms the push model into a *push-pull hybrid*, where the downstream can pull n elements from upstream if they are readily available. But if the elements are not ready, they get pushed by the upstream whenever they are produced." — [Reactor ref: reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)
- Reactor's "assembly line" analogy: Reactor is both conveyor belt and workstations. A clogged workstation "can signal upstream to limit the flow of raw material". — [Reactor ref: reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)
- Spring's own docs on performance: "Reactive and non-blocking generally do not make applications run faster ... The key expected benefit of reactive and non-blocking is the ability to scale with a small, fixed number of threads and less memory ... you need to have some latency (including a mix of slow and unpredictable network I/O)." — [Spring Framework docs: webflux/new-framework.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/web/webflux/new-framework.adoc)

**Reactive Streams contract (spec version 1.0.4, the version in the README's Maven snippet)** — all rules below are from the [RS spec README](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/README.md)
- Interfaces: `Publisher`, `Subscriber`, `Subscription`, `Processor`. Signal grammar: `onSubscribe onNext* (onError | onComplete)?`.
- **1.1** The total number of `onNext`s MUST be <= the total requested. **1.2** A Publisher MAY signal fewer than requested and terminate with `onComplete`/`onError`.
- **1.3** `onSubscribe`, `onNext`, `onError` and `onComplete` MUST be signaled **serially** (no concurrent signals to the same Subscriber).
- **1.4/1.5** A failing Publisher MUST signal `onError`. A Publisher that completes successfully MUST signal `onComplete`. **1.6** After a terminal signal the Subscription MUST be considered cancelled. **1.7** No signals after a terminal state.
- **1.9** `Publisher.subscribe` MUST call `onSubscribe` **prior to any other signals** and MUST return normally, except that a `null` Subscriber gets an NPE thrown to the caller. This is the "onSubscribe-first" rule.
- **1.10** `subscribe` may be called many times, but with a different Subscriber each time. **1.11** A Publisher decides whether each Subscription is unicast or multicast.
- **2.1** A Subscriber MUST signal demand through `request(n)` to receive `onNext`. **2.3** `onComplete`/`onError` MUST NOT call methods on the Subscription or Publisher. **2.5** A Subscriber MUST cancel a second Subscription if it already has an active one. **2.7** Calls to `request`/`cancel` MUST be serial. **2.8** A Subscriber must be prepared for `onNext` after `cancel()`. **2.9/2.10** A Subscriber must be prepared for `onComplete`/`onError` without any prior `request`. **2.12** `onSubscribe` at most once per Subscriber.
- **2.13** Calling `onSubscribe`/`onNext`/`onError`/`onComplete` MUST return normally, "except when any provided parameter is `null` in which case it MUST throw a `java.lang.NullPointerException`". The only legal way for a Subscriber to signal failure is cancelling its Subscription. This is the "no nulls" rule.
- **3.2** `request` must be callable synchronously from `onNext`/`onSubscribe` (so it must be reentrant). **3.3** It must bound synchronous recursion. **3.5** `cancel` must be idempotent and thread-safe. **3.6/3.7** After cancel, further `request`/`cancel` calls are NOPs.
- **3.9** While not cancelled, `request(n)` "MUST signal `onError` with a `java.lang.IllegalArgumentException` if the argument is <= 0".
- **3.10/3.11** `request` MAY synchronously call `onNext`/`onComplete`/`onError`, which means synchronous publishers are legal. **3.12/3.13** `cancel` MUST eventually stop signals and drop references. **3.17** A Subscription must support demand up to `Long.MAX_VALUE`, and demand >= 2^63-1 MAY be treated as "effectively unbounded".
- **4.1** A Processor is both Subscriber and Publisher and obeys both contracts. **4.2** It MAY recover from an `onError`, in which case it MUST consider the Subscription cancelled.

**java.util.concurrent.Flow and SubmissionPublisher**
- `Flow` (`@since 9`) holds `Publisher`, `Subscriber`, `Subscription` and `Processor`. "These interfaces correspond to the reactive-streams specification." "All (seven) methods are defined in `void` 'one-way' message style." `Flow.defaultBufferSize()` returns `DEFAULT_BUFFER_SIZE = 256`. The Javadoc's `OneShotPublisher` example says it "omits some error processing needed to fully conform to the Reactive Streams specification". — [OpenJDK Flow.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/Flow.java)
- `SubmissionPublisher` "asynchronously issues submitted (non-null) items to current subscribers until it is closed". Each subscriber has an independent buffer, created on first use and grown up to a maximum. `submit` "blocks until resources are available". The `offer` methods "may drop items (either immediately or with bounded timeout)" with an optional drop handler. If any Subscriber method throws, its subscription is cancelled. `consume(Consumer)` covers the request-everything case. A second `subscribe` of the same Subscriber gets `onError(IllegalStateException)`. — [OpenJDK SubmissionPublisher.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/SubmissionPublisher.java)
- Default executor, version-specific. In **JDK 21** it is `ForkJoinPool.commonPool()` unless common-pool parallelism is <= 1, in which case it uses a thread-per-task fallback ([jdk21u SubmissionPublisher.java](https://raw.githubusercontent.com/openjdk/jdk21u/master/src/java.base/share/classes/java/util/concurrent/SubmissionPublisher.java)). OpenJDK **master** calls a package-private `ForkJoinPool.asyncCommonPool()` ([OpenJDK master SubmissionPublisher.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/SubmissionPublisher.java); [ForkJoinPool.java](https://raw.githubusercontent.com/openjdk/jdk/master/src/java.base/share/classes/java/util/concurrent/ForkJoinPool.java)). The default max buffer capacity is `Flow.defaultBufferSize()` (256).
- [local run, JDK 21.0.12] `new SubmissionPublisher<>()` reports `getMaxBufferCapacity()=256` and executor class `ForkJoinPool`. `request(0)` produces `onError java.lang.IllegalArgumentException: non-positive subscription request`, so the JDK follows rule 3.9. With capacity 2 and no demand, `offer(i, (s, item) -> false)` dropped 8 of 10 items (`estimateMaximumLag()=2`).
- Bridging. The reactive-streams jar has `org.reactivestreams.FlowAdapters` with `toPublisher`, `toFlowPublisher`, `toFlowSubscriber` and `toSubscriber` (Java 9 source set) — [FlowAdapters.java](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/api/src/main/java9/org/reactivestreams/FlowAdapters.java). Reactor-core says it ships "converters from/to Java 9 Flow" — [reactor-core README (3.8.x)](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/README.md). [local run] `reactor.adapter.JdkFlowAdapter.flowPublisherToFlux(submissionPublisher).take(3)` received `[0, 1, 2]` on 3.8.8.

**Mono and Flux**
- "A `Flux<T>` is a standard `Publisher<T>` that represents an asynchronous sequence of 0 to N emitted items, optionally terminated by either a completion signal or an error." All events are optional: no `onComplete` means an infinite sequence. — [Reactor ref: flux.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/flux.adoc)
- "A `Mono<T>` ... emits at most one item via the `onNext` signal then terminates with an `onComplete` signal ... or only emits a single `onError` signal". `onNext` followed by `onError` is "explicitly forbidden". `Mono<Void>` represents completion only. `Mono#concatWith` returns a `Flux`, while `Mono#then(Mono)` returns a `Mono`. — [Reactor ref: mono.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/mono.adoc)

**Assembly time vs subscription time; cold vs hot**
- "Nothing Happens Until You `subscribe()`": you create "an abstract description of your asynchronous process". Each operator wraps the previous `Publisher` into a new instance. — [Reactor ref: reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)
- On subscribe, "a chain of `Subscriber` objects is created, backward (up the chain) to the first publisher". — [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)
- Cold publishers "generate data anew for each subscription". Hot publishers "do not depend on any number of subscribers". `just` "directly captures the value at assembly time and replays it to anybody subscribing to it later". `defer` makes it cold. `share()` and `replay(...)` turn cold into hot. — [Reactor ref: reactor-hotCold.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/reactor-hotCold.adoc)
- `Mono.just(T)` Javadoc: the item "is captured at instantiation time". — [Mono.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)

**Operators (defaults are version-specific to 3.8.x)**
- Default sizes: `Queues.SMALL_BUFFER_SIZE = max(16, reactor.bufferSize.small default 256)` and `Queues.XS_BUFFER_SIZE = max(8, reactor.bufferSize.x default 32)`. — [Queues.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/concurrent/Queues.java)
- `flatMap(mapper)` delegates to `flatMap(mapper, SMALL_BUFFER_SIZE, XS_BUFFER_SIZE)`, i.e. **concurrency 256, prefetch 32**. `flatMap(mapper, concurrency)` uses prefetch 32. The Javadoc says it eagerly subscribes to inners, "does not necessarily preserve original ordering", and lets values interleave. The concurrency argument "allows to control how many Publisher can be subscribed to and merged in parallel. In turn, that argument shows the size of the first Subscription#request to the upstream." — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `concatMap(mapper)` in 3.8.x is implemented by `FluxConcatMapNoPrefetch`. It "waits for one inner to complete before generating the next one and subscribing to it", preserves order, and "no prefetching is done on the source". — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `flatMapSequential(mapper)` defaults to maxConcurrency 256 and prefetch 32. It subscribes eagerly but "queues elements from late inners until all elements from earlier inners have been emitted", so output is in source order. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `switchMap(fn)` "requests the source for an unbounded amount" and does no prefetch of inners. Each new source item switches to a new inner. `switchMap(fn, prefetch)` is deprecated. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `filter`: when the predicate fails, "the value is ignored and a request of 1 is made upstream". Exceptions thrown by the predicate count as `false` only in `onErrorContinue` mode. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `take(n)`: "If n is zero, the source isn't even subscribed to". It "ensures that the total amount requested upstream is capped at n" (equivalent to `take(n, true)`). Use `take(n, false)` for unbounded upstream request. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java). [local run] `take(3)` gives upstream requests `[3]`. `take(3, false)` gives `[9223372036854775807]`.
- `groupBy` pitfalls (Javadoc): "works best with a low cardinality of groups". "The groups need to be drained and consumed downstream". A high group count "can lead to hanging if the groups are not suitably consumed downstream (eg. due to a flatMap with a maxConcurrency parameter that is set too low)". "To avoid deadlock, the concurrency of the subscriber to groupBy should be greater than or equal to the number of groups created". Groups are unicast and cannot be re-subscribed (`retry`/`repeat`). — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java). The reference guide warns the same way and has a deadlock walkthrough. — [Reactor ref: advanced-three-sorts-batching.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/advanced-three-sorts-batching.adoc)
- Windowing operators are `window`, `windowTimeout`, `windowUntil`, `windowWhile` and `windowWhen`. Buffering mirrors them (`buffer`, `bufferTimeout`, `bufferUntil`, `bufferWhile`, `bufferWhen`). Predicate-based windowing can produce empty windows. — [Reactor ref: advanced-three-sorts-batching.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/advanced-three-sorts-batching.adoc)
- 3.7.0 added support for `Set` in exact `Flux.buffer` (#3822). — [v3.7.0 release notes](https://github.com/reactor/reactor-core/releases/tag/v3.7.0)

**Combining**
- `Flux.zip(a, b)` waits for each source to emit one element, combines them, and "will continue doing so until any of the sources completes. Errors will immediately be forwarded". — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java). [local run] `Flux.zip(just(1,2,3), just("a","b"))` gives `[[1,a],[2,b]]`.
- `Flux.concat` subscribes sequentially and waits for each source to complete. Any error interrupts immediately. `combineLatest` combines "the most recently published value from each" source, and elements "can and will be passed to the combinator multiple times". — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- **`Mono.zip` with empty**: "An error or **empty** completion of any source will cause other sources to be cancelled and the resulting Mono to immediately error or complete, respectively". `Mono.zipDelayError` behaves differently: "If a Mono source completes without value, all other sources are run to completion then the resulting Mono completes empty". — [Mono.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java). [local run] `Mono.zip(delayed, Mono.empty())` gives empty result, and the delayed source is cancelled (`otherCancelled=true`).

**Errors**
- "In Reactive Streams, errors are terminal events." Error operators do not let the original sequence continue. Instead they convert `onError` into "the start of a new sequence (the fallback one)". — [Reactor ref: error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)
- The guide says that with no error handler "`onError` throws an `UnsupportedOperationException`", detectable with `Exceptions.isErrorCallbackNotImplemented`. — [Reactor ref: error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc). [local run] In practice `Flux.error(...).subscribe(v -> {})` returns normally to the caller and logs `[ERROR] Operator called default onErrorDropped - reactor.core.Exceptions$ErrorCallbackNotImplemented`.
- `retry` "works by *re-subscribing* to the upstream `Flux`. This is really a different sequence, and the original one is still terminated." `retryWhen` takes a companion `Flux` of `RetrySignal`. If the companion completes, the error is swallowed. `Retry.max(3)` and the `Retry` builders are the fluent forms. `transientErrors(true)` uses `totalRetriesInARow()`, which resets after a successful `onNext`. — [Reactor ref: error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)
- `Retry.backoff(maxAttempts, minBackoff)` defaults (3.8.x): multiplier `2`, jitter factor `0.5`, scheduler `Schedulers::parallel`, max backoff `Duration.ofMillis(Long.MAX_VALUE)`. On exhaustion the exception message is `"Retries exhausted: " + totalRetries + "/" + maxAttempts`. In transient mode the message includes "in a row (N total)". The delay is `minBackoff * multiplier^iteration`, capped at maxBackoff, then jittered. — [Retry.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/retry/Retry.java); [RetryBackoffSpec.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/retry/RetryBackoffSpec.java); [RetrySpec.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/retry/RetrySpec.java)
- 3.7.0 made the exponential backoff multiplier configurable (#3883). 3.8.0 fixed handling of fractional multipliers in `RetryBackoffSpec` (#4048). — [v3.7.0 notes](https://github.com/reactor/reactor-core/releases/tag/v3.7.0); [v3.8.0 notes](https://github.com/reactor/reactor-core/releases/tag/v3.8.0)
- **`onErrorContinue` is discouraged.** The Javadoc calls it "a specialist operator that can make the behaviour of your reactive chain unclear. It operates on upstream, not downstream operators, it requires specific operator support to work, and the scope can easily propagate upstream into library code that didn't anticipate it". It recommends handling errors inside the inner publisher instead: `.flatMap(id -> repository.retrieveById(id).doOnError(System.err::println).onErrorResume(e -> Mono.empty()))`. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- `timeout(Duration)`: "Propagate a TimeoutException as soon as no item is emitted within the given Duration from the previous emission (or the subscription for the first item)." — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)

**Schedulers (3.8.x)**
- Unless told otherwise, operators keep running on the thread of the previous operator, and the source runs on the thread that called `subscribe()`. A `Scheduler` is like an `ExecutorService` but also acts as a clock, which is what makes virtual time possible. — [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)
- `Schedulers.immediate()` runs on the current thread ("null object"). `single()` is one reusable thread shared by all callers. `parallel()` has as many workers as CPU cores. `boundedElastic()` is for blocking I/O: idle workers are evicted after 60s, threads are capped at "number of CPU cores x 10", and "Up to 100 000 tasks submitted after the cap has been reached are enqueued". `Schedulers.fromExecutorService(...)` and `newXXX` factories are also available. — [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)
- Tuning properties: `reactor.schedulers.defaultPoolSize`, `reactor.schedulers.defaultBoundedElasticSize`, `reactor.schedulers.defaultBoundedElasticQueueSize`, `reactor.schedulers.defaultBoundedElasticOnVirtualThreads`. Past the queue cap a `RejectedExecutionException` is thrown. — [Schedulers.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/scheduler/Schedulers.java)
- **Virtual threads (since 3.6.0).** On "a JDK 21+ runtime" with `reactor.schedulers.defaultBoundedElasticOnVirtualThreads=true`, the shared `boundedElastic()` becomes a thread-per-task implementation where "every submitted task runs on a new VirtualThread instance". It has no idle pool, and the same caps apply. The Javadoc advises: "Consider increasing DEFAULT_BOUNDED_ELASTIC_SIZE with the thread-per-task implementation". — [Schedulers.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/scheduler/Schedulers.java); [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)
- [local run] Without the property, boundedElastic runs on `Thread[#27,boundedElastic-5,...] virtual=false`. With `-Dreactor.schedulers.defaultBoundedElasticOnVirtualThreads=true` on JDK 21.0.12 it runs on `VirtualThread[#22,loomBoundedElastic-1]/runnable@ForkJoinPool-1-worker-1 virtual=true`.
- `publishOn` "affects where the subsequent operators execute (until another publishOn is chained in)" and uses a single thread from the scheduler because `onNext` is serial. `subscribeOn` "Changes the Thread from which the whole chain of operators subscribes". "Only the closest `subscribeOn` call in the downstream chain effectively schedules subscription and request signals to the source ... Using multiple `subscribeOn` calls will introduce unnecessary Thread switches". The doc says the placement of `subscribeOn` "does not matter" but also recommends putting it "immediately after the source". — [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc). `publishOn(Scheduler)` defaults to prefetch `Queues.SMALL_BUFFER_SIZE` (256). — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)
- Blocking in non-blocking threads: `block()`, `blockFirst()`, `blockLast()`, `toIterable()` and `toStream()` inside the default `single` and `parallel` schedulers throw `IllegalStateException`. Custom schedulers opt in through threads that implement the `NonBlocking` marker interface. — [Reactor ref: schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc). The message is `"block()/blockFirst()/blockLast() are blocking, which is not supported in thread " + name`. — [BlockingSingleSubscriber.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/BlockingSingleSubscriber.java)
- Wrapping a blocking call: `Mono.fromCallable(() -> blockingCall()).subscribeOn(Schedulers.boundedElastic())`. "`subscribeOn` does not subscribe to the `Mono`. It specifies what kind of `Scheduler` to use when a subscribe call happens." — [Reactor ref: faq.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/faq.adoc)
- BlockHound "will transparently instrument the JVM classes and intercept blocking calls (e.g. IO) if they are performed from threads marked as 'non-blocking operations only' (ie. threads implementing Reactor's `NonBlocking` marker interface...)". Activate it with `BlockHound.install()`. Failures look like `reactor.blockhound.BlockingOperationError: Blocking call! java.lang.Thread.sleep`. "for JDK 13+ ... please use the `-XX:+AllowRedefinitionToAddDeleteMethods` jvm argument". — [BlockHound README](https://raw.githubusercontent.com/reactor/BlockHound/master/README.md); [BlockHound quick_start.md](https://raw.githubusercontent.com/reactor/BlockHound/master/docs/quick_start.md). Reactor 3.8.0 built against BlockHound 1.0.15.RELEASE, and 3.9.0-RC1 against 1.0.18.RELEASE. — [v3.8.0 notes](https://github.com/reactor/reactor-core/releases/tag/v3.8.0); [v3.9.0-RC1 notes](https://github.com/reactor/reactor-core/releases/tag/v3.9.0-RC1)

**Backpressure operators**
- `limitRate(n)` splits downstream demand into batches capped at n, using "a prefetch-and-replenish strategy, requesting a replenishing amount when 75% of the prefetch amount has been emitted". It is "Equivalent to `flux.publishOn(Schedulers.immediate(), prefetchRate)`" (that is its 3.8.x implementation). Unlike `take`, "All data is still processed". — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java). [local run] `Flux.range(1,40).limitRate(10)` gives upstream requests `[10, 8, 8, 8, 8, 8]`.
- `onBackpressureBuffer()` requests unbounded and parks overflow, with errors delayed until the buffer drains. `onBackpressureDrop()` drops when there is no demand. `onBackpressureLatest()` keeps only the most recent item. `onBackpressureError()` signals an overflow error (`Exceptions.failWithOverflow`). All four request **unbounded** upstream. — [Flux.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)

**Hot publishers: Sinks, share, publish/refCount/autoConnect, cache, replay**
- `Sinks` are for "safe manual triggering of signals". `Processor` implementations "phased out" before 3.5.0. `tryEmit*` fails fast on concurrent calls (e.g. `FAIL_NON_SERIALIZED`). `emitNext(v, EmitFailureHandler.FAIL_FAST)` and `busyLooping(Duration)` are the handler forms, and a `busyLooping` instance cannot be reused. Use `asFlux()`/`asMono()` for views. — [Reactor ref: processors.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/processors.adoc)
- Flavors: `many().multicast()` transmits "only newly pushed data", honoring each subscriber's backpressure. With `onBackpressureBuffer()`, by default when all subscribers cancel it "clears its internal buffer and stops accepting new subscribers" (tunable via `autoCancel`). `directAllOrNothing()` and `directBestEffort()` are the simplistic backpressure variants. `many().unicast()` buffers data pushed before the first subscriber and allows only one subscriber. `many().replay()` uses `all()`, `limit(int)`, `limit(Duration)` or `limit(int, Duration)`. — [Reactor ref: processors.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/processors.adoc)
- [local run] multicast: an early subscriber got `[1,2,3]` and a late one got `[3]`. Items emitted to a multicast `onBackpressureBuffer()` sink **before any subscriber** were delivered to the first subscriber (`[10, 11]`), a warm-up buffer. `replay().limit(2)` late subscriber got `[2, 3]`. A second subscriber to a unicast sink got `IllegalStateException: Sinks.many().unicast() sinks only allow a single Subscriber`.
- `share()` "is an alias for `publish().refCount()`". It cancels the source when all subscribers cancel, and late subscribers may miss items. `Flux.cache()` retains "an unbounded volume of onNext signals" and replays completion and error. `Mono.cache()` caches "indefinitely. This process cannot be cancelled". — [Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java); [Mono.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)
- `ConnectableFlux` comes from `publish` and `replay`. `publish` pauses requesting when any subscriber has 0 pending demand. Connection options: `connect()` manually, `autoConnect(n)` after n subscribers, `refCount(n)`, which also cancels the upstream when subscribers drop, and `refCount(int, Duration)`, which adds a grace period. — [Reactor ref: ConnectableFlux page](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/advanced-broadcast-multiple-subscribers-connectableflux.adoc)

**Context and automatic context propagation**
- `Context` is immutable (`put` returns a new instance). `ContextView` is a read-only superinterface since 3.4.0. The Context "is propagated from the bottom of the chain towards the top". Read with `deferContextual` at a source and with `transformDeferredContextual` mid-chain. — [Reactor ref: context.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/context.adoc)
- Since 3.5.0 reactor-core supports the `io.micrometer:context-propagation` SPI, with no user action beyond having both jars. There are two modes. The **default (limited)** mode restores ThreadLocals only in `handle` and `tap`. The **automatic** mode is enabled with `Hooks.enableAutomaticContextPropagation()` (added 3.5.3), "applies only to new subscriptions", and should be enabled at startup. `contextCapture()` snapshots ThreadLocals into the Context. In automatic mode, blocking operators (`block()`, `blockFirst()`, `blockLast()`, `toIterable()`, ...) perform `contextCapture()` transparently. — [Reactor ref: advanced-contextPropagation.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advanced-contextPropagation.adoc); [Hooks.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Hooks.java)
- 3.6.0 "reinforced the ThreadLocal values restoration mechanics and added extra logic that detects any external Publisher implementations" (example: JDK `HttpClient` body `Flow.Publisher`), so ThreadLocals are no longer lost there. — [Spring blog, O. Dokuka, 2023-10-31](https://spring.io/blog/2023/10/31/what-new-is-coming-in-reactor-core-3-6-0)
- `Hooks.isAutomaticContextPropagationEnabled()` has Javadoc `@since 3.7.12`, and the 3.8.0 notes list it (#4090). — [Hooks.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Hooks.java); [v3.8.0 notes](https://github.com/reactor/reactor-core/releases/tag/v3.8.0)
- [local run] Placement matters: `deferContextual(...).contextWrite(Context.of("k","v"))` sees `v`. A `contextWrite` placed *above* (upstream of) the reader sees `missing`. With two writes of the same key below the reader, the one closest to the reader wins (`inner`).

**Testing (reactor-test 3.8.8)**
- `StepVerifier`: "Remember the `verify()` step, which triggers the verification." Shortcuts include `verifyComplete()`, `verifyError()` and `verifyErrorMessage(String)`. "By default, the `verify()` method and derived shortcut methods ... have no timeout. They can block indefinitely". Use `StepVerifier.setDefaultTimeout(Duration)` or `verify(Duration)`. — [Reactor ref: testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)
- `withVirtualTime(Supplier)` plugs a `VirtualTimeScheduler` into `Schedulers`. You must "always instantiate the `Flux` inside the lambda", otherwise "virtual time is not guaranteed". `thenAwait(Duration)` and `expectNoEvent(Duration)` advance the virtual clock. "`expectNoEvent` also considers the `subscription` as an event", so use `expectSubscription().expectNoEvent(d)`. "All `Schedulers` are replaced with the same `VirtualTimeScheduler`", which can lock the verification. `verify()` returns the real-time `Duration`. — [Reactor ref: testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)
- `TestPublisher`: `next`, `emit` (next + complete), `complete` and `error`. `create()` is well-behaved. `createNonCompliant(Violation...)` takes, among others, `REQUEST_OVERFLOW`, `ALLOW_NULL` and `DEFER_CANCELLATION`. It has `assert*` methods and `flux()`/`mono()` views. `PublisherProbe` checks execution paths such as `switchIfEmpty`. — [Reactor ref: testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)
- [local run] `expectNoEvent(500ms)` as the first step fails with `AssertionError: expectation failed (expected no event: onSubscribe(reactor.core.publisher.MonoDelay$MonoDelayRunnable@...))`.

**Debugging**
- `Hooks.onOperatorDebug()` is a global mode, activated at startup "or at least before the incriminated Flux or Mono can be instantiated". It captures stack traces at assembly, which is "costly", so it is "a last resort". `checkpoint()` covers one chain link. `checkpoint(String)` omits the stack trace and "imposes less processing cost". `checkpoint("description", true)` forces the stack trace. — [Reactor ref: debugging.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/debugging.adoc)
- "Production-ready Global Debugging": `reactor-tools` with `ReactorDebugAgent.init()` as the first line of `main`. It adds debug info "without paying the cost of capturing the stacktrace on every operator call". `processExistingClasses()` re-processes already-loaded classes ("takes a couple of seconds"). It uses ByteBuddy self-attach, or `java -javaagent:reactor-tools.jar`, or build-time ByteBuddy plugin instrumentation (project classes only). — [Reactor ref: debugging.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/debugging.adoc)
- The 2025.0.8 BOM aligns `reactor-tools` 3.8.8 with core. — [reactor-bom 2025.0.8 POM](https://repo1.maven.org/maven2/io/projectreactor/reactor-bom/2025.0.8/reactor-bom-2025.0.8.pom)

## Key Question 2: Which exact semantics do people get wrong?

### Takeaway
The most common errors: assuming work happens at assembly; `Mono.just(expensive())` running eagerly; expecting `flatMap` to keep order; thinking `subscribeOn` placement or repetition changes threads mid-chain; calling `block()` on non-blocking threads; expecting a stream to "continue" after an error; and assuming Reactor signals `onError` for `request(n<=0)`. Each was verified on 3.8.8 below.

### Cited Findings
- **Nothing happens without subscribe.** [local run] A `Flux.range(1,3).map(...)` counter stayed `0` until `subscribe()`, then became `3`. The docs say the same. — [Reactor ref: reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)
- **`Mono.just` evaluates eagerly.** The item "is captured at instantiation time" ([Mono.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)). With an HTTP-call argument, "only one network call is made, when instantiating `just`", and `defer` fixes that ([hot/cold doc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/advancedFeatures/reactor-hotCold.adoc)). [local run] `Mono.just(calls.incrementAndGet())` showed `calls=1` after assembly and still `1` after two `block()`s. `Mono.fromCallable(calls::incrementAndGet)` showed `0` after assembly and `2` after two subscriptions.
- **flatMap ordering.** flatMap "does not necessarily preserve original ordering" ([Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)). [local run, virtual time] With source `3,1,2` and inner delay `i*100ms`: `flatMap` gives `[1,2,3]` done at 300ms. `concatMap` gives `[3,1,2]` done at 600ms. `flatMapSequential` gives `[3,1,2]` done at 300ms.
- **flatMap concurrency is a cap on in-flight inners and the first upstream request.** [local run] `flatMap(blockingCallOnBoundedElastic, 4)` over 20 items gave max in-flight `4` and upstream requests `[4, 1, 1, 1, ...]`. Default `flatMap` first request is `256`. `concatMap` requests `[1, 1, 1, 1]` (no prefetch).
- **subscribeOn placement and repetition.** "Only the closest subscribeOn ... effectively schedules subscription" ([schedulers.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/schedulers.adoc)). [local run] With `subscribeOn(boundedElastic)` placed *after* a `publishOn(single)`, the source still ran on `boundedElastic-5` and operators after `publishOn` ran on `single-1`. With `subscribeOn(single).subscribeOn(boundedElastic)`, the source ran on `single-1` (the one nearest the source wins).
- **`block()` in non-blocking threads.** [local run] `Mono.delay(10ms).block()` inside a `parallel` worker gives `IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread parallel-1`. The same call inside `boundedElastic` is allowed. Caveat: `Mono.just(2L).block()` inside `parallel` **returned 2 with no exception** (a scalar shortcut). Don't use `Mono.just` to demo this check.
- **Errors are terminal.** "any error in a reactive sequence is a terminal event ... it replaces the terminated sequence upstream of it" ([error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)). [local run] `Flux.just(1,2,0,4).map(i -> 8/i).onErrorReturn(-1)` gives `[8, 4, -1]`, so element `4` is never processed.
- **`onErrorContinue` "works" but leaks upstream.** [local run] `map(8/i).onErrorContinue(...)` gives `[8, 4, 2]`. The recommended inner `flatMap(i -> fromCallable(...).onErrorResume(e -> Mono.empty()))` gives the same `[8, 4, 2]` without the upstream-scope hazard ([Flux.java Javadoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)).
- **`retry(n)` re-subscribes and rethrows the original error.** [local run] `retry(2)` on an always-failing source made 3 attempts and surfaced the original exception (`'x'`). `retryWhen(Retry.backoff(3, 100ms).jitter(0))` on an always-failing source made **4 attempts** over 100+200+400 = 700ms of virtual time, then failed with `reactor.core.Exceptions$RetryExhaustedException` (`'Retries exhausted: 3/3'`, cause = original, `Exceptions.isRetryExhausted(e) == true`).
- **Mono.zip with an empty source completes empty, with no error.** See Key Question 0 ([Mono.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Mono.java)). [local run] The result was empty and the other source was cancelled.
- **Reactor vs rule 3.9 (`request(n<=0)`).** The spec says this MUST signal `onError(IllegalArgumentException)` ([RS README](https://raw.githubusercontent.com/reactive-streams/reactive-streams-jvm/master/README.md)). Reactor's `Operators.reportBadRequest(n)` only logs `"Negative request"` at DEBUG ([Operators.java 3.8.x](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Operators.java)). [local run] `Flux.range(1,3)`, `Flux.just(1,2).map(...)` and `publishOn(...)` with `request(0)`/`request(-1)` produced **no signal at all** (no onNext, no onError). The JDK `SubmissionPublisher` produced `onError(IllegalArgumentException: non-positive subscription request)`.
- **Subscribing without an error handler.** The guide says `onError` throws `UnsupportedOperationException` ([error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)). [local run] The caller is not interrupted. Reactor logs `Operator called default onErrorDropped - reactor.core.Exceptions$ErrorCallbackNotImplemented`, so errors are easy to miss in tests that don't assert.
- **`share()` late subscribers miss items.** `share()` = `publish().refCount()`. "late subscribers might therefore miss items" ([Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)). `Mono.cache()` subscribes once and caches forever. [local run] With `Mono.fromCallable(counter).cache()` blocked twice, the source was subscribed once.
- **`StepVerifier` pitfalls.** Forgetting `verify()` means nothing runs. There is no default timeout. A `withVirtualTime` Supplier returning a pre-built Flux breaks virtual time. `expectNoEvent` as the first step fails on `onSubscribe`. — [testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)
- **`groupBy` hang.** [local run] `Flux.range(0,1000).groupBy(i -> i % 300).flatMap(g -> g.reduce(0, Integer::sum), 10)` **hung** (`IllegalStateException: Timeout on blocking read for 3000000000 NANOSECONDS` from `block(3s)`). With concurrency 300 it completed with 300 groups. This matches the Javadoc rule "concurrency ... should be greater than or equal to the number of groups" ([Flux.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/core/publisher/Flux.java)).
- **`subscribeOn` does not subscribe.** "Note that `subscribeOn` does not subscribe to the `Mono`." — [faq.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/faq.adoc)
- **Operators create new instances.** Dropping the return value of `flux.map(...)` means the operator is "not being applied" (FAQ item `faq.chain`). — [reactiveProgramming.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/reactiveProgramming.adoc)

### Inferences
- The `request(0)` divergence is a good "spec vs implementation" teaching moment: Reactor chose lenient logging over `onError`. Students who write raw `Subscriber`s against Reactor will *not* get an error for bad demand, so a stream that silently stalls is the symptom to recognise.
- Use non-scalar sources (`Mono.delay`, `fromCallable` + `subscribeOn`) whenever a demo depends on runtime checks or threading. Scalar sources (`just`, `empty`) take shortcuts.

### Gaps
- I did not find out whether Reactor passes TCK rule 3.9 tests through an exclusion. The `tckTest` suite exists in the build, but its 3.9 handling was not inspected.

## Key Question 3: Reactive vs virtual threads vs Kotlin coroutines, and when maintainers say reactive is still worth it (2025-2026)

### Takeaway
Spring and Reactor maintainers present virtual threads and reactive as **complementary**. Virtual threads remove most of the thread-count reason for async code in request/response apps with blocking I/O. Reactive stays the better tool for **streams, backpressure, cancellation and declarative concurrency (scatter-gather)**. Spring's current docs still say an MVC app that works fine has "no need to change", and that reactive needs real latency to pay off. Reactor joined in by running `boundedElastic` on virtual threads (3.6+). Kotlin coroutines interoperate with Reactor through `kotlinx-coroutines-reactor`, and Spring maps `Mono` to `suspend` and `Flux` to `Flow`.

### Cited Findings
- Mark Paluch (Spring, 2022-10-11): "The reasons to use asynchronous programming models go away in many cases if we start with the assumption that our code runs on Virtual Threads." Also: "asynchronous programming models do not remove the latency of e.g. a network call" — Netty and virtual threads both just switch tasks. — [Spring blog: Embracing Virtual Threads](https://spring.io/blog/2022/10/11/embracing-virtual-threads)
- Same post: "We also believe that ReactiveX-style APIs remain a powerful way to compose concurrent logic and a natural way for dealing with streams. We see Virtual Threads complementing reactive programming models in removing barriers of blocking I/O while processing infinite streams using Virtual Threads purely remains a challenge. ReactiveX is the right approach for concurrent scenarios in which declarative concurrency (such as scatter-gather) matters. The underlying Reactive Streams specification defines a protocol for demand, back pressure, and cancellation of data pipelines without limiting itself to non-blocking API or specific Thread usage." — [Spring blog: Embracing Virtual Threads](https://spring.io/blog/2022/10/11/embracing-virtual-threads)
- Same post: the apps most likely to benefit "without almost any change" are those "not doing anything asynchronous at all", and "there would have to be some actual I/O or other thread parking". In 2022, `synchronized` blocks around blocking I/O pinned carrier threads. — [Spring blog: Embracing Virtual Threads](https://spring.io/blog/2022/10/11/embracing-virtual-threads)
- JEP 491 ("Synchronize Virtual Threads without Pinning") was delivered in JDK 24. Virtual threads blocking in `synchronized` now release their carrier, while native or foreign calls still pin. **This came from a search-result summary only.** openjdk.org did not resolve, so the page was not fetched. — [JEP 491 (not fetched)](https://openjdk.org/jeps/491)
- Oleh Dokuka (Reactor, 2023-10-31): `boundedElastic` "is the main shared scheduler to offload all blocking calls ... However, it uses platform Thread instances by default which may add more contention". With Java 21+ and 3.6.x it can use virtual threads through the system property. — [Spring blog: reactor-core 3.6.0](https://spring.io/blog/2023/10/31/what-new-is-coming-in-reactor-core-3-6-0)
- The current Spring Framework docs (main branch, read 2026-10-30) still say: "If you have a Spring MVC application that works fine, there is no need to change. Imperative programming is the easiest way to write, understand, and debug code." Also: "If you have blocking persistence APIs (JPA, JDBC) or networking APIs to use, Spring MVC is the best choice for common architectures". Also: "keep in mind the steep learning curve ... start small and measure the benefits. We expect that, for a wide range of applications, the shift is unnecessary." And: "The greater the latency per call or the interdependency among calls, the more dramatic the benefits" of the reactive `WebClient`. — [Spring Framework docs: webflux/new-framework.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/web/webflux/new-framework.adoc)
- The same docs on performance: reactive "generally do[es] not make applications run faster". The benefit is scaling "with a small, fixed number of threads and less memory", which needs latency to show. — [Spring Framework docs: webflux/new-framework.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/web/webflux/new-framework.adoc)
- Kotlin coroutines in Spring: `Mono<Void>` becomes `suspend fun`, `Mono<T>` becomes `suspend fun ...: T` or `T?`, and `Flux<T>` becomes `Flow<T>`. "`Flow` is push-based while `Flux` is push-pull hybrid". Flow "Backpressure is implemented via suspending functions". Flow has a single suspending `collect` and operators as extensions. Coroutines support needs `kotlinx-coroutines-core` and `kotlinx-coroutines-reactor` ("Version 1.4.0 and above are supported"). — [Spring Framework docs: kotlin/coroutines.adoc](https://raw.githubusercontent.com/spring-projects/spring-framework/main/framework-docs/modules/ROOT/pages/languages/kotlin/coroutines.adoc)
- `kotlinx-coroutines-reactor` provides the `mono {}` builder ("A cold Mono that starts the coroutine on subscription"), `flux {}` (cold Flux), `Flow.asFlux` ("Converts the given flow to a TCK-compliant Flux", integrated with Reactor `Context` and `ReactorContext`), `Job.asMono`/`Deferred.asMono` (hot Mono) and `Scheduler.asCoroutineDispatcher`. — [kotlinx-coroutines-reactor README](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/master/reactive/kotlinx-coroutines-reactor/README.md)
- The course lab already depends on `kotlinx-coroutines-reactor` 1.11.0 next to reactor-core 3.8.8 (local `labs/reactive/build.gradle.kts`, `labs/build.gradle.kts`).

### Inferences
- A fair 2026 positioning for the course: (1) for request/response over blocking libraries (JDBC/JPA), virtual threads plus imperative code is the default recommendation; (2) for streaming (SSE, WebSocket, Kafka-style pipelines), demand control, cancellation propagation, rate-limited fan-out, retries/timeouts as composable operators, or an already-reactive stack (WebClient, R2DBC, Reactor Netty), Reactor still earns its complexity; (3) Kotlin teams get the reactive runtime with sequential-looking code through coroutines and Flow bridges. This matches the Spring docs and the Paluch post, but it is a synthesis, not a quoted maintainer statement for 2025-2026.
- Virtual threads and Reactor are not either/or inside one app: `boundedElastic` on virtual threads is Reactor's own bridge for unavoidable blocking calls.

### Gaps
- **No 2025-2026 statement by a named Spring or Reactor maintainer** on "when reactive is still worth it" was found and verified. Search turned up only third-party blogs (lucaberton.com, javacodegeeks.com, medium.com) and a DevNexus 2026 session listing whose page did not resolve. These are not maintainer sources and were not used for claims. Simon Baslé and Oleh Dokuka talks were not located.
- No verified benchmark data comparing WebFlux with virtual-thread MVC was gathered. A personal benchmark repo (chrisgleissner/loom-webflux-benchmarks) appeared in search but was not fetched.

## Key Question 4: Good exercises and demos (marble-style tasks, retry with backoff, rate-limited fan-out, StepVerifier virtual time)

### Takeaway
The best exercises make one invisible property observable (laziness, ordering, demand, thread, time) and assert it with `StepVerifier`, `doOnRequest` or thread names. Every "expected outcome" below was produced by running the code against reactor-core 3.8.8 / reactor-test 3.8.8 on JDK 21.0.12, unless marked otherwise.

### Cited Findings
- The reference guide has a "How to read marble diagrams?" appendix and a "Which operator do I need?" appendix, both good sources for marble-style tasks. — [Reactor ref nav.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/nav.adoc)
- `StepVerifier.withVirtualTime(() -> Mono.delay(Duration.ofDays(1))).expectSubscription().expectNoEvent(Duration.ofDays(1)).expectNext(0L).verifyComplete()` is the canonical example. `expectNoEvent` is better than `thenAwait` because it "guarantee[s] that nothing happened earlier than it should have". — [testing.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/testing.adoc)
- The guide's `transientErrors(true)` example: a source that fails twice in a row, recovers, then fails again. `retryWhen(Retry.max(2).transientErrors(true))` succeeds after 6 recorded errors. Without `transientErrors` the second burst exhausts retries. — [error-handling.adoc](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/docs/modules/ROOT/pages/coreFeatures/error-handling.adoc)
- Verified outcomes for the exercises in "Teaching notes" (all [local run]): flatMap/concatMap/flatMapSequential orders and virtual durations; flatMap concurrency 4 gives max in-flight 4 and first request 4; `limitRate(10)` gives requests `[10, 8, 8, 8, 8, 8]`; backoff gives 300ms to success and 700ms to exhaustion with `jitter(0)`; groupBy hang at concurrency 10 with 300 groups; switchMap output `[a0, b0, b1, b2]`; Sinks multicast/replay late-subscriber results; context placement results.

### Inferences
- Set `jitter(0)` in teaching tests of `Retry.backoff`. The default jitter factor is 0.5 ([Retry.java](https://raw.githubusercontent.com/reactor/reactor-core/3.8.x/reactor-core/src/main/java/reactor/util/retry/Retry.java)), so exact virtual-time assertions would otherwise be nondeterministic.
- Always add a timeout (`verify(Duration)` or `StepVerifier.setDefaultTimeout`) in exercises that can hang (groupBy, unbounded sources), so a wrong answer fails fast instead of freezing the build.

### Gaps
- No published course curricula or official Reactor workshop material ("reactor hands-on" style repos) were fetched to compare exercise designs.

## Teaching notes

### Misconceptions to address explicitly (each with the verified fact that corrects it)
1. **"Building the pipeline runs it."** Assembly only builds a description, and subscription triggers the work. Demo: a counter in `map` stays 0 until `subscribe()` [local run].
2. **"`Mono.just(callApi())` is lazy."** The argument is evaluated once at assembly. Use `Mono.fromCallable`/`fromSupplier`/`defer` for per-subscription work [local run: just=1 call for 2 subscribers, fromCallable=2].
3. **"flatMap keeps order."** It interleaves as inners complete. Use `concatMap` (sequential, slowest) or `flatMapSequential` (concurrent, ordered output) [local run: 300ms vs 600ms vs 300ms].
4. **"`flatMap` runs things in parallel threads."** flatMap only subscribes to several inners at once (up to `concurrency`). The parallelism comes from the inners being async (`subscribeOn`, async I/O, delays). With synchronous inners it is sequential on one thread. (Inferred from the Javadoc "subscribed to and merged" wording plus the scheduler doc "operators continue working in the Thread on which the previous operator executed".)
5. **"Put `subscribeOn` where you want the thread switch."** `subscribeOn` affects the subscription path, so the source runs on it wherever it is placed. Only the one nearest the source matters. Use `publishOn` to switch for downstream operators [local run].
6. **"`block()` is fine anywhere."** It throws `IllegalStateException` on `parallel`/`single` threads. It is tolerated on `boundedElastic`. Avoid it in reactive code paths entirely [local run]. Demo with `Mono.delay`, not `Mono.just`, because the scalar shortcut skips the check.
7. **"`onErrorResume` lets the stream continue."** Errors are terminal. The fallback *replaces* the upstream. To skip bad elements, handle errors inside the inner publisher of a `flatMap` [local run: `[8,4,-1]` vs `[8,4,2]`].
8. **"`onErrorContinue` is the easy fix."** It is scoped upstream, depends on operator support, and can leak into library code (Javadoc). Teach it only as a warning.
9. **"`retry(3)` retries 3 times, then I get a nice error."** `retry(n)` gives n+1 attempts and the original error. `Retry.backoff(3, d)` gives 4 attempts and a `RetryExhaustedException` ("Retries exhausted: 3/3") with the original as cause [local run].
10. **"`Mono.zip` fails if one is empty."** It completes empty and cancels the others (Javadoc + local run). Combine with `switchIfEmpty`/`defaultIfEmpty` when an empty result should be an error.
11. **"Backpressure means Reactor buffers for me."** `onBackpressureBuffer/Drop/Latest/Error` all request unbounded upstream and *choose a loss/buffer policy*. True backpressure means honoring `request(n)`. `limitRate` only reshapes requests (`[10, 8, 8, ...]`) [local run].
12. **"Reactor follows every spec rule literally."** Rule 3.9 says `request(0)` → `onError(IAE)`. Reactor operators only log at DEBUG and emit nothing, while the JDK `SubmissionPublisher` errors as the spec requires [local run].
13. **"`share()` = cache."** `share()` (`publish().refCount()`) gives late subscribers only new items and cancels when the count drops to 0. `cache()` replays everything [Javadoc; local run for Mono.cache].
14. **"Virtual threads make Reactor obsolete."** Spring's position: they are complementary. Virtual threads remove the blocking-I/O barrier, while reactive remains the tool for streams, backpressure, cancellation and declarative concurrency. Reactor itself can run `boundedElastic` on virtual threads (3.6+).
15. **"`Schedulers.elastic()`."** Not present in 3.8.x source despite a stale mention in the reference guide. Teach `boundedElastic()`.

### Analogies
- **Assembly line** (from the Reactor docs): operators are workstations, `Publisher` is raw material, and a slow workstation signals upstream to slow down (backpressure).
- **Recipe vs cooking**: assembly writes the recipe (no food yet). `subscribe()` cooks it, and each subscriber of a cold publisher cooks a fresh dish. `Mono.just(x)` is a dish cooked once while writing the recipe.
- **Push-pull hybrid** (Reactor docs): a restaurant where the customer orders `n` plates (`request(n)`) and the kitchen sends plates as they're ready, never more than ordered.
- **TV broadcast vs on-demand video** for hot vs cold: a multicast sink or `share()` is live TV (join late, miss the start), `replay`/`cache` is a DVR, and a cold Flux is on-demand.
- **Context flows upstream like a return address on an envelope**: it is written at the bottom (subscriber side) and visible to everything above.

### Demo ideas (verified outputs on reactor-core 3.8.8 / JDK 21.0.12)
- **Thread tour**: `Flux.range(1,1).doOnNext(log thread).publishOn(Schedulers.single()).doOnNext(log thread).subscribeOn(Schedulers.boundedElastic()).blockLast()` prints `src:boundedElastic-N`, then `afterPublishOn:single-1`.
- **Virtual-thread boundedElastic**: run `Mono.fromCallable(() -> Thread.currentThread() + " virtual=" + Thread.currentThread().isVirtual()).subscribeOn(Schedulers.boundedElastic()).block()` twice. Without the flag it prints `Thread[#..,boundedElastic-N,5,main] virtual=false`. With `-Dreactor.schedulers.defaultBoundedElasticOnVirtualThreads=true` it prints `VirtualThread[#..,loomBoundedElastic-1]/runnable@ForkJoinPool-1-worker-1 virtual=true`. The property must be set before `Schedulers` initialises, so pass it on the JVM command line.
- **Demand made visible**: put `doOnRequest(System.out::println)` above `limitRate(10)` (prints 10, 8, 8, ...), above `take(3)` (prints 3), above `take(3, false)` (prints `Long.MAX_VALUE`), above `flatMap(..., 4)` (prints 4, then 1s), and above `concatMap` (prints 1s).
- **`log()` operator**: insert `.log()` at different points to show `onSubscribe`/`request`/`onNext`/`cancel` signals, the spec's signal grammar in action.
- **Spec vs JDK**: a hand-written `Flow.Subscriber` that calls `request(0)` on `SubmissionPublisher` prints `onError java.lang.IllegalArgumentException: non-positive subscription request`. The same against `Flux.range` prints nothing.
- **SubmissionPublisher saturation**: capacity 2, subscriber that never requests, `offer(i, (s, item) -> false)` × 10 drops 8 items.
- **Flow ↔ Reactor bridge**: `JdkFlowAdapter.flowPublisherToFlux(submissionPublisher).take(3).collectList()` gives `[0, 1, 2]`. `FlowAdapters.toPublisher(...)` is the RS-jar equivalent.
- **Debugging**: compare a stack trace without and with `checkpoint("fetch-user")`, then `Hooks.onOperatorDebug()`, then `ReactorDebugAgent.init()`. The last one needs the `reactor-tools` dependency, which is not in the current lab build.
- **BlockHound**: `BlockHound.install(); Mono.delay(1s).doOnNext(x -> Thread.sleep(10)).block()` gives `BlockingOperationError: Blocking call! java.lang.Thread.sleep` (README). On JDK 13+ add `-XX:+AllowRedefinitionToAddDeleteMethods`. Needs the `io.projectreactor.tools:blockhound` dependency.

### Exercise ideas with expected outcomes (all verified [local run] unless noted)
1. **Marble ordering (virtual time).** Given `Flux.just(3,1,2)` and `i -> Mono.delay(Duration.ofMillis(i*100)).thenReturn(i)`, predict the output and virtual completion time for flatMap, concatMap and flatMapSequential, then assert with `StepVerifier.withVirtualTime`. **Expected:** flatMap `[1,2,3]` @300ms; concatMap `[3,1,2]` @600ms; flatMapSequential `[3,1,2]` @300ms.
2. **Laziness detector.** Count calls for `Mono.just(svc.call())` vs `Mono.fromCallable(svc::call)` across 2 subscriptions. **Expected:** 1 call (at assembly, even before subscribing) vs 0 at assembly and 2 total.
3. **Rate-limited fan-out.** Call a fake blocking service (`Thread.sleep(20)`, wrapped in `fromCallable(...).subscribeOn(boundedElastic())`) for 20 ids with `flatMap(..., 4)`, tracking concurrent calls with an `AtomicInteger`. **Expected:** max in-flight = 4, and upstream sees `request(4)` first, then `request(1)` per completion. Stretch: change to `flatMapSequential(..., 4)` and confirm ordered output with the same concurrency cap.
4. **Retry with backoff against a flaky service.** The service fails on attempts 1-2 and succeeds on 3. Use `Mono.defer(...)` (so each retry re-subscribes) with `.retryWhen(Retry.backoff(3, Duration.ofMillis(100)).jitter(0))`. Test with `withVirtualTime(...).expectSubscription().expectNoEvent(Duration.ofMillis(300)).expectNext("ok@3").verifyComplete()`. **Expected:** passes, 3 attempts. Variant "always fails": `expectNoEvent(Duration.ofMillis(700))`, then an error that is `RetryExhaustedException`, message `Retries exhausted: 3/3`, cause = service error, 4 attempts. Pitfall to teach: without `Mono.defer` (e.g. `Mono.just(svc.call())`) the retry re-subscribes to the same captured value or error and never calls the service again. (This pitfall follows from misconception 2 and was not run as a separate test.) Without `jitter(0)`, exact timing assertions are flaky (default jitter 0.5).
5. **Transient errors.** Reproduce the reference-guide scenario: a source that fails 2× in a row, emits, then fails 2× again, then succeeds. `Retry.max(2)` fails overall, while `Retry.max(2).transientErrors(true)` succeeds with 6 errors counted. **Expected outcome from the reference guide, not re-run locally.**
6. **Timeout plus fallback.** `slowCall().timeout(Duration.ofMillis(500)).onErrorResume(TimeoutException.class, e -> Mono.just(cached))` under virtual time. **Expected:** fallback value after 500ms virtual. The timeout semantics are from the Javadoc. This exact chain was not run.
7. **Mono.zip semantics.** `Mono.zip(Mono.delay(200ms).thenReturn(1), Mono.empty())`. **Expected:** completes empty (no value, no error), and the delayed source is cancelled. Then `zipDelayError`: also empty, but only after the other sources finish (Javadoc).
8. **Hot vs cold with Sinks.** Multicast `onBackpressureBuffer()`: subscriber A, emit 1 and 2, subscriber B, emit 3. **Expected:** A=[1,2,3], B=[3]. `replay().limit(2)` with 1,2,3 emitted before subscribing: **Expected:** [2,3]. Unicast second subscriber: **Expected:** `IllegalStateException: Sinks.many().unicast() sinks only allow a single Subscriber`. Bonus: multicast with emissions before any subscriber gives the first subscriber the warm-up items ([10, 11]).
9. **switchMap (search-as-you-type).** `Flux.just("a","b").delayElements(100ms).switchMap(s -> Flux.interval(60ms).map(n -> s+n).take(3))` under virtual time. **Expected:** `[a0, b0, b1, b2]` ("a" is cancelled when "b" arrives at 200ms).
10. **groupBy deadlock.** `Flux.range(0,1000).groupBy(i -> i % 300).flatMap(g -> g.reduce(0, Integer::sum), 10)` with `block(Duration.ofSeconds(3))`. **Expected:** timeout (hang). Fix by setting flatMap concurrency >= 300. **Expected:** 300 sums.
11. **Context placement.** Read key "k" with `Mono.deferContextual`. **Expected:** `contextWrite` below the reader gives "v". A `contextWrite` above the reader gives "missing". Two writes below give the one nearest the reader.
12. **Blocking detector.** Call `Mono.delay(10ms).block()` inside `.publishOn(Schedulers.parallel()).map(...)`. **Expected:** `IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread parallel-1`. Refactor to `flatMap` and the test passes.
13. **StepVerifier traps.** (a) Write a test without `verify()`; it "passes" vacuously because nothing runs. (b) Make `expectNoEvent` the first step. **Expected:** `AssertionError ... expected no event: onSubscribe(...)`. Fix with `expectSubscription()`. (c) Build the Flux outside the `withVirtualTime` Supplier; virtual time is "not guaranteed" (doc).
14. **Build a spec-compliant Publisher (advanced).** Implement a range `Publisher` that obeys rules 1.1, 1.3, 1.9, 2.13 and 3.9, then test it with `StepVerifier` and `TestPublisher`-style violations (`createNonCompliant(REQUEST_OVERFLOW)` shows what a misbehaving source looks like). **Expected:** the student's publisher emits `onError(IllegalArgumentException)` on `request(0)`, unlike Reactor's lenient operators. The RS TCK, which the spec README describes, can validate it, but TCK use was not set up in the lab.
15. **Kotlin bridge (labs already include kotlinx-coroutines-reactor 1.11.0).** Convert `fun find(id): Mono<User>` to `suspend fun find(id): User?` using `awaitSingleOrNull()`. Expose a `Flow<T>` as `Flux` with `asFlux()`. Build a cold Mono with `mono { ... }`. **Expected:** `mono {}` does nothing until subscribed (README: "A cold Mono that starts the coroutine on subscription"). The `awaitSingleOrNull` name comes from the kotlinx-coroutines-reactive module and was not verified in this research; check the API before publishing.

### Lab-setup notes for lesson writers
- To demo automatic ThreadLocal propagation, add `io.micrometer:context-propagation` (not in `labs/reactive/build.gradle.kts`) and call `Hooks.enableAutomaticContextPropagation()` at startup. It applies only to new subscriptions.
- To demo `ReactorDebugAgent`, add `io.projectreactor:reactor-tools:3.8.8` (aligned in BOM 2025.0.8). For BlockHound add `io.projectreactor.tools:blockhound` plus `-XX:+AllowRedefinitionToAddDeleteMethods`.
- Pass the virtual-thread flag as a JVM arg, e.g. `tasks.withType<JavaExec> { jvmArgs("-Dreactor.schedulers.defaultBoundedElasticOnVirtualThreads=true") }` (Gradle syntax is illustrative). The behavior itself was verified with a plain `java -D...` run.
- In tests that might hang, use `StepVerifier.setDefaultTimeout(Duration.ofSeconds(5))` (from the reference guide).
